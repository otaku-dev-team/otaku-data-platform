## 1. 定位与原则

- **纯规则、可解释、按站烘焙**：不引模型、不照搬网站未定口径、不写 `otaku` 硬编码。
- 第一阶段体验纵深的核心算法，**优先级最高**，可能需要跨模块多人投入。
- 客户端只做渲染与本地展示优化，**打分与画像聚合在服务端**。

## 3. 画像（#401 聚合 + #375 渲染）

聚合维度（草案）：

- `typeWeights`：作品类型偏好权重
- `tagWeights`：标签偏好权重
- `ratingTendency`：评分倾向（均值 / 分布）
- `recentActive`：近期活跃作品/标签

读取契约（草案，待三人确认）：

```
GET /api/profile
→ {
     "typeWeights": { "<type>": <float> },
     "tagWeights":  { "<tag>":  <float> },
     "ratingTendency": { "mean": <float>, "dist": [...] },
     "recentActive": [ "<workId>", ... ]
   }
```

## 4. 规则引擎（#373 原型 → #402）

从 #373 落地的规则（可解释、加权求和）：

1. **标签/类型协同**：基于画像 `tagWeights` / `typeWeights` 对候选打分。
2. **评分倾向**：偏好高均分或特定分布（结合 `rating_count` 阈值，低票不计入倾向）。
3. **时效/新鲜度**：近期、未看作品加权。
4. **站内共现**：协同过滤式（同看/同标签用户的交集作品）。

输出：候选作品带 `score`，截断 Top-N。

> 关联 / 相似（作品↔作品、资讯↔作品、实体反查、系列）的重构提案与分阶段路线见 [`relation-algorithm.md`](./relation-algorithm.md)。

## 5. 推荐 API（#402）

```
GET /api/recommend?limit=N
→ [ { "workId": "<id>", "score": <float>, "reasons": ["<ruleKey>", ...] } ]
```

- `reasons` 可解释，对应命中的规则，供客户端展示"为什么推荐给你"。
- `score` 范围与归一方式待三人确认。

## 6. 客户端渲染（#375 / #376）

- 消费 `/api/profile` 与 `/api/recommend`，**不自算打分**。
- 本地展示优化：排序微调、去重、空态、理由标签展示。
