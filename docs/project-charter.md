## 1. 总目标（唯一上位目标）

> **把平台做成来源站可以直接复用的客户端能力底座**：任何来源站都能以低接入成本获得一套跨手机与桌面的可用客户端，用户在平台获得比来源站原生页面更顺手的浏览与个人数据体验，并且**随时能一键回到原站**。

三条支撑目标（服务于总目标，不单独成为目的）：

| # | 支撑目标 | 含义 |
|---|---|---|
| G1 | **体验优于来源站原生页** | 客户端的浏览、搜索、发现、离线、个人数据管理，要比来源站自己提供的页面更好用 |
| G2 | **来源站接入成本趋近于零** | 新接一个来源站 = 加一份适配器配置，不改客户端、不改接口②③④ |
| G3 | **用户不被困在平台内** | 平台是体验增强层而非替代品；任何作品都能回到原站，且各站数据不串 |

**判定一条工作是否值得做，只问一句：它是否让某个来源站（或其用户）得到更好的客户端体验？** 不服务于这一句的，本轮不做。

- 账号体系重做、收藏模型重构——阶段 2 已通过验收，不重开。

- 依赖"先有服务器"才能推进的工作（W6 除外的任何前置）——按 2026-10-22 决议，服务器先按"没有"算。

## 3. 授权与自治规则

### 3.1 授权（本文的核心）

> **总目标由项目定；各模块的目标、拆解、顺序与验收，由各模块负责人在总目标框架内自行确定并自行推进。**

具体而言，以下事项**不再需要我逐条审批**，模块负责人直接做：

| 类别 | 具体内容 |
|---|---|
| **目标设定** | 在总目标 G1–G3 与工作流范围内，自行确定本模块的目标、里程碑、优先级与验收标准；也包括提出并推进**本模块的新目标** |
| **技术选型** | 框架、语言、库、存储方案、第三方 SDK、构建与发布工具链 |
| **内部结构** | 目录结构、模块划分、状态管理、抽象层次、内部重构、代码风格与提交规范 |
| **功能形态** | 功能如何组织、交互如何设计、是否拆成多个模块、是否加开关与灰度 |
| **过程安排** | 任务拆分、提交节奏、分支策略、评审方式、测试策略、文档位置 |
| **技术债** | 自选时机清理，不必等业务需要 |

**唯一需要我或团队介入的，是下面 3.2 的红线；其余一律自主。**

### 3.2 红线（必须回来确认，其余事项不得自行突破）

1. **跨模块接口或数据结构变更** —— 对外端点、请求/响应字段、错误码、语义（如"null 不覆盖"）、唯一标识规则、分页与排序约定。此类变更仍走**三人确认 + 落 `docs/` 契约**，流程不变。
2. **铁律边界** —— 来源站只读、不回写、不代持凭据、不抓登录后内容；来源站用户数据与评论不进平台；"来源是事实、平台是缓存"的快照语义（含"抓不到 ≠ 已删除"）；作品在来源侧消失不删库。
3. **密钥与凭据** —— 不入库、不进日志、不进客户端；来源站凭据不进平台。
4. **生产数据与对外服务** —— 破坏性数据操作、对外承诺的服务等级、真实用户数据的导出。

> 红线**不是审批清单，而是边界清单**：只要不触碰红线，模块内的任何做法都不需要事先请示。红线之内若确有变更需要，按 §5 流程发起确认即可——**发起不等于等待批准**，可以先做不影响他人的准备工作。

### 3.3 需要知会（不阻塞推进）

以下情形**知会一声即可**，不需要等回复：新引入重量级第三方依赖；改变数据规模或性能假设（如"列表要支持百万级"）；调整对外错误码的触发条件；引入新的第三方服务账号。

### 3.4 鼓励的创新方式

- **允许试错**：探索性实现可以先落在实验分支或功能开关后，失败即回滚，不算失误；把"没做成"如实写下来同样是有价值的产出。
- **允许推翻旧实现**：只要契约不变、验收标准不被降低，可以重写自己或前任的实现。
- **允许提新目标**：发现总目标范围内但当前没人认领的机会，直接立项推进，无需等我派工。
- **要求**：创新必须可验证——每个交付物都要能说清"用什么证据证明它达成了目标"。

### 3.5 合并权限：三人平等，谁都可以随时合

> **2026-10-24 决议**（本节优先于 §4 表格里"我核对 / 我确认"的旧表述，该表格改为描述**核对归口**，不再构成合并闸口）。

**@zhengmin486、@riceyu02、@pyxz0 三人拥有完全相同的合并权限**：任何人可以合并任何人的 PR，**也可以合并自己开的 PR**——不需要指派 reviewer，不需要等别人点头，不需要"谁提的谁不能合"。

能合的门槛只有三条，满足即可合：

1. **CI 全绿**（CI 覆盖到的 job 都要过）。CI 没触发或跑挂的分支不合——这正是 stacked PR 底座被重写后要重新改基的原因（参见 [`merge-queue.md`](merge-queue.md)）。
2. **不触碰 §3.2 红线**。红线相关的事项仍然先走三人确认；确认没走完之前不因"急着合"而破例，红线以外的不必等任何人。
3. **PR 里说清楚**：改了什么、冲突（如果有）怎么解的、回滚怎么走。谁合的，谁负责把这段话留下。

两条惯例（约定，不是门槛）：

- 合别人的 PR 前扫一眼正文与 diff 意图；有疑问先在 PR 里问一句，不阻塞其他部分的推进。
- stacked PR 按栈序走（合栈顶、关底座，或改用 merge commit 后先合底座）；合并后**把源 PR 关掉**，并在里面留一句"已随 #NNN 合入"，避免同一个 PR 被合两次。

> 这条规则的代价是**合并变快、冲突与返工可能变多**；但三人都在同一个 main 上，返工的成本低于"等一个人口头批准"的等待成本。因此统一取"先合、出问题就在 PR 里就地修"，不设审批队列。

## 4. 验收与信任机制

| 事项 | 归口 | 负责人 |
|---|---|---|
| 模块内成果是否达标 | **模块负责人自评**，附证据（测试、真机录屏、指标、before/after） | 模块负责人 |
| 跨模块行为是否一致 | 涉及另一模块的部分，**由对方复核一次**（限 1 轮，不做连环评审） | 消费方 |
| 契约是否一致 | 我核对契约与实现是否对齐 | zm |
| 红线是否被触碰 | 我核对 | zm |
| 里程碑是否达成 | 我确认 | zm |

**我只看四件事**：里程碑与总目标的对应关系、契约是否仍然一致、红线是否被触碰、有没有阻塞。日常进度不需要向我汇报；**完成时带着证据来**即可。

> §4 这张表是**核对归口**（谁适合看什么），不是合并闸口：核对结论不阻塞任何一个 PR 进 main（§3.5）。

## 5. 变更与决策流程

| 变更类型 | 流程 | 耗时预期 |
|---|---|---|
| 模块内实现 | 自主 → PR → CI 全绿 → **三人任一自行合入**（可自合，见 §3.5） | 不设闸口 |
| 跨模块契约变更 | 提案（写清改什么 / 为什么 / 影响谁） → 三人确认 → 落 `docs/` → 各方实现 | 以确认完成为准 |
| 探索项立项 | 提案 → 三人确认 → 并入工作流 | 同上 |
| 红线相关 | 一律走三人确认，不设例外 | — |

**决策原则**：三人意见不一致时，先按"对来源站与用户最有利、且不破坏铁律"的方案执行，并在文档中记录分歧；不因为分歧而停摆。
