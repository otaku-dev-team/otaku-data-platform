## A 类 · 商务与商业模式（客户必问，最紧急）

### A1 应用商店的上架主体与开发者账号归属

> ✅ **已定（2026-10-24）：按建议执行。** 默认以**客户（网站）名义**上架；客户无开发者账号时由我们代管，但**合同须写明迁移义务与条件**；包名（`applicationId`）一律按站点独立命名。

- **问题**：以**网站的名义**上架，还是以**我们的名义**？开发者账号归谁？
- **为什么现在要定**：客户一旦问"这是我的 App 吗"，这个问题绕不过去；且账号归属决定**迁移成本**——换主体意味着重新上架、丢评分与评论。
- **建议**：
  - **默认用客户的开发者账号**（商店显示他的名字，最符合"这是你的客户端"）；
  - 客户没有账号时，可用我们的账号代上架，但**合同写明迁移义务与条件**；
  - 包名（`applicationId`）一律按站点独立命名，从一开始就避免冲突。
- **不定的后果**：首站上架时临时决定，容易用成我们的账号，之后客户要独立出去就得重新上架。

### A2 私有化部署的交付边界

> ✅ **已定（2026-10-24）**：私有化**只交付"该网站自己使用的那一个端"**——即使额外付费，
> **也不提供可以取代我们市场地位的东西**（多站接入能力、站点配置能力、底座的平台能力）。
> 可交付：该站点的可运行客户端 + 其配套后端单站实例 + 部署与运维文档。
> 不可交付：接入其他站点的能力、站点配置、可复制本平台商业模式的部分。
> 架构上**预留由客户接管自己这一端的空间**，但接管范围仅限他自己用的端。

- **问题**："私有化"具体交付到什么程度？可运行系统 + 文档？是否含源码？是否含后续升级？
- **为什么现在要定**：这是报价与责任划分的基础，也是"留个架子"到底留多大的问题。
- **建议**：
  - 标准交付 = **可运行系统 + 部署文档 + 运维手册 + 培训**；
  - **源码**作为可选项单独计价，不默认给；
  - **升级服务**单独签（或按年续），不默认永久免费升级；
  - 架构上预留"客户自行接管"的接口与配置层——这部分**现在就该设计**，否则将来补不动。
- **不定的后果**：客户以为"买断=含源码+永久升级"，交付时必然扯皮。

### A3 计价维度与报价机制

> ✅ **已定（2026-10-24）：先定计价维度，数字继续 `[待定]`。** 五个维度：
> ① **接入站点数**；② **客户端形态数**（手机 / 桌面 / 小程序等）；③ **是否需要身份打通**；
> ④ **是否私有化部署**；⑤ **是否含站主运营后台**。
> 对外话术：按这五维评估，确认需求范围后给出报价——**先给结论再谈价**。
- **为什么现在要定**：客户问"多少钱"时我们已经答过一次"待定"，再答不出会显得不专业。
- **建议**：
  - **报价数字继续用 `[待定]`**（尚无交易，不编数字——这是纪律）；
  - 但先把**计价维度**定下来，回答时就能给结构而不是空白：
    ① 接入站点数；② 客户端形态数（手机 / 桌面 / 小程序）；③ 是否需要身份打通；④ 是否私有化部署；⑤ 是否含站主运营后台。
  - 对外话术："按这五个维度评估，确认需求范围后给出报价"，**先给结论再谈价**。
- **不定的后果**：每次被问价都要临时拼口径，容易前后不一致。

### A4 站主运营后台的排期与首版范围

- **问题**：范围已定（可管自己、不可管别人、站点配置不给），**什么时候做、首版做什么**？
- **为什么现在要定**：客户必然会问"我能不能管理我的 App 的用户和数据"；目前答案是"能，但还没建"。
- **建议**：
  - 列为正式 Issue，**排在阶段 2 联调之后**；
  - 首版只做三件事：查看自己站点的数据概览、管理自己站点的用户、查看同步状态；
  - **不做**：站点配置、跨站管理、底座管理（已定原则）。
- **不定的后果**：客户问到时只能说"在规划中"，可信度打折。

## B 类 · 对客户的承诺边界

### B1 客户端能力承载清单（App 原生 vs 跳网站）

- **问题**：哪些能力 App 原生做、哪些跳网站？需要一份**按站点维护的动态清单**。
- **为什么现在要定**：客户已经质疑过"什么都跳回网站，要你们干什么"。没有清单，这句质疑无法正面回应。
- **建议**：
  - 首站先定稿一版清单（浏览 / 检索 / 详情 / 注册登录 / 收藏 / 跨端同步 = 原生；评论 / 投稿 / 后台 = 跳网站）；
  - 写进文档并**随版本更新**，客户能直接看到"哪些已经有了、哪些在路上"。
- **不定的后果**："跳转是补位不是主路径"永远只是口号。

### B2 交付形态与路线图（小程序 / iOS / 原生 App）

- **问题**：小程序、iOS 是否列入路线图？要不要给时间？
- **为什么现在要定**：客户要的"App 或小程序"里，小程序是很常见的诉求。
- **建议**：**列入路线图，不给时间承诺**；客户主动问时明确说明"当前已打通 Flutter（Android + 桌面），小程序在路线图中"。
- **不定的后果**：要么过度承诺，要么客户以为永远不会有。

### B3 运行责任与 SLA

- **问题**：线上谁负责？可用性承诺？故障响应？数据备份谁做？
- **为什么现在要定**：持续服务模式下这是我们的责任，私有化模式下是客户的——两种模式必须写清楚。
- **建议**：
  - **持续服务**：我们负责运行与保障，SLA 另行约定；
  - **私有化**：客户自担运行责任，我们提供文档与支持（可另购）；
  - **数据备份**责任归属在合同里写明。
- **不定的后果**：线上出故障时互相指责，是最伤合作的一类问题。

## C 类 · 技术与契约（需拍板或补充事实）

### C1 授权端点的形态

- **问题**：标准 OAuth2 / OIDC，还是站主自研的"一次性登录票据"接口？
- **建议**：**一次性票据起步**——站主实现成本低（一个接口即可），只要满足"密码不经平台、令牌可撤销"；后续需要再升级到 OAuth2。
- **不定的后果**：站主想做也不知道做成什么样。

### C2 是否向首站站主提出授权端点需求（含收藏读写）

> ✅ **已定（2026-10-24）：站主后续会做、也会给，但当前还没有——先做好准备。**
> 即：现在**不实现**，但**接口契约与适配层先就位**，授权端点一到即可接入，不用返工。

- **问题**：要不要现在就去问 Otaku 站主：能否开放授权端点？收藏与状态是否开放读写？
- **为什么关键**：这是解锁"用户丝滑使用"的**唯一钥匙**，也是客户体验最大的缺口。
- **建议**：**直接问**，一次问清三件事：① 能否开放授权端点；② 收藏/状态能否读写；③ 登录用户可见内容是否在授权范围内。
- **不定的后果**：身份打通永远停在"目标状态"，客户体验始终是短板。

### C3 身份迁移方案（建议现在就做的技术准备）

> ✅ **已定（2026-10-24）：做好准备。** 现在不切换，但**用户表现在就预留「身份源 + 外部用户 ID」**，
> 将来切换只做映射、不返工。

- **问题**：平台账号 → 来源站身份切换时，已有收藏如何映射？
- **建议**：**不必现在实现，但表结构现在就要支持**——用户表预留"身份源 + 外部用户 ID"字段，将来切换只做映射不做重构。这是成本最低的先行动作。
- **不定的后果**：等要切换时才发现表结构不支持，返工代价大。

### C4 收藏双向同步的触发时机

- **问题**：实时写回，还是登录时批量同步？
- **建议**：**登录时批量拉取 + 变更时增量写回**，简单可靠，避免实时同步的一致性与限流问题。
- **不定的后果**：实现时临时选，容易选到复杂且易错的方案。

### C5 契约 §10 遗留的三人确认项

- **问题**：`stage1-minimal-contract.md` §10 尚有未确认项（评分尺度 `0-10` 是否直接入库、单批上限 500 是否合适、字段集是否够用、站内 ID 稳定且不回收等）。
- **建议**：**批量过一遍**，能定的定掉；站内 ID 稳定性这条**必须向站主确认**（它是 `(source, source_id)` 唯一键成立的前提）。
- **不定的后果**：契约长期挂着"待确认"，新人接手分不清哪些是已定的。

## D 类 · 数据事实待补充

### D1 首站数据覆盖率是否补

- **问题**：封面约 2.7%、评分约 36.2%、简介 84%+。要不要补？
- **建议**：
  - **评分不补**（无可靠来源，补了就是编数据）；
  - **封面可用 Bangumi 只读 API 补**（需要令牌，走 PR 通知团队、令牌存环境变量不入库）——但受限于资源，可列为可选；
  - 无论补不补，**客户端的占位路径必须完整**（这条已经写进契约）。
- **不定的后果**：客户看到大量无封面作品，观感差，但也不是硬伤。

## 附：已定事项（备查，防止反复）

| 项 | 结论（2026-10-24 拍板） |
| --- | --- |
| 商业模式 | **持续服务**（默认）+ **私有化部署**（预留自行接管的架构空间）；**源码买断不做** |

| 商务数字 | 一律 `[待定]`，**禁止编造**；只给三档结论 + 先给结论再排期 |
| 客户端归属 | 客户端是**网站的**，不是平台的；品牌、用户、内容、数据归属网站 |
