## A 类 · 商务与商业模式（客户必问，最紧急）

### A1 应用商店的上架主体与开发者账号归属

> **已定（2026-10-24）：按建议执行。** 默认以**客户（网站）名义**上架；客户无开发者账号时由我们代管，但**合同须写明迁移义务与条件**；包名（`applicationId`）一律按站点独立命名。

- **问题**：以**网站的名义**上架，还是以**我们的名义**？开发者账号归谁？
- **为什么现在要定**：客户一旦问"这是我的 App 吗"，这个问题绕不过去；且账号归属决定**迁移成本**——换主体意味着重新上架、丢评分与评论。
- **建议**：
  - **默认用客户的开发者账号**（商店显示他的名字，最符合"这是你的客户端"）；
  - 客户没有账号时，可用我们的账号代上架，但**合同写明迁移义务与条件**；
  - 包名（`applicationId`）一律按站点独立命名，从一开始就避免冲突。
- **不定的后果**：首站上架时临时决定，容易用成我们的账号，之后客户要独立出去就得重新上架。

### A2 私有化部署的交付边界

> **已定（2026-10-24）**：私有化**只交付"该网站自己使用的那一个端"**——即使额外付费，
> **也不提供可以取代我们市场地位的东西**（多站接入能力、站点配置能力、底座的平台能力）。
> 可交付：该站点的可运行客户端 + 其配套后端单站实例 + 部署与运维文档。
> 不可交付：接入其他站点的能力、站点配置、可复制本平台商业模式的部分。
> 架构上**预留由客户接管自己这一端的空间**，但接管范围仅限他自己用的端。

- **问题**："私有化"具体交付到什么程度？可运行系统 + 文档？是否含源码？是否含后续升级？
- **为什么现在要定**：这是报价与责任划分的基础，也是"留个架子"到底留多大的问题。
- **建议**：
  - 标准交付 = **可运行系统 + 部署文档 + 运维手册 + 培训**；
  - **源码**作为可选项单独计价，不默认给；
  - **升级服务**单独签（或按年续），不默认永久免费升级；
  - 架构上预留"客户自行接管"的接口与配置层——这部分**现在就该设计**，否则将来补不动。
- **不定的后果**：客户以为"买断=含源码+永久升级"，交付时必然扯皮。

### A3 计价维度与报价机制

> **已定（2026-10-24）：先定计价维度，数字继续 `[待定]`。** 五个维度：
> ① **接入站点数**；② **客户端形态数**（手机 / 桌面 / 小程序等）；③ **是否需要身份打通**；
> ④ **是否私有化部署**；⑤ **是否含站主运营后台**。
> 对外话术：按这五维评估，确认需求范围后给出报价——**先给结论再谈价**。
- **为什么现在要定**：客户问"多少钱"时我们已经答过一次"待定"，再答不出会显得不专业。
- **建议**：
  - **报价数字继续用 `[待定]`**（尚无交易，不编数字——这是纪律）；
  - 但先把**计价维度**定下来，回答时就能给结构而不是空白：
    ① 接入站点数；② 客户端形态数（手机 / 桌面 / 小程序）；③ 是否需要身份打通；④ 是否私有化部署；⑤ 是否含站主运营后台。
  - 对外话术："按这五个维度评估，确认需求范围后给出报价"，**先给结论再谈价**。
- **不定的后果**：每次被问价都要临时拼口径，容易前后不一致。

### B3 运行责任与 SLA

> **已定（2026-10-24 负责人拍板）**：**持续服务 = 我们负责**运行与保障（可用性承诺
> 另行约定）；**私有化 = 客户自担运行责任，但我们在必要处提供配合**（文档与支持，
> 深度支持可另行约定）；**数据备份责任归属写进合同**。已同步
> [`how-we-serve-sites.md`](how-we-serve-sites.md) §1.8 新增「运行责任」行。

- **问题**：线上谁负责？可用性承诺？故障响应？数据备份谁做？
- **为什么现在要定**：持续服务模式下这是我们的责任，私有化模式下是客户的——两种模式必须写清楚。
- **建议**：
  - **持续服务**：我们负责运行与保障，SLA 另行约定；
  - **私有化**：客户自担运行责任，我们提供文档与支持（可另购）；
  - **数据备份**责任归属在合同里写明。
- **不定的后果**：线上出故障时互相指责，是最伤合作的一类问题。

### B4 首站数据来源的授权与合规（待办，需负责人与站主沟通）

> **现状**：我们通过读取 Otaku 的公开接口取数 —— 这是**尚未建立正式客户关系时的权宜之计**，
> 不是产品固有形态。正常形态应为：客户授权 → 提供数据来源（接口或数据库）→ 我们接入。

- **问题**：首站至今没有正式的授权约定，数据源是"我们自己读来的"。
- **为什么现在要定**：长期是合规敞口 —— 对方改结构、加登录墙或追究起来，数据源就断；
  且首站只有转成正式关系，才成为**第一个可复制的客户范式**（授权 → 接入 → 客户端）。
- **需要沟通的三件事**（本文不擅自推进）：
  1. 把"读取公开接口"转为**合同约定的授权接入**；
  2. 明确历史数据的交付方式（对方给数据库导出，还是由我们灌库）；
  3. 明确新增数据的同步方式（对方推给我们，还是我们按约定频率拉取）。
- **不定的后果**：首站一直停留在"我们先做出来再谈"的状态，既不能作为样板对外讲，也随时可能断粮。

> 关联原则：[`technical-self-reliance.md`](technical-self-reliance.md) —— 靠抓数据是首站个例，
> 不是通用能力；且不要向客户索要开发能力，能用技术解决的先自己解。

  `min_rating=9`（意图 ≥9/10）返回 31 条而非 5 条。**全程不报任何错**，而这正是 W2 刚上线的两个能力。
  证据见 [`w4-second-site-report.md`](w4-second-site-report.md) §5。
- **备选与取舍**：A 案（适配器归一）把换算规则留成隐式约定，写错没人拦；C 案（`ORDER BY rating_value / scale`）
  索引失效，57 万条上不可行。B 案用一条校验把「静默错」变成「显式错」，不引入新概念。
- **不定的后果**：每接一个尺度不同的站，榜单与 `min_rating` 都是错的且无人察觉；已入库的错值要重导。

| 项 | 结论（截至 2026-10-25 拍板） |

| 站主运营后台 | 可管**自己**的用户与数据；不可管其他站或底座；**站点配置不给**（是底座核心能力） |
| 身份归属 | 网站已有用户 → **用网站的账号**；平台账号**仅过渡**，须预留切换路径 |
| **账号全渠道统一** | **所有渠道（网站 / App / 站主后台 / 未来小程序·iOS）共用同一套网站账号**——不是"各有一套再打通"，而是**不存在第二套**；**App 内可注册**（体验优先），但账号必须创建在**网站侧**；站主后台用网站账号登录 + 平台侧站主名单校验（OAuth scope 仅 identity，不带管理员标识）；平台账号仅过渡、非终态，须预留切换路径（账号映射 + 收藏迁移）。见 [`site-owner-console-proposal.md`](site-owner-console-proposal.md) §3.1 / §4.1 |
| App 注册入口 | **App 内要能注册**（2026-10-25 拍板），账号建在网站侧，**无任何对外依赖**：网站已有完整注册流程（`/register` 两步：邮箱验证码 + 提交）、且实测确认**邀请码可选**（普通用户可留空，仅管理员权限需要）。方案 = **App 内 WebView 承载网站注册页**，密码只在网站页面内、不经我们，不撞"代收密码转发"红线；**App 原生表单直 POST 一票否决**（= 代收用户密码转发）。网站不可用时的降级与责任边界见 [`app-registration-approach.md`](app-registration-approach.md) §7 |
| 授权关系判据 | 禁止=代收密码 / 持服务凭据 / 代爬；**允许=用户授权后可撤销令牌** |
| 多站形态 | 每站**独立客户端**（应用名 / 图标 / 包名按站独立）；**不做"一个 App 选站点"** |
| 商务数字 | 一律 `[待定]`，**禁止编造**；只给三档结论 + 先给结论再排期 |
| 客户端归属 | 客户端是**网站的**，不是平台的；品牌、用户、内容、数据归属网站 |
| 平台职责边界 | **平台不碰内容与运营** —— 内容只有网站运营在改，平台侧不产生内容、不做运营决策；站主后台是平台侧管理（看数据 / 管用户 / 同步状态），**不是 CMS、不做内容录入** |
| 技术自解优先 | **能用技术解决的，绝不麻烦客户开发接口**；先试"承载客户现有页面"，客户没有对应页面才谈接口。见 [`technical-self-reliance.md`](technical-self-reliance.md) |
