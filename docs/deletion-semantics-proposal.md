## 1. 结论先说

**取方案 B：新增 `POST /internal/import/deletions`，按 `(source, source_id)` 软删（`deleted_at`），
对外查询一律过滤。**

不进接口②，理由三条：

| 理由 | 说明 |
| --- | --- |
| 语义单一 | ②是「写入这批数据」，删除是「这批不再存在」。塞进同一个批次后，`on_missing` 三档、整体替换语义、500 上限都要重新解释 |
| 不动既有契约 | ② 的字段、批上限、三态语义一个不改，两端都没有迁移成本 |
| 可重放 | 端点幂等，网络中断后原样重发即可；混在②里重发会连带重跑写入 |

**软删而不是物理删**：源站误删、回滚、临时下架都能恢复；且不破坏收藏等外部引用。

## 2. 现状：缺口已经存在，不是等增量同步才出现

- 后端写作品是 `(source, source_id)` 的 upsert，**没有任何删除通道**。源站删掉的作品一直留在库里，
  列表里搜得到、点进去是旧数据。
- sync 侧**已经能算出谁被删了**：`--export-dataset` 会落 `<数据集>.diff.json`，其中
  `kinds.<kind>.deleted` 是**完整 id 列表**（不是计数），来自内容指纹对比
  （`manifest.py::diff_manifests`，上次有、这次没有）。
- ⚠️ **键的含义变了**：#264 之后发给后端的 `source_id` 是 **bangumi subject id**（`contents.bangumi_id` 重键），
  即 `deleted` 列表里的 id 与后端 `work.source_id` 同源，可以直接喂给端点。若沿用旧的
  `otaku.json`（源站 content id），删除名单会错杀同号的陌生作品。

所以缺的只有一件事：**把这个名单落到后端的通道**。

## 3. 三个必须先定的判定问题

### 3.1 部分失败时不许判删（最重要）

删除名单来自指纹对比，而指纹来自这一轮的导出。如果这一轮抓取/导出**有失败页**，
那些页上的作品就会「这次没有」，被误判成删除——一次网络抖动就能删掉一批。

**闸门**：只有整轮无失败页时才允许提交删除。sync 侧的 `failed_pages` 已有记账，
发布前判断 `len(failed_pages) == 0`，不满足就跳过删除提交并明确打印「本轮有 N 个失败页，跳过删除」。

### 3.2 跨 source 边界

只删**该 `source`** 的行。后端现有 19.8 万行是 `bangumi`，数据集发布走 `bangumi`；
不能因为数据集里没有某个 id，就去删 `otaku_site` 或其他来源的行。

### 3.3 软删之后对外怎么表现

| 面 | 建议 | 归属 |
| --- | --- | --- |
| 列表 / 搜索 / 标签筛选 / 年份筛选 | 完全过滤 | 后端 |
| 详情 `GET /api/works/{id}` | 返回 **404**（与「不存在」一致）。理由：软删是内部状态，不对外暴露「曾经有过」 | 后端 |
| 收藏 / 历史里的条目 | 显示「已下架」占位，不静默移除（用户会以为自己的收藏丢了） | 客户端 |
| 运营视角 | 软删行仍可查（后续若做恢复入口） | 后端 |

## 4. 契约草案（**待三人确认后才写进 `openapi.yaml`**）

```
POST /internal/import/deletions
```

请求：

```json
{
  "source": "bangumi",
  "batch_id": "del-2026-10-29",
  "items": [
    {"source_id": "265", "reason": "absent_from_snapshot"}
  ]
}
```

- `source` + `items[].source_id` 定位目标行，与 ② 的唯一键一致
- `batch_id` 供重放与排障（与 ② 同名同义）
- `reason` 可选，只入日志，不入库
- 单批上限 **500**（与 ② 一致）

响应：

```json
{"accepted": 12, "already_deleted": 3, "unknown": 1}
```

- **幂等**：已软删的计入 `already_deleted`，不报错——网络中断重发是常态
- **`unknown` 不算错**：库里没有这个 `(source, source_id)`（我们从没导过、或已被清理），
  计数返回便于对账，不整批失败
- 鉴权与 ② 相同（内部端点，Python 同步作业专用）

## 6. 四个坑

### 6.1 复活：软删行仍占唯一键

`(source, source_id)` 上有唯一约束。源站把作品**恢复**（或误删回滚）后，②的 upsert 会撞到这条软删行。
**必须在 upsert 里把 `deleted_at` 置空**，否则表现为「重新导入了却搜不到」，且不报任何错。
这条要和端点一起做，别留到下一期。

### 6.2 一次性删除量可能很大

换库、站点大改版时，单轮 `deleted` 可能是几万条。要按 500 分批 + 间隔，且**打日志汇总**，
避免一次事故删掉半库还看不出来。

### 6.3 不要按标题判删

`deleted` 来自 id 集合差，天然安全。**不要**为了「顺带清理重复」改成按标题匹配——同名不同作品极常见。

### 6.4 首次导出没有上轮快照

首次跑指纹时 `previous` 为空，全部算新增、没有删除。这是对的，不要为了「补齐」而去拉全量比对。
