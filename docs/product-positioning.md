# 产品定位（技术判断的上位依据）

> **本文的地位**：所有技术决策的**上位依据**。契约、接口、数据模型的取舍若与本文冲突，**以本文为准，并回头修契约**。
>
> **为什么要有这份文档**：项目初期产品定位模糊，导致部分技术规则把"我们当时的实现"误当成了"产品定义"。典型三例——
> ① 把来源站写成"数据供给方"（单向供给叙事）；② 把平台自建账号当成产品终态写进铁律；③ 把用户回网站叫"回流"（暗示网站是外部）。
> 这些都是**定位不清导致的技术误判**。本文先立定位，后续技术改正一律以本文为判据。

---

## 1. 一句话定位

面向**尚无客户端**的独立网站：以一次授权接入已建成的通用技术底座，在**显著短于自建或采购的周期内**，上线属于网站自己的客户端。

网站的客户端需求通常来自两方面：**改善既有用户的使用体验**、**扩大可触达的用户规模**。满足该需求有三条路径——自建团队开发、采购外包、接入本平台。接入本平台时，网站侧无需承担客户端开发工作，只需完成授权与站点适配。

我们交付的是**属于它自己的客户端**，**服务它自己的用户**。**这个客户端是网站的客户端，不是平台的客户端。**

平台复用的是技术底座；每个网站仍然是独立的服务对象。Otaku 是首个接入对象，不代表平台只服务 Otaku，也不代表未来所有网站要合并进一个内容产品。

### 1.1 三条路径对比

|  | 自建团队开发 | 采购 / 外包 | **接入本平台** |
| --- | --- | --- | --- |
| 网站侧投入 | 组建或培养客户端团队；需求、设计、开发、测试全流程 | 预算投入 + 需求沟通与验收管理 | **一次授权**（内容授权 + 可选身份授权），**无需开发投入** |
| 上线周期 | 数月 | 数月（沟通、排期与返工） | **最短**：底座已建成并验证，仅需完成站点适配 |
| 后续维护 | 网站自行承担（系统升级、机型适配、商店审核） | 持续付费，或由网站接手 | **由底座统一维护**，一次升级所有接入站受益 |
| 账号与用户体系 | 需另行建设 | 多数方案下仍需另行建设 | **沿用网站既有体系**（已有用户经授权即可使用） |
| 适用场景 | 具备客户端团队，将客户端作为核心产品经营 | 预算充足、需求高度定制 | **希望以最小投入与最短周期获得客户端，而不专门组建团队** |

**差异化不在于价格，而在于上线周期与网站侧投入**：技术底座已经建成并通过验证，
网站需要完成的仅是将底座接入自身站点这一环节——即**授权与配置**。

### 1.2 商业模式与归属边界（一句话说清我们是谁）

**我们建设并运营通用客户端底座；网站授权接入，得到使用自身品牌、服务自身用户的客户端服务。**

| | 归属 / 方式 |
| --- | --- |
| **归属网站** | 品牌、用户、内容、数据 |
| **归属平台** | 底座的研发、运营与升级 |
| **交付方式** | ① **持续服务**（默认）：由我们部署、运营与升级，一次升级所有接入站受益；② **私有化部署**：部署在网站自有环境，我们交付可运行的系统与配套文档，并在架构上**预留由网站自行接管的空间** |
| **私有化的硬边界** | **只交付该网站自己使用的那一个端**。即使额外付费，**也不提供可取代本平台市场地位的能力**（多站接入能力、站点配置能力、底座的平台能力）。理由与"站点配置不给"一致——那是底座的核心价值 |
| **站主运营后台** | **可管理自己网站的用户与数据**；不可管理其他接入站或平台底座；**不提供站点配置能力**（见下） |

**为什么站点配置不开放给站主**：接入与配置新站点属于**底座的核心能力**。若把它开放出去，网站即可自行接入任意站点，**服务本身的价值就不复存在**。
因此：站点接入与配置由平台负责；站主运营后台只覆盖"管理自己"这一层。

**商务口径（周期与报价）**：`[待定]` —— 尚无实际交易先例，机制待定。
文档中一律使用占位符，**不得填写未经负责人确认的数字**（见 §6）。

### 1.3 交付形态：接入一次，形态陆续补齐

网站要的"客户端"可能是 App、小程序、桌面端、Web。**接入只做一次**（授权 + 数据接入 + 站点适配），
新增形态是在同一底座上扩展，**不需要重新接入**。

按边界 5 与 6：**只承诺已实现的形态**。当前已打通的是 Flutter 客户端（Android + 桌面）；
小程序、iOS 原生等属目标形态，可列入路线图，**不写进对客户的承诺**。

## 3. 六条边界（这就是判据）

| # | 边界 | 用作判据时怎么判 |
| --- | --- | --- |
| 1 | **平台服务网站及其用户**，而不是把网站当作单纯的数据供应商 | 任何把网站写成"上游 / 来源 / 供给方"的表述都要改 |
| 2 | **客户端归属网站**：品牌、内容、账号、用户都是网站的，平台只提供底座 | 平台**不得**在客户端里建立与网站平行的长期用户身份；自建账号只能是过渡。**不做"一个 App 选站点"**——每站一个独立客户端，应用名、图标、包名按站独立配置 |
| 3 | 一套底座可服务多个网站，但**各站的内容、用户体系、运营主体保持独立** | 任何"跨站合并 / 账号打通 / 统一用户体系"都是错的 |
| 4 | **只读约束保护的是来源站的数据与业务边界**，不限制用户正常使用客户端或打开来源站 | 只读 ≠ 封锁。**不能拿"只读"当理由拒绝用户回网站、拒绝用户授权** |
| 5 | 客户端的价值是让**尚无客户端**的网站**授权接入即可上线**（周期最短、网站侧零开发投入），而不是宣称已替代网站全部功能 | **不包装**：已实现才当已交付。**尚未适配的按适配需求排期**（A 模式可临时回原页）。**跳转是补位，不能当卖点**；⚠️ **开发期不用当前进度写"不支持 / 不承诺"**——那是开发差不多之后才定的口径 |
| 6 | **区分产品目标与交付形态** | 可以说"支持多端"，但不能凭当前项目承诺原生 App / 离线 / 推送已实现 |

## 4. 身份与用户归属（本次的核心修正）

### 4.1 原则

**网站已经有用户，客户端就该用网站的账号。** 平台账号只是"该网站尚未开放授权端点"时的**过渡方案**，不是产品终态。

**终端用户不是我们的客户，是网站的客户。** 立场与决定权的排序上，**网站观点大于用户观点**——冲突时站点优先（例如：授权同意页做不做、隐私政策怎么写、撤销入口给不给，都由站点决定）。
**这不是用户不重要**：我们服务网站的本质就是服务它的用户（老用户丝滑使用、不锁用户、随时可回原页）；"站点优先"是决定权归谁，不是把用户当次要。

### 4.2 判定依据：看"授权关系"，不看"凭据形态"

| | 判定 |
| --- | --- |
| **禁止** | 平台持有来源站的服务 / 管理员凭据；平台代用户爬取；**平台代收用户密码再转发验证** |
| **允许** | 用户在来源站完成登录，平台只持有**可撤销的用户令牌**（OAuth2 / 一次性票据）。**授权的形态由站点决定**——含站点单方面授权、无用户同意页的形态（密码仍全程只在站点登录页，红线不变） |

区别在于**谁授权、能不能撤销**，而不在于平台手里有没有一串字符串。把两者混为一谈，是当初把"用户授权"也一起封死的根因。
**"授权形态由站点决定"是 §4.1 站点优先原则在技术侧的落点**：首站 Otaku 已定稿采用无同意页的站点单方面授权（2026-10-24，见 identity-auth-endpoint-playbook.md §4.1）。

### 4.3 用户本人的数据可以双向

用户在**本人授权范围**内的收藏与观看状态，可以与来源站保持一致。
这与"向来源站回写**业务数据**"是两回事——前者是用户处置自己的数据，后者是平台改动网站的内容。

### 4.4 过渡期必须留后路

采用平台账号过渡时，必须**提前设计**向来源站身份切换的路径（账号映射、收藏数据迁移），**不能等要切换时才想**。

## 5. 基于定位的技术判断（纠正此前因定位模糊造成的误判）

| 事项 | 初期的判断（错在哪） | 基于定位的判断 | 现状 |
| --- | --- | --- | --- |
| **平台账号** | 当成产品终态写进铁律 2 | **过渡方案**；目标是来源站身份 | 契约已改；实现待站主开放授权端点 |
| **"不回写"** | 一律不回写，连用户自己的收藏也不行 | 区分：作品业务数据不回写；**用户授权下的本人数据可双向** | 契约措辞已区分；实现需站主开放接口 |
| **授权形态** | 用户显式同意（同意页）才算授权 | **授权形态由站点决定**（含无同意页的站点单方面授权）；红线只看密码去向与可撤销性 | 定位已定（§4.2）；契约 §4.8 同步改 |
| **回网站** | 叫"回流"，暗示网站是外部 | 是**同一段体验的延伸**，客户端本来就是网站的 | 术语与文案已改 |
| **网站的角色** | "来源站 / 数据供给方" | **服务对象**，且是客户端的归属方 | 契约与文案已改 |
| **只读** | 被写成"单向供给"的技术链路叙事 | 只读是**保护来源站边界的措施**，不是产品关系 | 铁律 1 已改（2026-10-21） |
| **多站** | 有被合并成一个聚合站的风险 | 各站**独立客户端、独立用户**；复用底座不合并业务 | 契约 §4.6 已体现，本文强化 |
| **客户端品牌 / 包名 / 图标** | 未明确 | 应归属**网站**，不是平台 | **待确认**（见 §6） |
| **封面代理 + 本地缓存** | — | **符合定位**：既保护来源站（限流、不直连），又提升客户端体验 | 维持（有实测证据：无 CORS 头、缓存仅 43 分钟） |
| **只读拉取、网站零改造** | — | **符合定位**：降低接入成本 | 维持；但"零改造"不排斥站主为身份授权做**一次性**开发 |
| **不宣称未实现能力** | — | **符合定位**（边界 5、6）；注意：**"不宣称"≠"承诺不做"**，开发期只记进度 | 维持 |

## 6. 待确认事项（由定位直接推导，尚未决策）

1. **授权端点的形态**：标准 OAuth2 / OIDC，还是站主自研的"一次性登录票据"接口？
   ✅ **已定（2026-10-24，站主回复定稿）**：**标准 OAuth 授权码**（`GET /oauth/authorize` 浏览器重定向 + `POST /api/auth/token` 带 client_secret + `GET /api/me` + `POST /api/auth/revoke` 限管理员会话）。
   三点站点侧决定与本定位一致：**授权形态由站点决定**（无用户同意页、站点单方面授权）、**撤销入口归站点管理员**（终端用户不设自助撤销——§4.1 站点优先）、令牌 1 小时 + scope 固定 identity（收藏读写二期需再次授权）。
   详见 [`identity-auth-endpoint-playbook.md`](identity-auth-endpoint-playbook.md) §2/§4.1。
2. **客户端品牌归属**：应用名、图标、包名是否按接入站分别配置（每个站一个客户端）？按边界 2 与 3，答案应为**是**。
   ✅ **已定（2026-10-24）**：**是，每站一个独立客户端、品牌归网站**；首站四件套（应用名 `Otaku`、`applicationId=com.otaku.app`、图标、商店资料）**阶段 2 前冻结**（包名越晚改越贵）。
3. **身份切换的迁移方案**：平台账号 → 来源站身份时，已有收藏如何映射？
   ✅ **已定（2026-10-24）：做好准备**——现在不切换，但**用户表现在就预留「身份源 + 外部用户 ID」**，将来只做映射、不返工。
4. **收藏双向同步的触发时机**：实时写回，还是登录时批量同步？
   ✅ **已下放（2026-10-24，C5）**：由模块负责人按站点能力自行决定；契约只要求**以服务端最后成功提交为准**、失败不得显示"已同步"。
5. ~~商业模式~~ → **已定（2026-10-24）**：**持续服务为主，同时支持私有化部署**（交付可运行系统 + 预留自行接管的架构空间）。源码买断交付不在此列。
   ⚠️ **私有化硬边界**：**只交付该网站自己使用的那一个端**；即使额外付费，也**不给可取代本平台市场地位的能力**（多站接入、站点配置、底座平台能力）。
6. ~~站主运营后台~~ → **已定（2026-10-24）**：可管理**自己网站**的用户与数据；不可管理其他接入站或平台底座；**不提供站点配置能力**。
   ⚠️ **仍是实现缺口**：当前尚无站主运营后台，需立项（见 §5 技术判断表）。
7. **适配需求的商务口径**：**尚未产生实际交易，周期与报价机制待定**。文档统一用 `[待定]` 占位符，**不得编造数字**。
8. **客户端能力承载清单**：哪些能力 App 原生做、哪些跳网站——需按站点维护一份动态清单，避免"跳转"被当成能力不足的遮羞布。
   ✅ **已有载体（2026-10-24）**：见 [`site-feature-adaptation-plan.md`](site-feature-adaptation-plan.md) **附录 B**（逐项标 原生 / 降级 / 跳转 / 不支持）；**开发期只作自检标尺，不作验收闸门**。
9. **应用商店上架主体与开发者账号归属**：以网站名义还是平台名义上架？决定商店页面显示谁的名字，以及后续迁移成本。
   ✅ **已定（2026-10-24）**：**主体 = 网站**；我们**仅在网站没有自己上架能力时**提供**代理上架**服务。首站现状：应用名 `Otaku`、包名 `com.otaku.app`（已按站点品牌配置）。

## 7. 技术适配：谁决定、怎么推进

> **本节不列任务清单。** 各模块依据本文（定位）自行判断自己要做什么、以及怎么做。

### 7.1 自由度原则

- **模块负责人自己决定即可推进，不需要他人确认**——不需要负责人批准，也不需要其他模块同意。
- 负责人只给**产品与商业层面的要求**（来自定位与商业模式）；**不给实现方案、不指定技术条目、不替模块决定它该做什么**。
- 跨模块接口是**双方共同定义的约定**（两边都要改才能对接），这是技术必需，**不是审批流程**：谁先需要谁提出，对方配合对齐即可。

### 7.2 来自定位的产品要求（只有这些，其余自行判断）

| # | 产品要求 | 来源 |
| --- | --- | --- |
| 1 | 私有化只交付"一个端" → **一个站点要能独立部署、独立运行** | §1.2 A2 |
| 2 | 每站一个独立客户端、品牌归属网站 → **品牌资源要能按站点区分** | §3 边界 2 |
| 3 | 网站已有用户就用网站的账号 → **身份要能支持多个来源** | §4 |

**怎么做、什么时候做、做不做——由各模块负责人自行决定。**

### 7.3 明确不做（红线，由负责人定）

- 不做"一个 App 内选择站点"；
- 不做跨站账号打通或统一用户体系；
- 不向站主开放站点配置与接入新站点的能力；
- **不臆造身份打通**：授权端点未到位前，不自行设计"绕过站点"的打通方式；**首站端点已于 2026-10-24 定稿（标准 OAuth 授权码），按 `identity-linkup-contract.md` 推进即可**。

## 附录 A：站点生命周期与关停预案

> **性质**：定位的展开（2026-10-24 负责人拍板）。定义**归宿形态（三态）、体验门槛（9 成）、能力边界（UGC 托管 / 迁移 / 责任分工）**；实现形态与排期由各模块自行决定（§7.1）。
> **关联**：`site-feature-adaptation-plan.md`（齐平原则 / L1-L2-L3 分级）、`identity-linkup-contract.md`（身份迁移设计）、`how-we-serve-sites.md`（对外口径）、`站点能力差距清单.md`（首站功能池与事实来源）。

### A.0. 一句话

站点有三种归宿：**A 正常接入 / B 全面转入 / C 撤出**。B 模式下客户端接管整站、特色功能**必须原生级（不跳转）**。
**我们的商业价值门槛 = 至少 9 成原生体验**，覆盖 **①账号同步 ②功能同步 ③持续开发与运营能力**——三样缺一即"残缺产品"，不具备商业价值。

### A.1. 三态定义（负责人 2026-10-24 拍板）

| 态 | 触发 | 客户端角色 | 特色功能 | 身份 | 数据 | 出口 |
| --- | --- | --- | --- | --- | --- | --- |
| **A 正常接入** | 站点存续 | 网站的客户端 | 原生做不到的**跳原页补位** | 优先站点身份（OAuth）；平台账号兜底 | 只读快照同步 | 可转 B 或 C |
| **B 全面转入** | 站点关停（**关的是公开网站前端**） | **唯一端，接管整站** | **不许跳转，必须原生齐平** | 平台账号（迁移站点用户；主权归网站） | **主权归网站**；平台代存（可选）/ 站点自备服务器；非冻结 | 长期运营 |
| **C 撤出** | 客户不需要客户端 | 下线 | — | — | 副本按要求删除 | 终止 |

**判据变更**：「跳转＝补位」从"永远可接受"降级为**只在 A 模式可接受**。B 模式是**齐平原则（网站有的我们也要有）的完全态**——把"适配"从"能看"推到"能原生交互"。

> **角色分工（负责人 2026-10-24 定，贯穿三态）**：
> **网站** ＝ 主体 / 品牌 / 用户 / 内容 / 合规责任 / 内容与社区运营；**账号与数据的主权始终归网站**。
> **我们** ＝ 客户端化技术、功能迭代、技术运维、审核**工具**供给、以及**仅在网站没有自己上架能力时**的商店上架**代理**。
> **存储是可选项**：账号 / 数据**主权归网站**，平台**只是代存**（技术服务）；站点也可**自备服务器**；由谁提供服务器，不改变归属。
> **数据迁移** ＝ 我们提供导出 / 导入的**功能与工具**（可靠、幂等、可回滚），**站点执行、我们不代做、不担负担**（实施支持另议）。
> **一直是网站自己运营、自己担责；我们不是内容运营方，不承担内容审核主体责任。**
> **对终端用户不可见**：用户最好不知道平台存在；**我们只面对客户（站点）**。

### A.2. 商业价值门槛：≥9 成原生体验（负责人 2026-10-24 拍板）

三个维度**都要**达标，缺一即商业价值不成立：

| # | 维度 | 9 成体验的含义 |
| --- | --- | --- |
| 1 | **账号同步** | 登录 / 注册 / 改密 / 多端登录 / 收藏与状态跨端一致；站点存续时与站点双向；**关停前站点用户迁到平台账号、收藏历史不丢** |
| 2 | **功能同步** | 站点有的功能客户端都要有，且**原生**——读 / 策展 / 个人内容 / **UGC 全含**，不靠跳转 |
| 3 | **持续开发与运营能力** | 平台能**持续给这个站加功能**（L1/L2/L3 适配机制 + 快速部署 + 单站独立发版）；**客户端侧**的运营（发版、迭代、技术运维、UGC 审核工具供给）由我们做；**内容 / 社区 / 用户 / 合规**运营由网站做、网站担责 |

> **口径（负责人 2026-10-24）**：**9 成考核以"用户端"为主**；站主后台只要求**功能可用**（通用 Web 后台，能用即可），**不追求管理端体验分**。

> **B4 口径（2026-10-24，分维）**：**维度 1、2 是"体验分"，进 [`site-feature-adaptation-plan.md`](site-feature-adaptation-plan.md)（附录 B） 量化（≥90%）；维度 3 是"能力门槛（gate）"，pass / fail，不打分**。B 模式达标 = **账号 + 功能 ≥90% 且 运营能力门槛全过**。理由：运营能力是"具不具备"，用 0.6 分表达没有意义。

> ⚠️ 这三条不是"未来愿景"，是**接单的资格线**。达不到 9 成，就不是"少个功能"，而是**产品不成立**。

### A.3. B 模式原生齐平清单（三档，按能否真做成原生分）

| 档 | 具体功能 | 现状 | 目标 | 路径 / 量级 |
| --- | --- | --- | --- | --- |
| **读 / 策展** | 标签筛选、搜索、新番档期、详情富字段、人物页、公司页、档期分类、资讯 | 部分在合并队列（P1-P4） | 全部原生 | L2 适配 + 现成快照，回源 Bangumi；**可行** |
| **个人内容** | 收藏（阶段 2 已做）、观看历史、个人页 / persona | 收藏已托管；历史/persona 未做 | 全部原生、跨端 | 平台托管本人数据；**增量开发** |
| **UGC / 社交** | 评论 / 点评、社区、投稿 | **明确不做，跳原页补位** | **必须原生，平台托管** | **新能力（L3+）**：存储 + 发布/删除 + 举报 + 审核 + 合规 |

前两档是"补全 + 换数据源"，架构扛得住；**第三档是性质变化**，详见 §A.4。

### A.4. UGC 托管：性质变化与合规（必须说清）

- **现状**：平台只读快照，不碰任何用户生成内容；评论 / 社区 / 投稿一律跳原页。
- **B 模式下的必然结果**：公开前端关了、原页没了，UGC 只能在客户端内完成读写 → **需要由平台代存 UGC**（**主权仍归网站**，也可站点自备服务器），需新建：内容存储、发布 / 删除 / 编辑、举报与处置、审核（先审后发 / 机器 + 人工）、防滥用、数据留存。
- **责任主体 = 网站（负责人 2026-10-24 定）**：**一直是网站自己运营、自己担责**；我们提供**客户端化服务与方案**，主体是网站。UGC 的内容合规责任（实名 / 审核 / 留存 / 处置）由**网站**承担，我们**不是内容运营方、不承担审核主体责任**。
- **我们的角色 = 技术服务方 +（有条件）上架代理**：提供 UGC 托管的**技术能力**（存储 / 发布 / 举报 / **审核工具**，工具供网站使用）、客户端开发与迭代，以及**仅在网站没有自己上架能力时**的商店上架代理。主体、品牌、用户、内容、责任都在网站。
- **定位（负责人 2026-10-24 定）：技术服务 / 存储提供者**——**不主动发布任何内容**；**运营与我们无关**；**对终端用户不可见（用户最好不知道平台存在）**；**我们只面对客户（站点）**。这一条也是合同与叙事的基础。
- **前提**：**资质**——负责人 2026-10-24 明确"资质现在我们也没有，不管"，**当前暂不处理**（合规风险已知，留待后续 / 合同层面再议，`[待定]`）；合同写清"**技术服务 ≠ 内容运营**"的边界。
- **结论**：能力上是底座扩展（存储 + 审核工具），但**责任主体不动**——平台仍是技术底座，不变成内容平台运营方。

#### A.4.1 开发能力假设：允许但不依赖（负责人 2026-10-24 定）

- **我们允许网站后续自行开发**扩展；但**不能假设它有开发能力**——很多网站最终只剩"会用管理后台的运营"人员。
- 因此：**平台必须开箱即用**，ops-only 站点也能运营；**默认形态 = 平台代存 UGC + 站点使用我们提供的「站主管理后台」**维护内容 / 用户 / UGC（**主权归网站**；站点也可自备服务器）。
- **站主管理后台是核心必需能力**（不是可选）：站点没有开发人员时，靠它管理自己的站点。对应 Issue #144（当前缺口，需立项）。
- **后台 = 通用优先、不单独适配（负责人 2026-10-24 定）**：站主后台做成**一套通用 Web 后台**（按 `source` 隔离数据，一套服务所有站）；站点独有管理需求**不做单独适配**，需要时"回网页"（通用 Web 页或站点自有后台）；**后台只要求"能用"，不追求体验**——管理人员的体验不是重点。
- 站点若有开发能力，可在我们机制上扩展（适配 / 接口），但**这不是产品前提**。

### A.5. 关停前迁移 Checklist（B 的入场券，缺一不可）

> **迁移责任线（负责人 2026-10-24 定）**：**账号与数据主权归网站，平台仅代存（可选）、站点可自备服务器**；**迁移能力是我们保留的技术功能**，**执行由网站自己做 / 自己找人**，我们**不代做、不承担迁移负担**（如另提供实施支持，另议 `[待定]`）。**功能 / 媒体的"留 / 加 / 改"，由网站自己决定**（per-site）。运营策略由网站决定；**对用户侧尽量无感**（换源 / 迁移对用户透明、不打断使用）。

1. **身份迁移（站点导出用户）**：站点导出用户表 → 迁到平台账号（映射 / 绑定 / 改密），收藏 / 历史 / persona 一并。我们提供导入能力，**站点执行（可自雇）、不代做**。
2. **资源（媒体 / 图片）**：**原先已存的继续用**（不丢、不乱重下）；**未存的由站点决定"留 / 加 / 改"**（per-site 配置）。当前封面覆盖仅 2.7%（97% 上游档案本就没图），要补按 Issue #124 从 Bangumi 源补。
3. **内容维护（B 模式）**：关的是公开网站前端；**数据主权归网站**，**可存于平台（代存）或站点自备服务器**，两种都由同一套系统 / 站主管理后台维护（他们是运营、不是开发）；A 模式仍从站点同步。不预设"关停即冻结"。
4. **UGC 续存（零体验落差，硬约束）**：历史评论 / 社区内容迁移后**不能有体验落差**——可读、可交互一致、不丢、不改使用方式。**"零落差" = 相对站点原有审核策略**（站点原本先审才先审，**不擅自加审**）。**承载 = 平台代存（可选）/ 站点自备服务器（见 §A.9-8）**，且**必须可续写**——**只读归档不算达标**（不能评论 = 落差）。
5. **原页链接降级**：`source_url` 指向已关停站点时，客户端不渲染外链、改为站内页。
6. **商店与品牌**：应用名 / 图标 / 包名 / **上架主体 = 网站**；**仅当网站无上架能力时**由我们提供上架代理。
