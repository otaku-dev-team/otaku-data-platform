# 产品定位（技术判断的上位依据）

> **本文的地位**：所有技术决策的**上位依据**。契约、接口、数据模型的取舍若与本文冲突，**以本文为准，并回头修契约**。
>
> **为什么要有这份文档**：项目初期产品定位模糊，导致部分技术规则把"我们当时的实现"误当成了"产品定义"。典型三例——
> ① 把来源站写成"数据供给方"（单向供给叙事）；② 把平台自建账号当成产品终态写进铁律；③ 把用户回网站叫"回流"（暗示网站是外部）。
> 这些都是**定位不清导致的技术误判**。本文先立定位，后续技术改正一律以本文为判据。

---

## 1. 一句话定位

面向**尚无客户端**的独立网站：以一次授权接入已建成的通用技术底座，在**显著短于自建或采购的周期内**，上线属于网站自己的客户端。

网站的客户端需求通常来自两方面：**改善既有用户的使用体验**、**扩大可触达的用户规模**。满足该需求有三条路径——自建团队开发、采购外包、接入本平台。接入本平台时，网站侧无需承担客户端开发工作，只需完成授权与站点适配。

我们交付的是**属于它自己的客户端**，**服务它自己的用户**。**这个客户端是网站的客户端，不是平台的客户端。**

平台复用的是技术底座；每个网站仍然是独立的服务对象。Otaku 是首个接入对象，不代表平台只服务 Otaku，也不代表未来所有网站要合并进一个内容产品。

### 1.1 三条路径对比

|  | 自建团队开发 | 采购 / 外包 | **接入本平台** |
| --- | --- | --- | --- |
| 网站侧投入 | 组建或培养客户端团队；需求、设计、开发、测试全流程 | 预算投入 + 需求沟通与验收管理 | **一次授权**（内容授权 + 可选身份授权），**无需开发投入** |
| 上线周期 | 数月 | 数月（沟通、排期与返工） | **最短**：底座已建成并验证，仅需完成站点适配 |
| 后续维护 | 网站自行承担（系统升级、机型适配、商店审核） | 持续付费，或由网站接手 | **由底座统一维护**，一次升级所有接入站受益 |
| 账号与用户体系 | 需另行建设 | 多数方案下仍需另行建设 | **沿用网站既有体系**（已有用户经授权即可使用） |
| 适用场景 | 具备客户端团队，将客户端作为核心产品经营 | 预算充足、需求高度定制 | **希望以最小投入与最短周期获得客户端，而不专门组建团队** |

**差异化不在于价格，而在于上线周期与网站侧投入**：技术底座已经建成并通过验证，
网站需要完成的仅是将底座接入自身站点这一环节——即**授权与配置**。

### 1.2 商业模式与归属边界（一句话说清我们是谁）

**我们建设并运营通用客户端底座；网站授权接入，得到使用自身品牌、服务自身用户的客户端服务。**

| | 归属 / 方式 |
| --- | --- |
| **归属网站** | 品牌、用户、内容、数据 |
| **归属平台** | 底座的研发、运营与升级 |
| **交付方式** | ① **持续服务**（默认）：由我们部署、运营与升级，一次升级所有接入站受益；② **私有化部署**：部署在网站自有环境，我们交付可运行的系统与配套文档，并在架构上**预留由网站自行接管的空间** |
| **私有化的硬边界** | **只交付该网站自己使用的那一个端**。即使额外付费，**也不提供可取代本平台市场地位的能力**（多站接入能力、站点配置能力、底座的平台能力）。理由与"站点配置不给"一致——那是底座的核心价值 |
| **站主运营后台** | **可管理自己网站的用户与数据**；不可管理其他接入站或平台底座；**不提供站点配置能力**（见下） |

**为什么站点配置不开放给站主**：接入与配置新站点属于**底座的核心能力**。若把它开放出去，网站即可自行接入任意站点，**服务本身的价值就不复存在**。
因此：站点接入与配置由平台负责；站主运营后台只覆盖"管理自己"这一层。

**商务口径（周期与报价）**：`[待定]` —— 尚无实际交易先例，机制待定。
文档中一律使用占位符，**不得填写未经负责人确认的数字**（见 §6）。

### 1.3 交付形态：接入一次，形态陆续补齐

网站要的"客户端"可能是 App、小程序、桌面端、Web。**接入只做一次**（授权 + 数据接入 + 站点适配），
新增形态是在同一底座上扩展，**不需要重新接入**。

按边界 5 与 6：**只承诺已实现的形态**。当前已打通的是 Flutter 客户端（Android + 桌面）；
小程序、iOS 原生等属目标形态，可列入路线图，**不写进对客户的承诺**。

## 2. 产品模型

```text
   独立运营的网站                        独立运营的网站
   （网站 A）                            （网站 B）
   自有原站 / 公开作品数据                自有原站 / 公开作品数据
   自有业务规则 / 自有运营体系             自有业务规则 / 自有运营体系
   ★ 自有账号与用户体系                    ★ 自有账号与用户体系
        │                                      │
        │ ① 受控的数据接入（只读作品元数据）      │
        │ ② 身份授权（可选，用户登录在网站侧完成） │
        ▼                                      ▼
┌──────────────────────────────────────────────────────┐
│  通用客户端平台（一套可复用的技术底座）                  │
│  通用能力：浏览 · 检索 · 收藏 · 跨端                    │
│  单站适配：来源 · 导航 · 内容 · 品牌 · 功能差异           │
└──────────────┬───────────────────────┬───────────────┘
               ▼                       ▼
     网站 A 的客户端              网站 B 的客户端
     ★ 品牌是 A 的                 ★ 品牌是 B 的
     ★ 用户是 A 的用户              ★ 用户是 B 的用户
     独立服务 A 站用户              独立服务 B 站用户
        │                              │
        │ 需要网站原生能力（评论 / 投稿 / 社区）时
        ▼                              ▼
     打开 A 站原页                   打开 B 站原页
```

## 3. 六条边界（这就是判据）

| # | 边界 | 用作判据时怎么判 |
| --- | --- | --- |
| 1 | **平台服务网站及其用户**，而不是把网站当作单纯的数据供应商 | 任何把网站写成"上游 / 来源 / 供给方"的表述都要改 |
| 2 | **客户端归属网站**：品牌、内容、账号、用户都是网站的，平台只提供底座 | 平台**不得**在客户端里建立与网站平行的长期用户身份；自建账号只能是过渡。**不做"一个 App 选站点"**——每站一个独立客户端，应用名、图标、包名按站独立配置 |
| 3 | 一套底座可服务多个网站，但**各站的内容、用户体系、运营主体保持独立** | 任何"跨站合并 / 账号打通 / 统一用户体系"都是错的 |
| 4 | **只读约束保护的是来源站的数据与业务边界**，不限制用户正常使用客户端或打开来源站 | 只读 ≠ 封锁。**不能拿"只读"当理由拒绝用户回网站、拒绝用户授权** |
| 5 | 客户端的价值是让**尚无客户端**的网站**授权接入即可上线**（周期最短、网站侧零开发投入），而不是宣称已替代网站全部功能 | 做不到的就写"客户端暂不支持，请回网站"，不包装；未实现的形态不承诺。**跳转是补位，不能当卖点** |
| 6 | **区分产品目标与交付形态** | 可以说"支持多端"，但不能凭当前项目承诺原生 App / 离线 / 推送已实现 |

## 4. 身份与用户归属（本次的核心修正）

### 4.1 原则

**网站已经有用户，客户端就该用网站的账号。** 平台账号只是"该网站尚未开放授权端点"时的**过渡方案**，不是产品终态。

### 4.2 判定依据：看"授权关系"，不看"凭据形态"

| | 判定 |
| --- | --- |
| **禁止** | 平台持有来源站的服务 / 管理员凭据；平台代用户爬取；**平台代收用户密码再转发验证** |
| **允许** | 用户在来源站完成登录与授权，平台只持有**可撤销的用户令牌**（OAuth2 / 一次性票据） |

区别在于**谁授权、能不能撤销**，而不在于平台手里有没有一串字符串。把两者混为一谈，是当初把"用户授权"也一起封死的根因。

### 4.3 用户本人的数据可以双向

用户在**本人授权范围**内的收藏与观看状态，可以与来源站保持一致。
这与"向来源站回写**业务数据**"是两回事——前者是用户处置自己的数据，后者是平台改动网站的内容。

### 4.4 过渡期必须留后路

采用平台账号过渡时，必须**提前设计**向来源站身份切换的路径（账号映射、收藏数据迁移），**不能等要切换时才想**。

## 5. 基于定位的技术判断（纠正此前因定位模糊造成的误判）

| 事项 | 初期的判断（错在哪） | 基于定位的判断 | 现状 |
| --- | --- | --- | --- |
| **平台账号** | 当成产品终态写进铁律 2 | **过渡方案**；目标是来源站身份 | 契约已改；实现待站主开放授权端点 |
| **"不回写"** | 一律不回写，连用户自己的收藏也不行 | 区分：作品业务数据不回写；**用户授权下的本人数据可双向** | 契约措辞已区分；实现需站主开放接口 |
| **回网站** | 叫"回流"，暗示网站是外部 | 是**同一段体验的延伸**，客户端本来就是网站的 | 术语与文案已改 |
| **网站的角色** | "来源站 / 数据供给方" | **服务对象**，且是客户端的归属方 | 契约与文案已改 |
| **只读** | 被写成"单向供给"的技术链路叙事 | 只读是**保护来源站边界的措施**，不是产品关系 | 铁律 1 已改（2026-10-21） |
| **多站** | 有被合并成一个聚合站的风险 | 各站**独立客户端、独立用户**；复用底座不合并业务 | 契约 §4.6 已体现，本文强化 |
| **客户端品牌 / 包名 / 图标** | 未明确 | 应归属**网站**，不是平台 | **待确认**（见 §6） |
| **封面代理 + 本地缓存** | — | **符合定位**：既保护来源站（限流、不直连），又提升客户端体验 | 维持（有实测证据：无 CORS 头、缓存仅 43 分钟） |
| **只读拉取、网站零改造** | — | **符合定位**：降低接入成本 | 维持；但"零改造"不排斥站主为身份授权做**一次性**开发 |
| **不承诺未实现能力** | — | **符合定位**（边界 5、6） | 维持 |

## 6. 待确认事项（由定位直接推导，尚未决策）

1. **授权端点的形态**：标准 OAuth2 / OIDC，还是站主自研的"一次性登录票据"接口？
   ✅ **已定（2026-10-24）**：**一次性票据起步**（实现成本低），须满足"密码不经平台、令牌可撤销"。
   **站主后续会提供，当前没有 → 先做好准备**：接口契约与适配层先就位，**不提前实现**。
2. **客户端品牌归属**：应用名、图标、包名是否按接入站分别配置（每个站一个客户端）？按边界 2 与 3，答案应为**是**。
3. **身份切换的迁移方案**：平台账号 → 来源站身份时，已有收藏如何映射？
   ✅ **已定（2026-10-24）：做好准备**——现在不切换，但**用户表现在就预留「身份源 + 外部用户 ID」**，将来只做映射、不返工。
4. **收藏双向同步的触发时机**：实时写回，还是登录时批量同步？
5. ~~商业模式~~ → **已定（2026-10-24）**：**持续服务为主，同时支持私有化部署**（交付可运行系统 + 预留自行接管的架构空间）。源码买断交付不在此列。
   ⚠️ **私有化硬边界**：**只交付该网站自己使用的那一个端**；即使额外付费，也**不给可取代本平台市场地位的能力**（多站接入、站点配置、底座平台能力）。
6. ~~站主运营后台~~ → **已定（2026-10-24）**：可管理**自己网站**的用户与数据；不可管理其他接入站或平台底座；**不提供站点配置能力**。
   ⚠️ **仍是实现缺口**：当前尚无站主运营后台，需立项（见 §5 技术判断表）。
7. **适配需求的商务口径**：**尚未产生实际交易，周期与报价机制待定**。文档统一用 `[待定]` 占位符，**不得编造数字**。
8. **客户端能力承载清单**：哪些能力 App 原生做、哪些跳网站——需按站点维护一份动态清单，避免"跳转"被当成能力不足的遮羞布。
9. **应用商店上架主体与开发者账号归属**：以网站名义还是平台名义上架？决定商店页面显示谁的名字，以及后续迁移成本。
   首站现状：应用名 `Otaku`、包名 `com.otaku.app`（已按站点品牌配置），但**上架主体归属未定**。

## 7. 技术适配大方向（只定方向，实现由各模块自定）

> 定位确立后，技术上要往哪走。**本节只给方向与边界，不规定实现方式**——
> 各模块（Flutter / Java / Python）内部的设计、技术选型与实现顺序，由各自负责人自行决定。

### 7.1 跨模块方向

| # | 方向 | 为什么 | 主要落在 |
| --- | --- | --- | --- |
| 1 | **身份支持双来源**：来源站身份优先，平台账号过渡 | 网站已有用户，就该用网站的账号 | 后端为主，客户端配合 |
| 2 | **用户表预留「身份源 + 外部用户 ID」** | 现在不改，将来切换就要返工（成本最低的先行动作） | 后端 |
| 3 | **授权接入的适配层先就位**（一次性票据起步） | 站主后续会提供，接口一到即可接入，不返工 | 后端 + 客户端 |
| 4 | **客户端品牌资源按站配置化**（应用名 / 图标 / 包名） | 每站一个独立客户端，不做"一个 App 选站点" | 客户端 + 构建配置 |
| 5 | **单站可独立部署** | 私有化只交付"他自己用的端"，必须能单独跑一套 | 后端架构 + 部署 |
| 6 | **能力承载清单按站维护**（原生 vs 跳网站） | 避免"跳转"被当成能力不足 | 客户端 + 文档 |

### 7.2 各模块的自主范围（负责人自定，不干预）

- **backend-java（@pyxz0）**：用户表与会话如何支持双身份源、授权适配层如何实现、单站部署如何切分——自行决定。
- **app-client（@riceyu02）**：品牌资源如何配置化、登录流程如何同时支持两条路、承载清单如何在界面上体现——自行决定。
- **sync-python**：数据接入按现有契约执行；身份与授权不在其职责内。

### 7.3 明确不做（避免走偏）

- 不做"一个 App 内选择站点"；
- 不做跨站账号打通或统一用户体系；
- 不向站主开放站点配置与接入新站点的能力；
- **不在授权端点到位前强行实现身份打通**——做好准备即可（契约 §4.8 已就位）。
