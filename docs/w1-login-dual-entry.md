## 0. 结论先行

登录页从「一个表单」变成「**一个主按钮 + 一个折叠表单**」：

1. **主入口「用 Otaku 账号登录」**——走系统浏览器授权，回来即登录。这是目标形态（#150：平台账号只是过渡/兜底）。
2. **次级入口「平台账号登录」**——现有的用户名密码表单，收在「使用其他方式登录」里，视觉上退到次要位置。

配套三件：账号菜单显示**身份来源**、401 时**静默重走一次授权**、桌面端这一轮**不显示**站点入口（loopback 没定，不给不能用的按钮）。

一句话理由：两个入口**不是对等关系**。做成两个一样大的按钮，用户每次登录都要先判断「我是哪种人」——而这个判断本该由产品形态替他做掉。

## 2. 形态方案

### 2.1 主次关系与文案

| 元素 | 文案 | 位置 |
|---|---|---|
| 主按钮 | 「用 Otaku 账号登录」 | 表单上方，`FilledButton`，整行宽 |
| 次级入口 | 「使用平台账号登录」 | 主按钮下方，`TextButton`，点开才显示账号密码表单 |
| 说明行 | 「Otaku 账号登录会打开网站授权页，密码只在网站输入」 | 主按钮下方，`bodySmall` |

**为什么平台账号要收起来**：#150 已拍板「平台账号仅过渡/兜底，目标=来源站身份」。登录页是用户对产品身份认知的第一现场，把过渡形态摆在和主形态同等的位置，等于每天提醒用户「我们还没做完」。收起来不是藏功能——老用户（已有平台账号）点一次就记住位置，新用户根本不该被它干扰。

**为什么必须写「密码只在网站输入」**：这是授权流程相对表单登录唯一需要用户理解的新事实。不写，用户会以为 App 偷了他的密码；写了，这一句同时是安全承诺。

### 2.2 授权链路（按契约 §2，客户端只做第 1、3、5 步）

```
用户点主按钮
  → 客户端生成随机 state，落 LocalPrefs，打开系统浏览器
      GET /oauth/authorize?client_id=otaku-app-client
          &redirect_uri=com.otaku.app:/oauth2redirect&state=<随机>
  → 站点：未登录先 303 跳自己的登录页（无同意页）；已登录直接回跳
      com.otaku.app:/oauth2redirect?ticket=<一次性120s>&state=<原样>
  → 客户端：scheme 回跳 → 校验 state 一致 → POST /api/auth/site-login {ticket}
  → 平台后端：带 secret 换站点令牌 → 建平台会话 → 返回 {token, user}
  → 客户端：与现有 login 完全同构地进入 signedIn
```

**用系统浏览器，不用 App 内 WebView**：RFC 8252 对原生应用的推荐；用户能从地址栏确认域名（防钓鱼），App 侧全程不接触站点登录页。这一条没有商量余地——WebView 方案看起来「体验更连续」，实际是把两个系统的安全边界都拆了。

**state 必须落盘，不能只存内存**：Android 上从系统浏览器回到 App，进程完全可能已经被回收（内存压力、用户中途切走）。state 只存内存 → 回来时对不上 → 用户看到「校验失败」而实际什么都没错。存 `LocalPrefs`，校验通过或明确失败后立即删掉。

### 2.3 错误分支（每条单独文案，不合并成「登录失败」）

| 情况 | 用户看到 | 客户端动作 |
|---|---|---|
| state 与本地存的不一致 | 「登录状态校验失败，请重新登录」 | 删 state；不自动重试（可能是别的东西在调这个 scheme） |
| ticket 过期（120s） | 「授权已过期，请重新授权」 | 清 state，允许再点一次主按钮 |
| ticket 已被用过（一次性） | 同上 | 同上 |
| 平台返回 401（secret 错 / ticket 无效） | 「授权失败，请重试」 | **不静默重试**——重走一遍授权也还是这个结果 |
| 打不开授权页（站点不可达） | 「打不开授权页面，请检查网络」 | 停留在登录页 |
| 用户中途返回浏览器首页 | 无感 | 删 state，留在登录页等下一步 |

「过期」和「失败」分开：前者让用户知道**再点一次就行**，后者是**出问题了**。合成一句，用户会在过期时反复重试同一个坏 ticket。

### 2.4 401 兜底与静默续期（契约 §5）

- **401 静默重走一次**：仅对**站点身份**账号生效；只重试一次；重试期间界面显示「正在恢复登录…」，成功后无感，失败才清会话并提示重新登录。
  - 为什么只对站点身份生效：平台账号的 401 就是密码/会话问题，重走授权解决不了，只会让用户多等一轮。
- **临期续期（< 5 分钟）**：契约说 authorize 对已登录用户幂等、静默重走即可。客户端**这一轮不做主动续期**——平台会话有效期若与站点令牌脱钩，客户端预判「临期」反而会提前把用户赶去浏览器。等契约明确平台会话与站点令牌的寿命关系再做（见 §6 第 3 条）。

### 2.5 账号菜单：身份来源 + 断开连接

| 状态 | 菜单显示 |
|---|---|
| 站点身份账号 | 昵称 + 一行小字「Otaku 账号」；菜单项「退出登录」 |
| 平台账号 | 昵称（现状不变） |
| （待后端端点） | 「断开与 Otaku 账号的连接」——本地解绑 + 平台代理 self-revoke |

「退出登录」对站点身份账号补一句说明：**退出只解绑平台侧，网站侧令牌仍有效到过期**。这是三态里的第①条，用户有权知道退出不等于「网站那边也退了」。

「断开与网站的连接」（三态第②条）**这一轮做不了**——契约 §5 写的是「持当前 Bearer 调站点 `POST /api/auth/revoke`」，但客户端按契约根本不持有站点令牌（secret 与令牌交换都在平台后端）。要么平台补一个代理端点，要么这一条延期，见 §6 第 1 条。

### 2.6 桌面端这一轮不显示站点入口

契约里桌面 loopback（`http://127.0.0.1:<port>/callback`）还是唯一遗留项，且桌面授权需要 App 内起本地 HTTP 服务器接回调——工作量与风险都不小，而桌面端用户目前都可以用平台账号登录。

所以：桌面端登录页**只显示平台账号表单**，站点入口整体隐藏（不是置灰）。隐藏而不是禁用，理由同 W1.3a 的桌面通知：**不给点了没反应的按钮**。等 loopback 端口补报、桌面链路就绪再放出来。

端口由客户端先定下来报备（清掉这条遗留项）：**`http://127.0.0.1:38711/callback`**。选它的理由：避开常见代理与服务端口（8888/7890/1080/52189/8080），四万段被占用的概率低；一旦站点加白名单就不会再改。

### 2.7 Mock 模式要能走通

`AppConfig.useMock` 默认 `true`，桌面走查与 widget 测试都跑在 Mock 上。授权链路必须**在 Mock 下可完整走通**，否则这条功能在联调前等于没法看：

- `SiteAuthLauncher` 的 Mock 实现不真的开浏览器，直接返回一个假 ticket；
- `AuthDataSource.siteLogin()` 的 Mock 返回一个站点身份的 `AccountUser`（`username` 取站点昵称）；
- 深链回跳用测试替身注入，不需要真浏览器。

## 3. 客户端改造点（照现有分层，不发明新结构）

| 层 | 新增 / 改动 | 说明 |
|---|---|---|
| `features/auth/site_auth_launcher.dart` | 新增：接口 + Android 实现 + Mock | `openAuthorize(state)` 打开系统浏览器；`Stream<String> redirects` 收 scheme 回跳。深链接收候选 `app_links` 插件或手写 MethodChannel，实现期定 |
| `features/auth/site_auth_state.dart` | 新增：state 生成 / 校验 / 清理 | 纯函数部分（`generateState` / `matches`）单测；存储走 `LocalPrefs`，键 `site_auth_state`，用完即删 |
| `data/datasources/auth_data_source.dart` | 加 `siteLogin(ticket)` | 接口 + 真实现（`POST /api/auth/site-login`）+ Mock 三份，照现有范式 |
| `features/auth/auth_controller.dart` | 加 `siteLogin()` 流程 | 复用 `submitting` / `error`；401 静默重走一次的逻辑挂在这里，不散到网络层 |
| `features/auth/login_page.dart` | 双入口呈现 | 主按钮 + 折叠表单；桌面端隐藏站点入口（`PlatformInfo.isDesktop`） |
| `shared/widgets/account_menu.dart` | 身份来源小字 | 依赖 `AccountUser` 带身份来源字段（§6 第 2 条） |
| `AndroidManifest.xml` | 加 scheme intent-filter | `com.otaku.app:/oauth2redirect`，与站点白名单一致 |

**深链接收选型**（实现期定，先说清权衡）：`app_links` 插件成熟、双端一致、社区维护；手写 MethodChannel 少一个依赖但要自己处理 Android 的 `onNewIntent` 与进程重启两种入口。倾向 `app_links`——这条链路的坑（进程被回收后回跳）比一个依赖更值得花钱。

## 5. 需要确认的点（给 #147 的输入）

1. **「断开与网站的连接」缺一个平台端点**。契约 §5 的三态②要求 self-revoke，但客户端不持站点令牌——这个调用只能由平台后端代理（建议 `POST /api/auth/site-unlink`，平台侧据此调站点 revoke 并清映射）。没有它，三态②这一轮做不了，登录页与账号菜单只能交付①。
2. **平台 `user` 响应需要带 `identity_source`**（NULL = 平台账号）。否则账号菜单无法显示身份来源，客户端也无从区分「该不该静默重走授权」。这是 `AccountUser` 要加的字段，属账号结构变更，一并走三人确认。
3. **平台会话与站点令牌的寿命关系**。契约说站点无 refresh_token、authorize 幂等可静默续；但客户端持的是**平台**令牌。若两者寿命脱钩（平台 30 天、站点 1 小时），「临期静默重走」在客户端侧根本无从判断——需要明确「平台会话是否随站点令牌失效而失效」。在此之前，客户端只做 401 被动重走，不主动续期。
4. **桌面 loopback 端口**：客户端定 `http://127.0.0.1:38711/callback`，请站点补白名单（这一轮桌面不做入口，先报备）。
5. **ticket 120 秒够不够**。系统浏览器冷启动 + 站点登录 + 回跳，慢一点就可能超。客户端按 120 秒设计、不假设更宽；若站主愿意放宽到 300 秒，超时投诉会少一批。

## 6. 不做什么（防方案膨胀）

- **不做收藏迁移**：本期 scope 固定 `identity`，收藏读写是二期 C4。
- **不做「已有平台账号再绑定站点」的登录页形态**：契约 §6 步 5 提到这个验收场景，但本期映射规则是「授权即建号」。若确认要做，入口应放账号菜单（「绑定 Otaku 账号」）而不是登录页——登录页放三个入口就更没人知道该点哪个了。
- **不做站点资料回显**：`nickname` / `avatar_url` 仅客户端展示，不回写平台、不再分发（契约 §7）。
- **不做多站绑定**：首站 1:1，N:M 是未来目标。
- **不做 iOS**：本仓库没有 iOS 端。
- **不做桌面授权入口**：这一轮隐藏，loopback 就绪再说。
- **不自己持有任何站点凭据**：secret、站点令牌都不进 App——这是整套方案的前提，不是可选项。

## 7. 与三条铁律的关系

| 铁律 | 本文如何守 |
|---|---|
| 1 来源站只读 | 客户端只打开授权页与接收回跳；所有数据访问仍走平台 `/api/**`，不新增任何直连来源站的调用 |
| 2 来源站用户数据不进平台 | 平台只存 `external_user_id` 映射与令牌哈希；昵称/头像仅展示不回写 |
| 3 抓不到 ≠ 已删除 | 授权链路失败一律显式报错，不静默降级成「已登录」或「未登录」的猜测 |
