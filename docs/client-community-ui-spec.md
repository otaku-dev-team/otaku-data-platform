# 客户端社区 UI 实现规格（大方向，非约束）

> 配套 issue：**#240**（社区/UGC 平台代存 day-one）。本文只定**结构与必须尊重的后端契约行为**，
> 不规定布局、组件拆分、动效、分页交互、空态/错误态文案——这些留给实现者（riceyu02，#95）按手感定。
> 权威契约见 `client-dev-handoff.md` §9，线上真响应样张见 `docs/samples/ugc-samples.json`（照样张写解析比照 YAML 猜快）。

## 1. 范围与边界

- **做什么**：作品详情页内，让用户能评论 / 点评 / 互动，体验优于单纯跳原页。
- **不做什么**：不碰后端（已上线 V18–V24，十项闭环）；不做内容运营（审核/合规责任在网站）；
  不混入来源站数据（只读红线的边界不变）。
- **开关语义**：社区是**可选增值**，由站主在后台启用；未启用时客户端整块不渲染、跳来源站原页补位。

## 2. 结构方向（建议，非强制）

作品详情页底部两个 tab，互不转换：

| Tab | 语义 | 后端表 |
|---|---|---|
| 评论 | 讨论流，可多条、可一层回复 | `ugc_comment` |
| 点评 | 对作品的评价，一人一条，可打分 | `ugc_review` |

**入口闸**（进页面先查一次）：`GET /api/site/features`
- `ugc_enabled = false` → 两个 tab 整块不渲染，跳来源站原页，不要画空评论区。
- `ugc_moderation = "pre"` → 发帖/编辑后落 `pending`，输入框附近宜有「审核后显示」提示（文案自定）。

## 3. 必须尊重的后端契约行为

这些不是「设计偏好」，是后端已上线的硬行为，违背会被当成 bug：

**评论**
- 列表 `total` **只算顶层**；每条带 `reply_count`（回复总数）与 `replies`（最早 3 条预览，对话顺序）。
  `reply_count > 3` 再调 `.../comments/{id}/replies` 取完整回复（分页、最早在前）。
- 回复只支持**一层**：`parent_id` 指向回复会 `400`。
- 编辑响应里顶层评论的 `replies` 是**空数组**——只替换那一条本身，别把整条覆盖成「零回复」。
- 删顶层评论**连带隐藏该楼层的回复**（楼层撤回语义，行保留，站主导出仍可见）。
- 已注销账号的 `author` 显示「已注销用户」，不要用它做用户跳转。

**点评**
- 概览三个数口径不同：`total`（含只写文字不打分的）/ `rated`（打了分的）/ `average`（只对打了分的求均值，**可为 null**）。
  无打分时显示「暂无评分」，**不要显示 0**；`distribution` 只含有数据的分数，不补 0。
- 与作品自带的 `main_rating`（来源站聚合分）是**两套口径**，并列展示、各自标注来源，不相加/平均/覆盖。

**错误码**（详见 §9.5）
- `400 CONTENT_REJECTED`：机器审核不通过、**未落库**，提示「修改后再发」并带 `message` 理由，改完可直接重发。
- `403`：只能操作自己的内容 / 本站未开启社区。
- `404`：内容已删或不存在，刷新列表。
- `409 REVIEW_EXISTS`：重复发点评，引导去**编辑原点评**，不要弹「失败」。
- `429 RATE_LIMITED`：按 `Retry-After` 提示「发言太快」。

## 4. 留白（由实现者定，本文不限制）

- tab 的具体视觉布局、列表项卡片样式、头像/昵称来源；
- 回复的展开/收起手势、分页或无限滚动；
- 发帖/编辑的输入框形态（弹层、内联、全屏）；
- 空态、加载态、错误态的文案与插画；
- 举报的触发入口与理由选择器；
- 与作品页其余区块（封面、简介、资讯）的衔接位置。

## 5. 验收锚点

- 站主后台关掉社区开关时，客户端看不到任何评论/点评入口、不请求相关接口；
- 对着 `docs/samples/ugc-samples.json` 的 7 份真响应把解析跑通（尤其「字段在哪一层」）；
- 先审后发站点下，发帖后该条 `status = pending` 且公开列表不出现；
- 机器审核 `CONTENT_REJECTED` 时内容不入库、可改完重发。
