## 0. 为什么是这一条

总目标 G1 是「客户端体验优于来源站原生页」。客户端已具备双端真实浏览、账号跨端同步与来源站回流的地基，**剩下的差距全在体验层**：原生手感、离线可用、主动触达，以及把后端已有的发现能力（排序、相关推荐）真正露出来。

W1 是六条工作流里**唯一一条完全在客户端内闭环、不依赖服务器资源**的，因此不受 Issue #78 阻塞。

## 2. W1.1 · 原生体验打磨

**目标**：把现有「能联调」的双端，打磨成「产品可用」的双端。

**范围（负责人视角，具体实现由主责人定）**

- 桌面 / Android 交互对齐：以 **PR #62 桌面差异清单** 为收口基准，清零未决差异。
- 列表分页体验：无限滚动 或 分页按钮，保证翻页稳定（契约 §6.4 已保证分页稳定）。
- 四类边界状态打磨一致：空结果 / 缺封面 / 无简介 / 请求失败——契约 §6.3 已定义占位规则，本轨道补齐统一 UI 反馈。
- 刷新 / 重试交互（如下拉刷新）。
- 评分尺度（`0-10`）的展示。

**验收口径**

- A1 桌面与 Android 在列表 / 详情 / 回流入口行为一致，以 PR #62 清单为收口基准，**0 个未决差异**。
- A2 四类边界状态（空结果 / 缺图 / 无简介 / 请求失败）均有明确 UI 反馈，无裸异常 / 空白页。
- A3 回流入口（PR #75）在本轨道不被退化。

## 3. W1.2 · 离线可用

**目标**：已浏览过的列表与详情在无网 / 弱网时仍可查看，降低对后端实时依赖（呼应铁律 3）。

**设计约束（负责人视角）**

- 仅缓存「平台（Java）已返回」的响应；**绝不直接连来源站**。
- **快照语义**：本地有缓存但请求失败 → 展示缓存并提示「离线 / 上次更新时间」，**绝不**把失败推断为「作品已删除」。
- 个人数据（收藏 / 状态）离线只读展示；写操作联网后重试或明确禁止离线写（由主责人定）。
- 缓存范围建议：最近浏览的 N 页列表 + 打开过的详情；封面已由 `cached_network_image` 的 HTTP 缓存覆盖，不必重复缓存。
- 本地存储选型自主决定（`shared_preferences` 已在依赖中但暂未用于数据，或引入 `drift` / `sqflite` / `hive`）。可参考现有 `TokenStore` 的「接口 + 实现 + 内存包装」分层范式。

**验收口径**

- B1 正常联网浏览列表 / 详情后断网，重开 App 仍能查看已浏览内容。
- B2 断网时打开**未缓存**内容 → 明确「离线不可访问」提示，不崩溃。
- B3 后端不可达（非删除）时，已缓存作品照常展示，并标注「数据可能为上次同步」。
- B4 联网恢复后，列表 / 详情静默刷新为最新；缓存与服务端冲突时以服务端为准。
- B5 全程不引入任何来源站直连。

## 4. W1.4 · 发现体验接入

**目标**：把后端已具备的发现能力（排序、同题材推荐）接进客户端界面。

**范围**

- 列表 `sort` 选择器：`id` / `rating` / `year`，默认 `id`，非法取值走默认不崩。
- 详情页 `/related` 同题材推荐区：`basis_tags`（实际参与匹配的标签）+ `items`（7 字段 `WorkSummary`）；无标签作品不显示该区；请求失败时该区不渲染，详情正文不受影响。
- 与 W2（跨源视图）的呈现衔接：跨源同名作品在列表与推荐位如何可辨识。

**验收口径**

- C1 列表可选 `sort`；切换后顺序正确，翻页带同一参数（否则第 2 页与第 1 页接不上）。
- C2 详情页渲染 `/related`（`basis_tags` + `items`）；无标签作品不渲染推荐区；推荐失败不影响详情。
- C3 排序与推荐在桌面与 Android 行为一致。

> PR #90 已在进行中；本轨道在其基础上收口跨端一致性与真机视觉验证即可。

## 5. W1.5 · 呈现层的数据适配

**目标**：在数据覆盖不完整（真实情况）的前提下，呈现仍可用。

**范围**

- 封面缺失（bangumi 97% 无封面，实测见 [`data-quality-report.md`](data-quality-report.md)）时的占位策略与视觉一致性。
- 评分覆盖不足（bangumi 仅 34.4%）时排序的可解释性——避免用户点「按评分」后看到大量无分条目而困惑。
- 跨源同名作品（13,261 组）的可辨识性：至少不让用户把两条不同记录误认为同一部。

**验收口径**

- D1 封面缺失的作品有稳定占位，不出现裂图或布局塌陷。
- D2 评分缺失条目在排序结果中的位置有可解释表现（沉底或明确标注），不造成误读。
- D3 跨源同名作品在列表中可被区分（标题相同但来源不同）。

**D2 的落地口径（2026-10-22）**

排序本身不用改：服务端 `rating_value DESC`，无评分条目自然沉到末尾。要补的是**解释**——
末尾那一片卡片没有评分徽标，看着和「加载失败」一样。因此客户端做两件事：

1. 按评分排序且结果里确实有无评分条目时，列表顶部加一行说明「没有评分的作品排在最后」；
   结果全都有分时不显示（那时候这一行是废话，还白占一屏高度）。
2. 无评分条目在卡片/列表行上标出「暂无评分」四个字，**只在按评分排序时标**。
   契约 6.3 的「`null` 不显示 `0.0`」继续成立：标的是「没有分」，不是零分。

D3 仍被契约卡住：`WorkSummary` 不含 `source`，跨源同名在列表层无法区分，
改契约属于跨模块变更（红线），需要先和 W2 / W3 对齐。

## 6. W1.3 · 通知触达（需后端协同，延后）

**目标**：平台侧事件（新批次导入完成 / 追更提醒等）主动通知用户。

**为什么延后**

- 必须新增后端设备令牌注册端点 + 接入推送服务商（FCM / APNs），属**跨模块接口变更**，需三人确认并写入契约。
- 依赖「有运行中的后端」；开发可在本地后端联调，正式可用需部署（与 W6 休眠不冲突，属独立事项）。
- 「追更」依赖后端暂无的订阅 / 关注机制，范围大于「导入完成通知」，故先只做后者。

**跨模块依赖（供三人确认）**

- 新增端点：`POST /api/devices`（或在 `/api/me` 下注册 push token），鉴权复用 Bearer。
- 后端引入推送服务商 SDK 与密钥管理（@pyxz0 负责）。

**验收口径（目标值，待后端接口定型后冻结）**

- E1 客户端能采集并在登录后注册设备令牌。
- E2 触发事件时用户收到系统通知。
- E3 点击通知正确跳转到对应内容。
- E4 登出 / 换设备时令牌失效或解绑。

## 7. 交付与自验

- **自评 + 证据**：每条轨道交付时附证据（测试、真机录屏、before/after 截图或指标）。

- **进度自维护**：本工作流的进展由主责人在 [`ROADMAP.md`](ROADMAP.md) 对应节自行更新，不需向负责人逐条汇报。
- **不在范围**：账号体系重做、收藏模型重构、多来源站接入、服务器部署。
