# 阿宅画像：`PersonaProfile` → `PersonaInsight` 的映射方案（#375）

> 2026-11-07 · 针对 #401（`GET /api/me/profile`，已上线）与 #375（画像页，UI 壳见 #427）
>
> **状态（2026-11-08）**：已按本文推荐值落地——#487 接上真数据、#522 修了提示文案。
> §7 的三个点按推荐值定稿；如有异议，只改 `PersonaInsightMapper` 一个文件，
> 页面与数据源都不用动。
>
> **一句话结论**：mock 设想的六个轴里，**只有 1 个能用现有契约算出来**，2 个要给后端加字段，
> 3 个基本无解。现在直接接真数据，雷达图会有 3–5 根轴是编的。本文给出两条可行路线与取舍。

## 1. 两头对照

### 后端给什么（`PersonaProfile`，`docs/openapi.yaml`）

| 字段 | 形状 | 说明 |
|---|---|---|
| `type_weights` | `{anime, comic, game, novel} → -1..1` | 按维度各自归一化，最强恒为 ±1，负值 = 看得少 / 打低分 |
| `tag_weights` | `{标签 → -1..1}` | 负值来自低分作品，是「不喜欢」的证据 |
| `rating_tendency` | `{mean(1–10, nullable), count, dist[10]}` | 只有打过分的点评计入 |
| `recent_active` | `string[]` ≤20 | 最近 30 天有行为的 **work_id**，按时间倒序；**不带年份/类型** |
| `sample_size` | `int` | 参与聚合的行为行数（浏览 + 收藏 + 点评），**不拆分来源** |
| `generated_at` | `date-time` | — |

> 后端内部其实读了 `collection.status`（`want`/`watching`/`watched`）和 `ugc_review.rating`
> （见 `PersonaService.collectionWeight()` / `reviewWeight()`），但**只用来加权，没有把分布输出**。

### 客户端要什么（`PersonaInsight`，`persona_view_data.dart`）

| 字段 | 现状 |
|---|---|
| `title` 称号 | mock 给「深夜考据派」，无来源 |
| `review` 锐评 | mock 给三句话；注释写「服务端生成（首站是 LLM 链路）」，客户端不能调 LLM |
| `dimensions` 六维 | mock 给 深度 / 热度 / 广度 / 忠诚度 / 尝鲜 / 社交，每项 0..1 + 一句 caption |
| `topTags` | ✅ 可直接取 `tag_weights` 正向前 N |
| `tone` / `boundAccount` | 契约没有 → 保持 `null`，UI 显示「未设置」/「未绑定」（与 #427 一致） |

## 2. 六个轴逐个判定

| 轴 | mock 的 caption | 需要什么 | 现有契约 | 判定 |
|---|---|---|---|---|
| **深度** | 设定与考据 | 标签的语义分类（哪些算「考据」） | 只有权重，没有标签分类 | ❌ 只能用「口味浓度」近似，不是同一件事 |
| **热度** | 主流话题 | 全站榜单 / 热度基准 | **完全没有** | ❌ 无解 |
| **广度** | 题材跨度 | `tag_weights` 的非零条目数 | ✅ 有 | ✅ **现在就能算** |
| **忠诚度** | 追完率 | `collection` 状态分布（watched / want / watching） | 后端有、**未输出** | ⚠️ 加 1 个字段即可 |
| **尝鲜** | 新番占比 | `recent_active` 作品的年份/首播 | 只给 work_id | ⚠️ 要改字段形状（需 join 作品表） |
| **社交** | 讨论参与 | 点评 / 回复条数（与浏览分开） | `sample_size` 混算 | ⚠️ 加 1 个字段即可 |

统计：**能算 1 / 加字段能做 2 / 无解 1 / 只能近似 1 / 需改形状 1**。

## 3. 三条路线

### 路线 A：换成「现有数据一定能算」的六轴（推荐，零后端改动）

把轴名改成诚实的、每个都能追溯到某个字段的说法：

| 新轴 | 公式（全部 0..1） | 数据来源 |
|---|---|---|
| **类型集中度** | `max(type_w) / Σ\|type_w\|`；`Σ = 0` 时取 0 | `type_weights` |
| **题材广度** | `min(1, 非零 tag 数 / 12)`（阈值 0.15） | `tag_weights` |
| **口味浓度** | `1 − H(tag 正权重) / log(n)`；`n ≤ 1` 时取 1 | `tag_weights` |
| **评分态度** | `\|mean − 5.5\| / 4.5`；`mean = null` 时整轴跳过 | `rating_tendency.mean` |
| **活跃度** | `min(1, log(1 + sample_size) / log(1 + 300))` | `sample_size` |
| **近期活跃** | `recent_active.length / 20` | `recent_active` |

三个边界必须显式处理，否则会出现 `NaN` 画到雷达图上（Flutter 的 `Canvas` 拿到 NaN 会静默不画，
看起来像「这个轴没数据」，很难查）：**`Σ|type_w| = 0`**、**非零 tag 数 ≤ 1**、**`mean = null`**。
后两种情况下对应轴直接不进 `dimensions` 列表——少一根轴，比画一根假轴好。

优点：**一根假轴都没有**，每个数字都能说出怎么来的。
代价：和 mock 的产品语义（深度/热度/忠诚度/社交）不一样，等于承认「那些维度我们测不了」。

### 路线 B：后端补 3 个字段，做 5 个真轴

补：

```yaml
collection_status: { want: int, watching: int, watched: int }   # → 忠诚度
review_count: int                                              # → 社交（表达欲）
recent_active: [{ work_id, year, type }]                       # → 尝鲜（改形状）
```

补完能做：广度 ✅、忠诚度 ✅、社交 ✅、尝鲜 ✅、深度（仍只能近似）、**热度仍然无解**。

代价：`PersonaProfile` 已上线并发版，改形状要 pyxz0 排期 + 客户端同步改。

### 路线 C：不做雷达图

改成 4–6 条横向进度条，每条写清「这个数字来自哪些行为」。最诚实，但要重做 #427 的 UI 壳。

## 4. 我的建议

**先走 A，同时把 B 的字段需求挂到 #401 的后续**。

理由：

1. 雷达图的价值在「一眼看出形状」，但**假的轴会毁掉这个价值**——用户看到「社交 0.34」会问「我哪里社交了」，
   而我们答不上来；
2. A 是纯客户端改动，不阻塞任何人，今天就能接上真数据；
3. B 补字段后，A 的轴可以直接替换，页面结构（雷达图 + caption）一行不用改；
4. 热度这条**永远做不了**（我们没有全站热度基准），所以「六维」这个产品设定本身要接受一次修订。

**如果产品坚持要 mock 那六个名字**，那只有一个诚实做法：把算不出来的轴显示为**空心/虚线**并标注
「数据不足」，而不是填一个编的数字。

## 5. 锐评（`review`）：规则模板，不是 LLM

客户端不能调 LLM，后端也没有这条链路（契约注释里的「首站是 LLM」指的是网站侧）。

用三段式模板，每段都由可验证的数据决定：

```
句1（口味）："{主类型}为主" + "，偏爱{最强正标签}"        ← type_weights / tag_weights
句2（广度）：  "题材跨度{很广｜中等｜偏窄}"                 ← 非零 tag 数分档（≥8 / 4–7 / ≤3）
句3（态度）：  "打分{偏严｜中肯｜宽容}（均分 {mean}）"      ← rating_tendency.mean（<6.5 / 6.5–7.9 / ≥8）
```

空态（`sample_size < 5`）：**不生成锐评**，显示「看得还不够多，多留几条记录再来」。

⚠️ 文案里不要出现「你是」这种定论句——规则生成的文字一旦像断言，用户会觉得被贴标签。
用「看起来」「偏向」这类描述性措辞。

## 6. 称号（`title`）：从最强正标签生成

```
有正标签：  "{最强正标签}派"            → 科幻派 / 群像派
无正标签：  "{主类型}观众"              → 动画观众
sample_size < 5：不显示称号（UI 已支持空串）
```

注意：**只能用正权重标签**。`tag_weights` 的负值是「不喜欢」，拿来当称号会冒犯人（比如「后宫派」）。

## 7. 三个点（2026-11-08 按推荐值定稿）

1. **轴名**：采用方案 A 的六轴（类型集中度 / 题材广度 / 口味浓度 / 评分态度 / 活跃度 /
   近期活跃），已实现（#487）。换轴只改 `PersonaInsightMapper` 一个文件。
2. **热度**：正式砍掉。我们没有全站热度基准，除非以后引入榜单。
3. **`collection_status` / `review_count`**：暂不提。#516 之后「评分态度」已经能吃来源站均分
   （自己写的点评分优先），短期不缺这一根；等真实用户数据跑一段时间再评估。

## 8. 实现步骤（按 A 走）

1. `PersonaRemoteDataSource.fetchInsight()`：把 `PersonaProfile` 映射成 `PersonaInsight`（公式见 §3A）；
2. `title` / `review` 用 §5 / §6 的规则生成，抽成一个纯函数（可单测，不用 widget 测试）；
3. `topTags` 取 `tag_weights` 正向前 8；
4. `tone` / `boundAccount` 保持 `null`；
5. 空态：`sample_size == 0` → 整页空态（现有壳已支持 `dimensions.isEmpty`）；
6. 测试：公式边界（全零 / 单一类型 / 全负标签）、锐评分档、称号不取负标签。

接口落地后**页面一行不用改**——这正是 #427 当初把 `PersonaInsight` 和契约分开的目的。
