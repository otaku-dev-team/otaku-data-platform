# 网站连续性与重心反转：风险清单与预案

> **状态**：草案（2026-10-26），含**待拍板事项**，本文不擅自决策。
> 上位依据：[`product-positioning.md`](product-positioning.md)、[`open-decisions.md`](open-decisions.md)。
> 相关：[`app-registration-approach.md`](app-registration-approach.md) §7（网站不可用时的降级）。

---

## 1. 两个问题

负责人提出（2026-10-26）：

1. **网站可能关停** —— 可能性不大，但一旦发生影响面大；
2. **客户端用户更多，运营重心转移到客户端，网站反而要从平台同步** —— 即主客关系出现反转。

本文逐项给出**影响清单**、**做什么 / 不做什么**，以及**需要拍板的点**。

---

## 2. 问题一：网站关停会断掉什么

### 2.1 影响清单（按能力逐项）

| 能力 | 网站关停后 | 说明 |
|---|---|---|
| 浏览作品（列表 / 详情 / 检索） | ✅ **不受影响** | 数据是**快照副本**存于我们库内（全量 57.1 万条） |
| 已登录用户（短期内） | ✅ 不受影响 | 平台会话令牌有效期内照常工作 |
| 已登录用户（令牌过期后） | ❌ 无法续期 | 续期要走网站 authorize，源没了即失败 |
| 新用户注册 | ❌ 不可用 | 账号必须创建在网站侧（账号统一的固有代价） |
| **已缓存在磁盘的封面** | ✅ 可用 | 已落盘的不依赖源 |
| **未缓存的封面** | ❌ 取不到 | 后端 `/api/covers/{id}` 是**服务端回源网站 `/media/*`**（host 白名单、fail-closed），源没了就取不到 |
| `source_url` 跳转 | ❌ 失效 | 指向网站人读页，关停即 404 |
| 内容更新 | ❌ 停止 | sync 从网站抓取；**Bangumi 独立源不受影响** |

### 2.2 关键判断

- **内容不会丢失**——快照在我们库里。丢的是**更新能力**与**身份**，不是已有数据。
- **最痛的是身份**：所有用户依托网站身份，这是我们为"账号全渠道统一"付出的尾部代价。
- 可能性不大 → **不为它改变架构**。

### 2.3 做什么 / 不做什么

**明确不做**：

- ❌ **不引入第二套账号**兜底。用永久的架构代价（账号分裂）去换一个低概率场景，不划算。

**要做的（都是低成本保险）**：

| 措施 | 现状 | 作用 |
|---|---|---|
| **身份可迁移** | 用户表已预留 `identity_source` + `external_user_id`（C3 已定） | 网站关停时可切换为平台身份：邮箱验证重建 + 收藏映射，不返工 |
| **提高封面自持率** | 封面仅 2.7% 有地址，且依赖回源网站 | 见 §4 —— 回填后封面指向 **Bangumi CDN（独立源）**，网站关停也不丢 |
| **离线能力**（W1.2） | riceyu02 自主推进中 | 客户端缓存越厚，网站不在时越能撑 |
| **合同条款** | 尚未约定 | 见 §6 待拍板 3 |

## 3. 问题二：重心反转（网站反过来要从平台同步）

### 3.1 先定性：这是好消息

方向本来就是让客户端成为用户主入口（G1：客户端体验优于网站原生页）。客户端用户更多、网站退为内容源 / 后台，**说明路走对了**。

### 3.2 但形态必须守住边界

| 形态 | 是否合规 | 理由 |
|---|---|---|
| **我们提供只读出口，网站自己来拉** | ✅ **合规** | 我们不写网站；网站用自己的凭据来取；数据所有者取自己的数据，天经地义 |
| **我们主动往网站写数据** | ❌ **违反铁律** | "只读、不回写"——我们代网站写业务数据，越界且要担责 |

结论：**可以做，但形态是「出口」，不是「回写」。**

### 3.3 需要新增什么（若要支持）

- 现在是单向的：网站 → 我们（`/internal/import/**` 导入接口）。
- 反向需要：**面向网站的数据读取出口**（网站持自己的凭据来取用户行为 / 同步状态等）。
- 这是**跨模块接口新增** → 红线 1，须三人确认（后端 + 客户端）。
- 且它是**新产品能力**：我们开始"供数"，会影响定位叙事与计价维度（A3 五维度里"是否需要身份打通"之外可能新增一项）。

### 3.4 顺带回答一个隐忧：网站弱化了，内容从哪来

- 作品数据现由 sync 从网站抓取；网站停更 → **网站独有内容（约 1.5 万条）停更**。
- 但我们有 **Bangumi 独立源**（约 55.6 万条，占全量 97%）→ **内容大盘不依赖单一网站**。
- 断的是：网站独有内容的新增、以及人读页链接。

### 3.5 顺带回答另一个隐忧：网站没人访问了，注册还合理吗

合理，且体验不受影响 —— App 内 WebView 承载网站注册页，用户全程在 App 内完成，**感知不到网站存不存在**。
这是 `app-registration-approach.md` 方案的一个附加价值：即使网站退化为纯后台，注册体验也不打折。

## 4. 封面：回填的"去依赖"只在首站成立，通用答案另有一解

封面回填（Issue **#124**）原定位是数据补全（覆盖率 2.7% → 显著提升）。我一度认为它还有第二重价值：**回填后封面指向 Bangumi CDN（独立第三方源），网站关停也照常显示**。

> ⚠️ **该论据被负责人纠正（2026-10-26），现限定如下。**

### 4.1 为什么它不能推广

回填能成立，前提是**这批数据本来就有 Bangumi subject id 对应关系**——首站 Otaku 的 bangumi 源（约 55.6 万条）直接来自 Bangumi 档案，`source_id` 即 subject id，所以能调 Bangumi API 取图。

**换一个网站，条目与 Bangumi 没有对应关系，这条路根本走不通。** 这是 Otaku 这类"开发中的小站"特有的条件——它本来就依托 Bangumi 建库。其他网站大概率无法复刻。

**教训（值得作为通用设计原则）**：不要把首站的巧合当成架构能力。凡"去依赖"结论，须先问一句——它依赖的是**通用机制**，还是**恰好存在的对应关系**？

### 4.2 真正通用的去依赖：封面自持

与源无关的通用解法只有一个思路：**自己持有一份**。

| 做法 | 解决什么 | 是否通用 |
|---|---|---|
| **回填**（改指向 Bangumi CDN） | 解决"**有没有**"——覆盖率 2.7% → 提升 | ❌ 仅首站（依赖 subject id 对应关系） |
| **封面自持**（抓取后持久化到我们自己的存储） | 解决"**稳不稳**"——无论源是谁，我们都有自己的一份 | ✅ **与源无关，通用** |

现状是"用时回源 + 磁盘缓存"（`/api/covers/{id}` 回源后落盘）：**已访问的图是稳的，没访问过的图源一断就取不到**。
封面自持 = 把"碰巧缓存过"变成"确定持有"，顺带还能降低回源压力、加快客户端加载。

**代价**：需要存储规模评估。按何种规格自持（原图 / 中等图）、总量多大，**须实测确认，本文不给数字**（纪律：不编造）。这也构成对服务器资源的要求，与 Issue #78 同源。

### 4.3 修正后的结论

- **#124（回填）** 对首站仍有去依赖价值，但它是**首站特例**，不足以作为通用论据，其战略优先级**回归"数据补全"本来的位置**。
- **通用的去依赖措施是"封面自持"** —— 与 Bangumi 无关、与网站无关，是架构层能力，应作为长期项评估（阻塞：服务器存储资源，同 #78）。

---

## 5. 一句话结论

- **网站关停**：内容不丢，丢的是更新与身份；不为此引入第二套账号，但要**保住迁移路径**。
- **重心反转**：是成功不是问题；支持方式是**提供出口**而非**回写**，属新产品能力需拍板。
- **封面的稳**：改指向第三方（回填）只是首站特例；**通用答案是"自持"**——与源无关，靠我们自己持有一份。
