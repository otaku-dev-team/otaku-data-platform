# 客户端能力承载清单（App 原生 vs 跳网站）

> 目的：把「哪些能力 App 原生做、哪些跳回网站」写成一份**按站点维护的动态清单**，随版本更新。
> 上位：总目标 G1–G3（[`project-charter.md`](project-charter.md) §1）、待决策清单 [`open-decisions.md`](open-decisions.md) **B1 类**。
> 维护人：@riceyu02（W1 客户端）。**每一列的形态变了就要改这一份**，改完客户可以直接看「哪些已经有了、哪些在路上」。

## 1. 为什么非得有这份清单

客户已经质疑过一句很难回答的话：**「什么都跳回网站，要你们干什么？」**

章程 §1 里 G3 写的是「用户不被困在平台内，任何作品都能回到原站」——
跳转本身是**设计内的补位**，不是偷懒。但这句话只有在**清单存在**时才成立：
有了清单，才能指着说「浏览、检索、离线、收藏、追番提醒是原生的；评论、投稿、后台本来就该在网站上」。
没有清单，G3 永远只是一句口号。

## 2. 判定原则（新增能力时用这三条，不要临场随机决定）

| 判定 | 结论 | 理由 |
|---|---|---|
| **只用公开 API 就能实现、且要离线可用 / 跨端一致** | **原生做** | 这是 G1「体验优于来源站原生页」的落点，也是这套客户端存在的意义 |
| **要在来源站写数据、或本身就是社区的产物** | **跳网站** | 评论、投稿、论坛、运营后台——我们既没有这份数据，也不该代持站点账号（铁律 2） |
| **站点的认证与账号管理** | **跳网站** | 注册、找回密码、`client_secret` 授权流程一旦在客户端里再造一份，就是把用户密码引入平台边界（铁律 1） |

一句话：**我们做的是「读」的体验增强层和「自己账号」的个人数据层**，
**写内容、社区互动、账号生命周期**仍然归站点——这不是能力缺口，这是分工。

### 3.4 设计内跳网站的部分（不是缺口）

| 能力 | 形态 | 为什么不该原生做 |
|---|---|---|
| 注册、找回密码、服务端浏览历史 | ⤴️ 跳网站 | 站点账号生命周期归站点；再造一份就等于把密码 / 凭据引入平台边界（铁律 1、#141 的授权形态） |
| 评论、打分、投稿、论坛 | ⤴️ 跳网站 | 社区的产物，我们没有这份数据也不要代持（铁律 2） |
| 站主运营后台 | ⤴️ 跳网站 | 属 A4 单独排期，不在客户端的范围内 |

## 4. 这份清单怎么用

1. **每接入一个来源站，就按同一张表再填一列**——形态会是 per-site 的，因为站点侧能提供什么不一样（G2 的出发点）。
2. **形态发生变化的那一版，同时改这一份**：尤其「🔵 在路上」变「🟢 原生」时，客户是看这份清单判断进度的。
3. ⚠️ **这份清单只记录结果，不构成允诺**：某条能力若需要新增公开端点或改动字段，仍是跨模块契约变更（章程 §3.2 红线），要先走三人确认——清单里写清楚了也照样要确认。
