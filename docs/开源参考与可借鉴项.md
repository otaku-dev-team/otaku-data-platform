# 开源参考与可借鉴项

> 调研记录，不改任何代码。2026-11-01。
>
> **这页只放结论和入口。** 细节没抄进来——需要的人按「先看哪儿」直接去读源码。
> 抄二手描述不如看原文件，何况原文件会更新，这页不会。

---

## 1. 结论

**① 有对标，但都不在我们这条线上。**
「一个客户端适配多个站」是一整类，最大的 [mihon](https://github.com/mihonapp/mihon) 24.9k 星。
但它们全是客户端单方面抓站：站点不知情、不授权、改版就挂。
我们是站点授权后接入、站点侧零开发。**这层开源里没有现成设计**，只能自己定，别在上面找参照。

**② 能抄的分三档，别一刀切。**
想法和结构随便用；十几行的通用实现可以用；整个文件和核心算法不搬。理由在 §3。

**③ 对着它们核出两处我们自己的差距。**
收藏表缺版本号和墓碑（§4）、筛选参数全局固定（§5）。这两处跟「抄不抄」没关系，是核的过程里发现的。

## 3. 抄的分寸

**① 想法、结构、字段划分 —— 随便用。** 版权不保护想法，只保护表达。
「冲突只分三档」「评分不拆字段」这些判断，照着写自己的实现，跟许可证无关。本文 90% 的价值在这一档。

**② 十几行的通用实现 —— 可以用。** 一段 SQL、一个 enum、一对 DTO，这个量级不构成实质性表达。
只留两个习惯：不连注释和命名一起搬；**commit 里不写「参考 xxx 第 N 行」**——
对 copyleft 项目，这种溯源等于自己给对方递证据。

**③ 整个文件、核心算法 —— 不搬。** AGPL / GPL 的传染性落在整体交付物上，
后端是要交付给客户的，冲突的代价远大于省下的几百行。

## 4. 收藏同步：唯一「抄了能少踩坑」的一条

他们解决的是和我们一样的问题：本地库和站点各有一个写入口，谁改的、要不要覆盖对方。

三个判断直接可用：

- **评分整体判，不拆字段。** 评分 + 短评 + 标签 + 是否私密绑成一个单元。
  拆开合并会拼出谁都没写过的组合（「给了 8 分但没写短评」+「写了短评没评分」）。
- **删除单独成一档。** 它是破坏性的，选错就把收藏删了，必须让用户明确选。
- **进度带计数。** 六个状态、每步带条数，结束带 error。用户知道同步到哪了。

### 我们的缺口

`collection` 表（`V2__account_and_collection.sql:40`）只有 `updated_at`：

```sql
CREATE TABLE collection (
    user_id, work_id, status, created_at, updated_at,
    UNIQUE KEY uk_collection_user_work (user_id, work_id)
) COMMENT '个人收藏；取消收藏即删行，状态随之消失';
```

- **没有版本号** → 两个写入口并发改，只能「后写的赢」，不知道是不是覆盖了别人；
- **没有墓碑** → 分不清「两边都删了」和「一边删了、另一边还没同步」；
- 和 #249 的软删语义有交互：软删行占唯一键，upsert 必须把 `deleted_at` 置空。

要做收藏和站点同步，**前置是先加列**（列级版本，或 `deleted_at` 与 #249 统一）。
属跨模块变更，得三人确认、改 `openapi.yaml`。这份文档里不改。

顺序建议只做「列级版本」，不做命令日志——命令序列是为多端离线编辑付费的，我们现在没这个场景。

## 5. 通用客户端类：有，但没有一个是「站点授权后接入」

这一类的体量都比前面几个大，形态也最接近我们，但差别是本质的：

| 项目 | 形态 |
|---|---|
| mihon + keiyoushi 扩展源 | 一个客户端，每站一个扩展包，几百个站 |
| Suwayomi-Server | 服务端跑扩展，多客户端共用一个后端 |
| legado | 声明式「书源」，用户自己写规则 |
| Aidoku | iOS 上同一套模型 |

**扩展都是社区单方面写的**——抓页面、逆向接口，站点不知情、不授权、改版就挂。
我们不写扩展，是站点给数据。所以「站点怎么授权、授权后能拿到什么」没有参照，自己定。

### 三件能抄的

**① 筛选器由站点自己声明。** mihon 每个站实现 `getFilterList()`，客户端不硬编码。
我们是一套 `type` / `tag` 打所有站——**加第二站那天一定要打补丁**，现在先记着。

**② 能力用布尔写进契约，不用文档对齐。** `supportsLatest: Boolean` 在代码里，
客户端据此决定显不显示「最新」入口。我们对应的是 `站点能力差距清单.md`——文档会过期，布尔不会。

**③ 隔离靠加载器，不靠约定。** 他们扩展是独立安装包 + 独立 classloader。
我们的站点隔离是一个后端加一个 `source` 字段、靠查询条件保证
（`scripts/check-site-isolation.py` 守的就是这个）。单站私有化够用，
但站点多了要清楚：**这是约定，不是结构**。现在不用改。

### 三件不抄

- **客户端自己抓站。** 我们站点侧给数据，这是定位不是实现选择。
- **legado 的规则 DSL。** 我们要的是站点给接口，不是让用户写规则。另外它没有 license。
- **Suwayomi 的多用户模型。** 它的多用户是「一个服务端多个用户」，我们是「多个站点多份交付」，别混。

## 6. 其余四个，看结论就够

**多源适配（animeko）。** `datasource/` 一个源一个 module，布局干净，但参考价值有限：
我们只有两个源，且走「Python 抓 → Java 入库」，不是客户端直连多源。不必按这个粒度重切。

**后台任务（ani-rss）。** 这条我一开始判成可借，核完是反的：
`import_batch_run` 已被 importer / schedule / article 三处共用（`ImportBatchRepository:64`），
还多做了 requestHash 比对，我们比它细。**没有增量。**

顺带发现一处可以收敛：`applyOnce + transactionTemplate` 抄了三遍
（`ImportService:302`、`ScheduleImportService:179`、`ArticleImportService:179`）。
改导入语义要改三处，是机会；但三处实体类型不同，**不建议顺手重构**。

**客户端（Kazumi）。** 分层对得上（`repositories` ↔ 我们的 `data`），说明结构没错，
只借网格尺寸档位。#355 正在做三档密度，可对照断点取值（我没逐行读它的网格实现）。

**元数据匹配（KomgaBangumi）。** 只借一条判断：匹配不上就留空，不写一个差不多的。
13,261 组同名作品已经证明「标题 + 年份」会撞，错封面比没封面更糟——用户看不出来，我们也查不出来。
打分实现**我没读**，要用先读源码，不预设它比我们的做法好。
