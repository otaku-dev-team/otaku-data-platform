## 1. 结论先说

### 1.1 抄的分寸：想法随便用，片段可以用，整文件不搬

四个项目的许可证：

| 项目 | 星 | 许可证 | 整文件搬 |
|---|---|---|---|
| open-ani/animeko | 21.4k | **AGPL-3.0** | 不搬 |
| Predidit/Kazumi | 40.4k | **GPL-3.0** | 不搬 |
| wushuo894/ani-rss | 3.6k | **GPL-2.0** | 不搬 |
| dyphire/KomgaBangumi | 141 | MIT | 可以，留版权声明 |

分三档看，别一刀切：

**① 想法、结构、字段划分、状态机档位 —— 随便用。**
版权不保护想法，只保护表达。他们决定「冲突只分三档」「评分不拆字段」，
我们照着这个判断写自己的 Java enum，是我们的东西，跟许可证无关。
本文 90% 的价值在这一档。

**② 小段实现（十几行、通用写法：一段 SQL、一个 enum、一对 DTO、一处配置）—— 可以用。**
这种量级本身就不构成「实质性表达」，全世界的 Spring 项目都长一个样。
只保留两个习惯：不连注释和命名一起照搬（注释是最像「表达」的部分），
以及**不要在 commit / PR 里写「参考 xxx 项目第 N 行」**——
对 copyleft 项目，这种溯源等于自己给对方递证据。

**③ 整个文件 / 核心算法实现 —— 不搬。**
AGPL / GPL 的传染性落在**整体交付物**上：被认定是衍生作品时，义务是
「按同许可证提供完整源码」。后端是要交付给客户的，这条和交付形态直接冲突，
而冲突的代价远大于省下的那几百行。

所以本文写的是「他们怎么想的」，遇到值得顺手抄的片段会直接标出位置和量级。

### 1.2 按我们的卡点排优先级

| 优先级 | 借鉴点 | 来源 | 对应我们的哪一处 |
|---|---|---|---|
| **高** | 收藏双向同步的冲突模型 | animeko | #242 之后的收藏对齐；**现有 `collection` 表结构做不了** |
| 中 | 跨源条目映射的三元组形态 | animeko | #356 人物 id、E1 跨源身份 |
| — | ~~后台任务「运行留痕进库」~~ | ani-rss | **核完是反的**：我们已统一，无可借；只发现一处收敛机会（§4.2） |
| 低 | 客户端分层与网格尺寸档 | Kazumi | `app-client` 呈现层 |
| 低 | 元数据匹配的「宁可留空」策略 | KomgaBangumi | W3 封面 / 简介补全 |

只有第一条是「抄了能少踩一个坑」，其余是「看一眼省半天」。
ani-rss 那条我一开始判错了方向，留在表里是为了下次别再花半天验一遍。

## 2. 收藏双向同步（animeko）· 最值得看的一条

### 2.1 他们面对的问题和我们一样

本地库和站点各有一个写入口，用户在两边都可能改，于是「同步」必然要回答：
**这次改动是谁的、要不要覆盖对方。**

### 2.2 他们的三个设计

**① 同步是命令日志，不是直接改状态**

`app/shared/app-data/src/commonMain/kotlin/data/models/bangumi/BangumiSyncCommand.kt`：

```kotlin
data class BangumiSyncCommand(id: String, op: BangumiSyncOp?, createdAt: Instant)

sealed class BangumiSyncOp {
    data class AddCollection(subjectId, type, rating)      // 加收藏
    data class UpdateCollection(subjectId, type, rating)   // 改收藏
    data class DeleteCollection(subjectId)                 // 删收藏
    data class UpdateEpisodeCollection(subjectId, episodeId, type)
}
```

每条命令带 `createdAt`。同步是把命令序列推给对方，而不是「把当前状态整表覆盖过去」。
好处是顺序可判、失败可重放；代价是要维护命令表。

**② 冲突按字段类型分档，不逐字段合并**

`BangumiMerge.kt` 里 `BangumiConflictFieldType` 只有三个值：

- `COLLECTION` —— 收藏状态，**包含「某一侧删除了收藏」**
- `RATING` —— 评分单元，`评分 + 短评 + 标签 + 是否私密` **作为一个整体**解决
- `EPISODE` —— 观看进度，只出现在自动合并明细里，**不产生需要用户确认的冲突**

两个细节值得记：

- 评分不拆字段。用户的「我给了 8 分但还没写短评」和「我写了短评但没评分」同时存在时，
  逐字段合并会拼出一个谁都没写过的组合。整体解决反而符合直觉。
- `DeleteCollection` 是破坏性操作，源码注释原文写明「选择 NOT_COLLECTED 的一侧会删除收藏（破坏性）」，
  所以它单独成一档、要用户明确选。

**③ 全量同步是显式状态机**

`BangumiSyncState.kt`：
`Preparing → FetchingSubjects(count) → FetchingEpisodes(count) → Inserting(saved) → Finishing(saved) → Finished(saved, error)`

进度带计数、结束带 error、还有一个 `Unsupported`（服务端版本不支持）。
客户端据此渲染进度条，用户知道「同步到哪一步了」，而不是一个转圈。

### 2.3 对我们的直接结论

**现有 `collection` 表做不了「谁改的」判定。** 核对 `V2__account_and_collection.sql:40-54`：

```sql
CREATE TABLE collection (
    user_id, work_id, status, created_at, updated_at,
    UNIQUE KEY uk_collection_user_work (user_id, work_id)
) COMMENT '个人收藏；取消收藏即删行，状态随之消失';
```

- 只有 `updated_at` 一个时间戳，**没有版本号**，也没有各字段的修改时间
  → 客户端和站点两个写入口并发改同一个收藏时，服务端只能「后写的赢」，无法判断是不是覆盖了别人的改动；
- **没有墓碑**，取消收藏就是删行
  → 站点侧删了收藏、我们这边也删了，同步时无法区分「两边都删了」和「一边删了、另一边还没同步」；
- 和 #249 的软删语义有直接交互（`docs/deletion-semantics-proposal.md`）：
  软删行会占唯一键，upsert 必须把 `deleted_at` 置空——这一条已经踩过一次。

**所以如果要做（#242 之后）收藏与站点对齐，前置条件是先改表**：

| 缺什么 | 补什么 | 代价 |
|---|---|---|
| 「哪一侧改过」 | `base_version`（客户端带回上次见到的版本）或每字段 `updated_at` | 加列 + 三端契约 |
| 「删了」和「没同步」 | `deleted_at` 墓碑，与 #249 统一 | 加列 + 所有查询加过滤 |
| 改动的先后 | 命令序列（要新表） | 最重，除非要做离线队列 |

三者都是**跨模块数据结构变更 → 三人确认 + 改 `openapi.yaml`**。
建议顺序：只做第一行（列级版本），不做命令日志——我们目前是单站、单客户端，
没有多端离线编辑的场景，命令日志是为那个场景付费的。

### 2.4 可以直接用的部分

`BangumiSyncState` 的六个状态和 `BangumiConflictFieldType` 的三档分类是**纯设计**，
不含他们的代码表达（Kotlin sealed class 那套换成 Java enum 就是我们的东西）。
写我们自己的状态机时按这两个清单对齐即可，别自己再想一遍。

### 2.5 真动手时大概长这样

下面是按 §1.1 第二档（十几行、通用写法）落的形状，不是从他们代码翻过来的，
真要写就照这个起手：

```java
// 冲突只分三档：收藏、评分单元、剧集进度
public enum CollectionConflictField { COLLECTION, RATING, EPISODE }

// 评分不拆字段——四个值一起判，任一不同即为冲突
public record RatingUnit(Short score, String comment, List<String> tags, boolean isPrivate) {
    public boolean conflictsWith(RatingUnit other) { /* 任一字段不等即 true */ }
}

// 同步是显式状态机，进度带计数、结束带 error
public sealed interface CollectionSyncState {
    record Preparing() implements CollectionSyncState {}
    record FetchingSubjects(int count) implements CollectionSyncState {}
    record Inserting(int saved) implements CollectionSyncState {}
    record Finished(int saved, String error) implements CollectionSyncState {}
}
```

三处判断是他们的、不是我的：**评分整体判**（拆开合并会拼出谁都没写过的组合）、
**删除单独成一档**（破坏性，要用户明确选）、**进度要带计数**（不是转圈）。

## 3. 多源适配与跨源条目映射（animeko）

### 3.1 目录布局

```
datasource/
├── api/        统一契约
├── bt/         种子
├── ikaros/     自有服务端
├── jellyfin/   媒体库
└── web/        网页
```

一个源一个 module，各自实现 `api` 的契约。旁边 `app/shared/` 按 UI 层再切
（`ui-foundation / ui-comment / ui-download / ui-episode / ui-exploration / ui-exprovider / ui-adaptive / application / app-data`）。

对我们的参考价值有限：我们只有两个源，且走的是「Python 抓 → Java 入库」而不是「客户端直连多源」。
我们的 `sync-python/src` 里适配器的分层已经够用，不必按这个粒度重切。

### 3.2 跨源条目映射：一个极简三元组

`datasource/ikaros/.../models/IkarosSubjectSync.kt` 全文只有四个字段：

```kotlin
data class IkarosSubjectSync(
    val subjectId: Long,
    val platform: String?,   // 可空
    val platformId: String?, // 可空
    val syncTime: String?,
)
```

值得抄的是**可空**这件事：他们允许「知道这条属于哪个平台，但不知道对方 id」。
映射是尽力而为，不确定就留空，不硬猜。

### 3.3 和 #356 的关系

我们的问题是反过来的——**不是缺映射，是两套 id 撞了**：
`people.source_id`（网站自增）与 `person_ref`（Bangumi 人物 id）有 4,115 个数值相同但指的不是同一个人，
而 #271 已经按后者填了 19,399 行且 `INSERT IGNORE` 只补不覆盖，
**错名一旦写进去就改不回来**（详见 `docs/person-id-unification.md`）。

animeko 这个形态能借的只有一条：**「平台 + 平台 id」永远是显式的一对，不塞进主键**。
我们的 `work` 表已经是这个形状（`uk_work_source(source, source_id)`），
`people` 要想不重蹈覆辙，就不该把 Bangumi 人物 id 放进 `source_id`——这正是
`person-id-unification.md` 里 A 方案的做法，但要注意 A 的代价是**丢掉网站本地 id**，
以后要有「网站侧改了人名、我们同步」这类场景，就没有对照键了。

> 这条不是「抄 animeko」，是拿它当反例核对 A 方案。

### 3.4 不能抄的部分

他们的条目是「同一部番在多个源」，我们的是「同一部作品在两个来源各自独立入库」。
前者的终点是合并成一个条目，后者的定位明确**不合并**（`docs/d3-cross-source-identity-proposal.md` §1）。
跨源合并属探索项 E1，按 `project-charter.md` §3.2 是红线。抄字段形态可以，抄合并不行。

## 4. 后台任务留痕（ani-rss）

### 4.1 结构

`pom.xml` 只有两个 module：`ani-rss-application` / `ani-rss-ui`。Java 侧包：

```
ani/rss/{annotation, auth, build, cache, commons, comparator, config, controller,
         download, entity, enums, exception, handle, list, mcp, notification,
         service, start, task, update, util}
```

`task` 下只有四个类：`BaseTask / RssTask / BgmTask / RenameTask`——**任务类型很少**。
`entity` 里有 `Log.java / Item.java / ListAni.java`，即运行记录进库，不靠日志文件。

### 4.2 我们不仅没落后，而且已经统一了

这条最初被我判成「可借」，核对后是反的。

`V4__import_batch_runs.sql` 的 `import_batch_run` 有
`run_seq / inserted / updated / unchanged / rejected / errors(JSON) / started_at / finished_at`，
主键 `uk_batch_run(batch_id, run_seq)`——已经比一个 `Log` 表细致。

更关键的是**三处导入共用同一套留痕**，不是各写各的：

```
importer/ImportBatchRepository.java:64   public int saveAndRecordRun(...)
importer/ImportService.java:217          batchRepository.saveAndRecordRun(...)
schedule/ScheduleImportService.java:161  batchRepository.saveAndRecordRun(...)
article/ArticleImportService.java:161    batchRepository.saveAndRecordRun(...)
```

而且 `ScheduleImportService` 还多做了两件他们没做的事：
`findRequestHash(batchId)` 比对上一轮，**同一 batch_id 内容变了会打 warn**
（"同一天数据变更"）；返回 `run_seq` 并写进日志，能直接回答「这是第几轮」。

**结论：这条没有可借增量。** 唯一值得记的是他们的收敛倾向——
`task` 下只有四个类、一个 `BaseTask`，说明任务抽象做得薄。
我们这边是同一段形状抄了三遍：

```
importer/ImportService.java:302-303           applyOnce → transactionTemplate.execute
schedule/ScheduleImportService.java:179-180   applyOnce → transactionTemplate.execute
article/ArticleImportService.java:179-180     applyOnce → transactionTemplate.execute
```

如果哪天要改导入语义，是三个地方一起改。这是**收敛机会**，不是抄点——
三处实体不同（`NormalizedItem` / `NormalizedSchedule` / `NormalizedArticle`），
抽公共骨架要先处理这个差异，收益和风险都不是零，别顺手重构。

### 4.3 不要硬套

他们是 RSS 订阅驱动（订阅 → 发现新种子 → 下载 → 重命名），
我们的导入是「一批数据进来 → upsert → 记一轮」。
任务粒度、重试语义都不一样，相通的只有「留痕」这一点，而这一点我们已经做了。

## 5. 客户端（Kazumi）

`lib/` 分层：`bean / core_module.dart / app_module.dart / modules / pages / repositories / request / services / plugins / webview / utils`。

- **可借**：`repositories` 与 `pages` 分离——我们的 `app-client/lib/data` + `features` 已经是这个形状，
  说明结构没错，不用改；
- **可借**：网格尺寸档位。我们 #355 正在做「作品库三档密度 + 列数可调」，
  可对照它的断点取值（**未验证**：没有逐行读它的网格实现）；
- **不借**：`plugins` 那套规则热更新。我们的数据来自自建后端，不是外部规则抓取，
  引入规则体系等于多一层要维护的东西。

另外它 40k 星但落点是「看番」：播放器、弹幕、超分。我们是「逛数据」，页面结构重合的只有列表 / 详情 / 搜索。

## 6. 元数据匹配（KomgaBangumi，MIT）

用 Bangumi API 给 Komga 漫画库刮削元数据。对 W3（封面 / 评分 / 简介补全）的价值在**匹配策略**：
标题相似度 + 年份的组合判定，以及「匹配不上就留空，不写一个差不多的」。

这条对我方尤其重要：`work` 里 13,261 组同名作品已经证明「标题 + 年份」会撞，
封面回填如果按标题直接匹配，会把 A 的封面贴到 B 上，而且**错封面比没封面更糟**——
用户看不出来，我们也查不出来。

> **未验证**：只确认了仓库定位、许可证与活跃度，没有读它的打分实现。
> 要用得先读源码，不预设它比我们的做法好。

## 7. 明确不做

1. **整文件 / 核心算法搬 copyleft 代码**（§1.1 第三档）。小段通用写法不受此限。
2. **抄聚合看番的产品结构**。animeko / Kazumi 都是「把所有源聚到一个 App 里看」，
   我们是「给某一个独立网站做它的客户端」。照搬会直接撞 `docs/product-positioning.md` 的定位边界。
3. **抄跨源合并**。E1，红线，先过三人确认。
4. **为了「对齐开源」而重构现有结构**。我们 `sync-python` 的适配器分层、`importer` 的运行留痕
   都不比参考项目差，改的收益是负的。
