## 0. 一句话

让「网站自己的账号」在客户端里直接可用，**唯一钥匙是站主开放授权端点**。首站现在没有——
本文说清三件事：**我们要的最小集是什么、怎么跟站主开口、站点给不了时的分级预案**。
首站已开口并拿到定稿契约（A 路），本文规格即按站点定稿态维护，后续站点问需直接复用 §4 沟通稿与 §2 契约。

## 1. 现状事实（2026-10-24 只读探测，非推测）

| 事实 | 内容 |
|---|---|
| 网站**有**完整账号体系 | `/login` `/register`（邀请码）`/logout` `/me` `/contents/{id}/favorite` `/contents/{id}/status` `/me/favorites/*` `/me/history/*` `/me/persona/*` |
| 但**全是页面端点** | 网页表单 + cookie session，**无 JSON API、无任何 OAuth / token 签发端点** |
| 还有两个产品相关限制 | 注册要**邀请码**；登录态是 cookie，App 拿不到也不该拿 |

**结论**：定位定的目标状态（客户端直接用网站账号）**现阶段技术上做不到**；平台账号是按定位 §4.1 定位的**过渡方案**，不是终态。本文要解决的，就是把「做不到」变成「站点给一个小接口就能做到」——**首站已确认能给（2026-10-24）**。

## 2. 接口契约：从「我们的最小集」到「站点定稿」

我们的原始最小集是「两个端点 + 一张令牌表」的不完整 OAuth 形态；站点回复采用**标准 OAuth 授权码思路**，
安全更严（令牌端点加 client_secret），且给了 `GET /api/me` 与 `POST /api/auth/revoke` 的完整形态。**定稿契约如下（站点 2026-10-24 回复，一一对应原规格端点）**：

| # | 端点（站点侧） | 调用方 | 入参 | 出参 |
|---|---|---|---|---|
| 1 | `GET /oauth/authorize` | 浏览器 / WebView | `client_id`、`redirect_uri`、`state`（均必填；`redirect_uri` 须在站点白名单内，`state` 防 CSRF） | 未登录先走站点登录页；**登录后自动回跳** `redirect_uri?ticket&state`（站点单方面授权，无用户同意页） |
| 2 | `POST /api/auth/token` | **平台后端**（服务端到服务端） | `ticket`、`client_id`、`client_secret`（`application/x-www-form-urlencoded`；secret 仅平台后端持有、永不进浏览器，站点侧恒定时间比对） | `{ access_token, token_type:"Bearer", expires_in:3600, user:{ external_user_id, nickname, avatar_url } }` |
| 3 | `GET /api/me` | 平台后端 | Header: `Authorization: Bearer <access_token>` | `{ external_user_id, nickname, avatar_url, scope:"identity" }` |
| 4 | `POST /api/auth/revoke` | ① **自助吊销（self-revoke）**：持有效 Bearer 的平台后端（用户在 App 内点「断开与网站的连接」时触发）；② **管理员应急吊销**：站点管理员会话 | ① 无需入参，撤销**该令牌持有者名下、同一 client 的全部未吊销令牌**；② `access_token` 或 `external_user_id`（全量） | 撤销后相关令牌立即失效。**自助吊销不暴露任何终端用户可见的站内 UI，端点由站点掌控** |

**站点声明的安全边界（我们拿不到的，也是我们不想要的）**：用户密码全程只在站点登录页输入；令牌 scope 固定 `identity`（只读用户资料，不写任何业务数据；收藏 / 状态读写是二期，需站点再次授权并扩展 scope）；令牌站点侧只存哈希、票据一次性 + 120 秒、令牌 1 小时过期且可撤销。

**五条硬要求**（原始规格，站点定稿逐条核过——成立情况见括注）：

1. **密码全程不经过平台**：用户在网站自己的登录页完成登录，平台只见票据与令牌。（站点明确「你们后端不可见」）
2. **票据一次性、短寿命**：120 秒，过期作废，用一次即失效。（站点采纳）
3. **令牌可撤销**：平台下次调用即失效。（站点提供双形态：管理员应急吊销 + **self-revoke 自助吊销**。2026-10-24 负责人拍板**启用 self-revoke**（§7.9）：站点二次回复主动开放且明确不暴露终端用户可见的站内 UI、端点由站点掌控，触发方是平台后端（用户在我们 App 内点「断开与网站的连接」时）——这是对「终端用户不做自助撤销入口」拍板的增强而非违背（入口 UI 本来就是客户端自己的，且站点零额外负担）。用户侧控制三条：① 客户端内退出登录 = 平台**即时本地解绑**；② App 内「断开与网站的连接」= self-revoke **远程吊销**；③ 联系站点管理员应急吊销。详见 §4.1 第 3 点）
4. **`external_user_id` 稳定不变**：账号映射与收藏迁移的前提。（站点明确 = 站点用户主键，稳定不变）
5. **只给身份，不给业务写权限**：起步范围 = 用户资料；收藏 / 状态的读写是二期（C4）。（站点明确 scope 固定 `identity`，二期需再次授权）

**新增第六条（站点安全考量，我们接受并闭环）**：

6. **平台后端持有 client_secret**：`client_id` 经浏览器下发、本质公开，仅靠它鉴权则票据可被冒领。secret 按铁律存环境变量、**绝不入库**（变量名建议 `OTAKU_SITE_OAUTH_CLIENT_SECRET`），联调用临时值、正式环境由站点注入。这与「密码不经过平台」是同一道防线的补齐，不矛盾。

**我们绝不向站主要的**（对齐定位 §4.2 判定依据）：用户密码、站点的服务 / 管理员凭据、登录后内容的抓取授权、任何业务数据的写权限。

## 3. 授权流程（定稿态，无密码过平台、无用户同意页）

```text
① 客户端点「用网站账号登录」
② 系统浏览器打开 GET /oauth/authorize?client_id&redirect_uri&state
   （未登录先走站点登录页——用户在此输入密码，只交给网站）
③ 登录成功后站点自动回跳 redirect_uri?ticket=<票据>&state=<原值>
   （站点单方面授权，无「是否授权」中间页——站点产品决定）
④ 客户端校验 state、把票据交给平台后端
⑤ 平台后端调 POST /api/auth/token（带 client_id + client_secret）兑换令牌，与平台账号绑定
⑥ 用户资料走 GET /api/me；令牌 1 小时过期，后端在过期前静默重新走 ②–⑤ 续期（站点已确认 `authorize` 对已登录用户**幂等**，每次直接签新票据回跳；重授权成本=一次无交互浏览器跳转）
```

密码只出现在第 ② 步的网站页面上。客户端与平台**从头到尾见不到密码**——这正是定位 §4.2「允许」与「禁止」的分界线。
**redirect_uri 按站配置**（品牌资源按站区分原则的延伸）：建议形态 = 移动端自定义 scheme `com.otaku.app:/oauth2redirect` + 桌面端 loopback `http://127.0.0.1:<port>/callback`（RFC 8252 原生 App 实践），具体值由客户端模块最终定并报站点加白名单。

>

### 4.1 站点定稿与原始规格的三点差异：评估与答复

站点回复（2026-10-24）三点调整，均为安全考量、不影响集成体验。逐点评估：

**第 1 点：令牌端点增加 client_secret —— 接受，且闭环到我们的密钥纪律。**
站点理由成立：`client_id` 经浏览器下发本质公开，仅靠它鉴权则票据可被冒领。这正是我们 §7.1 挂起的问题，站点从安全侧替我们答了。落实：secret 存环境变量、绝不入库（铁律）；联调临时值由站点给，正式环境站点注入。

**第 2 点：不做用户同意页（站点单方面授权，用户无感知） —— 接受，体验反而更好。**
红线禁的是「代收密码 / 持服务或管理员凭据 / 代用户爬取」，站点方案三条均不犯；密码仍只在站点登录页。用户少一次点击，符合「老用户丝滑使用网站账号」的目标。
**负责人拍板（2026-10-24）**：授权形态由站点决定；**终端用户不是我们的客户，是网站的客户——网站观点大于用户观点**（同意页做不做、隐私政策怎么写、撤销入口给不给，都由站点决定），**但这不是用户不重要**：我们服务网站的本质就是服务它的用户；站点优先是决定权排序，不是重要性排序。定位 §4.1 / §4.2 与契约 §4.8 已按此口径修订（见 PR #141）。
另有一句供站点自行决定、我们不强制的建议：站点可在登录页脚注或隐私政策里提及「本站账号可用于本站官方 App」——用户知情对站点是资产不是负担，但是否写、怎么写是站点的产品决定。

**第 3 点：撤销仅站点管理员侧可用，不给终端用户入口 —— 接受；站点二次回复又主动开放了 self-revoke。**
「站点可随时吊销」成立（应急能力保留，这恰是泄漏场景最需要的形态）。
**负责人拍板（2026-10-24）**：「终端用户不是我们的客户，是网站的客户，只是网站观点大于用户观点，不是用户不重要」——撤销入口归站点管理符合该排序；**终端用户侧不做自助撤销入口**（self-revoke 亦不向站点提——不为终端用户侧撤销能力给站点增加开发负担）。
**站点二次回复（2026-10-24）主动开放 self-revoke**：持有效 Bearer 的一方（平台后端，用户在 App 内点「断开与网站的连接」时触发）可撤销该持有者名下、同一 client 的全部未吊销令牌；**不暴露任何终端用户可见的站内 UI，端点由站点掌控**。站点同时明确「你们不调用它，按本地解绑处理即可，二者不冲突」。
**评估**：这是对拍板的**增强而非违背**——「不做自助撤销入口」当时的顾虑是「不给站点增加开发负担」；站点主动提供且零 UI 负担，顾虑消失。且入口 UI（App 内「断开与网站的连接」）本来就是客户端自己的。**负责人拍板启用（2026-10-24，§7.9）**——用户控制手段三条：① App 内退出登录 = 平台即时本地解绑；② App 内「断开与网站的连接」= self-revoke 远程吊销（持当前 Bearer 调 `POST /api/auth/revoke`，撤销该持有者名下同 client 全部未吊销令牌）；③ 联系站点管理员应急吊销。

## 5. 预案：站点没有授权端点怎么办（四级阶梯）

| 级 | 情形 | 站点侧 | 我们侧 | 用户体验 | 升级条件 |
|---|---|---|---|---|---|
| **A** | 站点可开发（**首选**，**首站已验证：已开口→拿到定稿契约**） | 实现 §2 契约 | 提供规格 + 联调；账号绑定 + 收藏迁移 | 老用户直接用网站账号；收藏可双向（二期） | — |
| **B** | 站点已有标准 OAuth2 / OIDC | 确认授权范围与撤销策略 | 适配标准授权码流程（契约 §4.8 优先级） | 同上 | 站点换框架 / 换方案时重评 |
| **C** | 短期做不了 / 不愿做 | 无 | **平台账号过渡**（现状）+ 按 §6 预留迁移路径 | 平台临时账号；客户端**明示**「注册 / 登录也可回网站完成」 | 站点排期变化即重评 |
| **D** | 明确不做 | 无 | 客户端定位为**浏览增强**：身份类操作（登录 / 注册 / 改密 / 注销）全部回原页 | 只读体验完整；个人数据不同步，**如实说明**，不包装 | 站点态度变化即重评 |

**三条共性规则**（写进入接清单，每站必走）：

1. **接入启动时必问**：「有没有授权端点？没有的话能否开发？」——问的时机是接入开始时，不是用户投诉时；
2. **齐平原则兜底**：登录 / 注册是网站**有的**能力，客户端暂时做不到就明确写「请回网站完成」（定位边界 5：做不到的就明说，不包装）；
3. **邀请码是站点规则，我们不绕过**：新用户只能从网站注册——客户端引导回原页，不自建注册体系。

## 8. 不做什么

- 不代收密码转发、不做 WebView 内嵌登录（均已判定不可行）；
- 不在授权端点到位前实现身份打通（定位 §6.1：先做好准备不实现）；
- 不因等授权端点阻塞其他轨道（W1.2 离线、档期、资讯等已在合并队列推进）；
- 不向站主承诺我们侧的周期与报价（商务口径 `[待定]`，见定位 §6.7）；
- 不自建注册体系绕过邀请码（站点规则，齐平原则）；
- 不替站点做用户告知的产品决定（同意页做不做、隐私政策怎么写是站点的事）——最多建议，不干预。
