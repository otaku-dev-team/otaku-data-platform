## 0. 一句话

让「网站自己的账号」在客户端里直接可用，**唯一钥匙是站主开放授权端点**。首站现在没有——
本文说清三件事：**我们要的最小集是什么、怎么跟站主开口、站点给不了时的分级预案**。

## 1. 现状事实（2026-10-24 只读探测，非推测）

| 事实 | 内容 |
|---|---|
| 网站**有**完整账号体系 | `/login` `/register`（邀请码）`/logout` `/me` `/contents/{id}/favorite` `/contents/{id}/status` `/me/favorites/*` `/me/history/*` `/me/persona/*` |
| 但**全是页面端点** | 网页表单 + cookie session，**无 JSON API、无任何 OAuth / token 签发端点** |
| 还有两个产品相关限制 | 注册要**邀请码**；登录态是 cookie，App 拿不到也不该拿 |

**结论**：定位定的目标状态（客户端直接用网站账号）**现阶段技术上做不到**；平台账号是按定位 §4.1 定位的**过渡方案**，不是终态。本文要解决的，就是把「做不到」变成「站点给一个小接口就能做到」。

## 2. 我们要什么：最小集 = 一次性票据授权

不要求站点做完整的 OAuth2 服务。最小实现是**两个端点 + 一张令牌表**：

| # | 端点（站点侧新增） | 调用方 | 入参 | 出参 |
|---|---|---|---|---|
| 1 | `POST /api/auth/ticket` | 站点页面（用户已登录的浏览器会话） | `client_id`（平台接入应用标识） | `{ "ticket": "<一次性票据>", "expires_in": 120 }` |
| 2 | `POST /api/auth/token` | **平台后端**（服务端到服务端） | `ticket`、`client_id` | `{ "access_token": "<可撤销令牌>", "expires_in": 3600, "user": { "external_user_id": "<稳定不变的用户标识>", "nickname": "…" } }` |
| 3 | `GET /api/me` | 平台后端 | Header: `Authorization: Bearer <access_token>` | 用户资料（含 `external_user_id`） |
| 4 | `POST /api/auth/revoke` | 站点侧 / 平台后端 | `access_token` 或 `external_user_id` | 撤销结果 |

**五条硬要求**（缺一条就不成立，不是建议）：

1. **密码全程不经过平台**：用户在网站自己的登录页完成登录，平台只见票据与令牌；
2. **票据一次性、短寿命**（建议 120 秒，过期作废，用一次即失效）；
3. **令牌可撤销**：用户在站点侧可随时吊销，平台下次调用即失效；
4. **`external_user_id` 稳定不变**：这是账号映射与收藏迁移的前提（改一次，迁移全部返工）；
5. **只给身份，不给业务写权限**：起步范围 = 用户资料；收藏 / 状态的读写是二期（C4），不与身份捆绑。

**我们绝不向站主要的**（对齐定位 §4.2 判定依据）：用户密码、站点的服务 / 管理员凭据、登录后内容的抓取授权、任何业务数据的写权限。

## 3. 授权流程（六步，无密码过平台）

```text
① 客户端点「用网站账号登录」
② 系统浏览器打开网站登录页（用户在此输入密码——只交给网站）
③ 登录成功后，页面出现「授权并返回 App」→ 调 POST /api/auth/ticket 拿到一次性票据
④ 页面跳转 otakuapp://auth?ticket=<票据>（自定义 scheme，按站配置）回到客户端
⑤ 客户端把票据交给平台后端
⑥ 平台后端调 POST /api/auth/token 兑换令牌，与平台账号绑定；用户资料走 GET /api/me
```

密码只出现在第 ② 步的网站页面上。客户端与平台**从头到尾见不到密码**——这正是定位 §4.2「允许」与「禁止」的分界线。

## 4. 怎么和站主说（沟通稿，可直接发）

> **关于「让 App 用户直接用你网站的账号」——需要你开放一个小接口**
>
> 你的 App 现在已经能让用户浏览内容、收藏、追番。接下来最影响体验的一件事是登录：
> 现在 App 用的是平台临时账号，你的老用户进来要**再注册一个号、再记一个密码**——这不合理，
> 你的用户本来就是你的用户。
>
> **我们想做的**：让 App 的登录直接走你网站的账号。用户点「用网站账号登录」，
> 跳到你现在的登录页，输你的密码（只给你的网站），登录后点一下「授权并返回 App」就好了。
> **密码不经过我们，我们永远看不到。**
>
> **需要你做的**：在网站上加两个小接口（签发一次性票据、票据换令牌）和一张令牌表。
> 接口规格我们写好了（附件），可以按你现在的技术栈直接实现；如果你愿意，
> 我们也可以提供一份参考实现供你的开发评审后合并。
>
> **我们不需要的**：你的用户密码、网站的管理员权限、任何写你业务数据的权限。
> 用户在你网站里随时可以吊销授权。
>
> **你得到的**：老用户零门槛进入 App（不再有第二个账号）；收藏、观看状态以后可以和你网站双向一致（二期，同样要你授权）。
> 新用户仍然从你网站注册（你现在是邀请码，这个不变）。
>
> 接口上线后我们联调，**你这边没有长期负担**——不增加你的服务器压力（联调用量极小），
> 也不需要你之后维护什么。

**给站点开发的规格**：直接引用 §2 的表与五条硬要求。若站点已有标准 OAuth2 / OIDC（用成熟 CMS / 框架自带的），优先走标准授权码流程——我们适配，规格另议（预案 B）。

## 5. 预案：站点没有授权端点怎么办（四级阶梯）

| 级 | 情形 | 站点侧 | 我们侧 | 用户体验 | 升级条件 |
|---|---|---|---|---|---|
| **A** | 站点可开发（**首选**） | 实现 §2 最小集 | 提供规格 + 可选参考实现；联调；账号绑定 + 收藏迁移 | 老用户直接用网站账号；收藏可双向（二期） | — |
| **B** | 站点已有标准 OAuth2 / OIDC | 确认授权范围与撤销策略 | 适配标准授权码流程（契约 §4.8 优先级） | 同上 | 站点换框架 / 换方案时重评 |
| **C** | 短期做不了 / 不愿做 | 无 | **平台账号过渡**（现状）+ 按 §6 预留迁移路径 | 平台临时账号；客户端**明示**「注册 / 登录也可回网站完成」 | 站点排期变化即重评 |
| **D** | 明确不做 | 无 | 客户端定位为**浏览增强**：身份类操作（登录 / 注册 / 改密 / 注销）全部回原页 | 只读体验完整；个人数据不同步，**如实说明**，不包装 | 站点态度变化即重评 |

**三条共性规则**（写进入接清单，每站必走）：

1. **接入启动时必问**：「有没有授权端点？没有的话能否开发？」——问的时机是接入开始时，不是用户投诉时；
2. **齐平原则兜底**：登录 / 注册是网站**有的**能力，客户端暂时做不到就明确写「请回网站完成」（定位边界 5：做不到的就明说，不包装）；
3. **邀请码是站点规则，我们不绕过**：新用户只能从网站注册——客户端引导回原页，不自建注册体系。

## 7. 待确认（负责人）

1. **`client_secret` 要不要**：起步建议**不要**（站点实现成本最低；票据一次性 + 短 TTL，滥用窗口极小）。要更严再议。
2. **取值**：票据 TTL 建议 120 秒；令牌有效期由站点定（建议 1 小时级 + 刷新机制二期）。
3. **授权范围**：起步只要身份（用户资料）；收藏 / 状态读写二期（C4），不与身份捆绑。
4. **谁去问首站站主、何时问**（C2）：本文 §4 沟通稿可直接用；**开口时机请定**。
5. **参考实现的边界**：我们替站点写参考实现，是否写入对客户的交付物清单（影响「网站侧零开发投入」的口径——注意：授权端点是定位里明确认可的「站主为身份授权做的一次性开发」，与「零开发投入」不矛盾，但对外表述要一致）。

## 8. 不做什么

- 不代收密码转发、不做 WebView 内嵌登录（均已判定不可行）；
- 不在授权端点到位前实现身份打通（定位 §6.1：先做好准备不实现）；
- 不因等授权端点阻塞其他轨道（W1.2 离线、档期、资讯等已在合并队列推进）；
- 不向站主承诺我们侧的周期与报价（商务口径 `[待定]`，见定位 §6.7）；
- 不自建注册体系绕过邀请码（站点规则，齐平原则）。
