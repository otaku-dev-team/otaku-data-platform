## 1. 环境与复现（本机，Windows）


## 2. 联调时修掉的一个环境问题（值得记）

首启动失败：Flyway 报 `Detected resolved migration not applied to database: 7`。

原因：这个 datadir 是 merge train 演练时的产物——**V8（schedule）被应用了，V7（work_tag）没有**，
Flyway 校验不过。处理：

1. 删掉 `flyway_schema_history` 里 version='8' 的行（`schedule` 表本身保留）；
2. 手动执行 `V7__work_tag_filter.sql`（幂等：`CREATE TABLE IF NOT EXISTS` + `INSERT IGNORE`，
   回填 1,451,784 行）；
3. 重启，Flyway 自行补齐 V7/V8/V9 记录。

⚠️ 教训：**库的迁移历史可能和代码不同步**（演练分支 outOfOrder 执行过）。
本地库起不来先查 `flyway_schema_history`，别急着改代码。

数据是从真后端拉下来存下的响应原文，见 §7）。

关于第 3 条「封面三态」：三态在 widget test 里**无法自然触发**——
`cached_network_image` 走 `flutter_cache_manager` 自己的 HTTP 栈，
不受 flutter_test 的 400 拦截影响，真实请求在 fake async 下不推进，
错误回调永远不来（实测挂 12 秒仍停在加载态，连非法 URL 也一样）。
所以把 `placeholder` / `errorWidget` 两个回调提成
`CoverImage.loadingFallback` / `CoverImage.errorFallback` 公开方法，
直接断言它们渲染出什么：加载中 = 纯骨架无渐变无文字；
没有封面 = 渐变 + 首字；加载失败 = 与「没有封面」同款（契约 6.3 不许破图）；
并额外断言「加载中 ≠ 没有封面」——这是三态存在的意义。

关于第 5 条「档期页」：季度切换验证了「重新拉该季度的数据、标题与季度标签都换掉、
旧条目消失」，另有一条「只有一个季度时不显示切换下拉」（孤零零的下拉箭头
会让人以为还有别的季度可看）；空 `work_id` 条目验证了「只展示、点了不跳转、
并写明『本站未收录，仅展示档期信息』」。

### 6.1 哪些必须真机（模拟器验不了的部分）

下面这些**不是没做**，是物理设备才能验的：

| 项 | 为什么模拟器不行 | 怎么验 |
|---|---|---|
| 通知**实际弹出与送达** | 模拟器上 `flutter_local_notifications` 能排程、能建通道，但通知栏的展示与点击回跳在真机通知系统上才有意义 | 真机开提醒 → 等到点 → 看通知栏 → 点进去应跳档期页 |
| **重启后闹钟重注册** | `ScheduledNotificationBootReceiver` 要 `BOOT_COMPLETED` 广播。模拟器重启慢且广播时序不稳 | 真机重启 → 打开 App → `dumpsys alarm` 应看到重排的闹钟 |
| 站点登录**完整闭环** | 需要真实站点账号（密码只在站点页面输入，客户端不碰） | 真机上用站点账号登录 → 应回到 App 并落到收藏页 |
| 系统浏览器授权的**回跳** | `site_auth_bootstrap` 走系统浏览器 → 回跳 App 的那条链路 | 真机登录后锁屏或切浏览器再回 App |
| **厂商推送通道** | 国内 Android 无 GMS，FCM 不可用；设备注册端点 #190 已在，客户端未接 | 属另一个工作流（`w1.3-notification-proposal.md`），不在本轮 |
| 息屏 / 切后台 / 内存紧张 | 模拟器不真正息屏 | 真机把 App 切后台再回，观察状态恢复 |

**判定**：Android 侧**模拟器可验的部分全部通过**；唯一的阻断项（无主导航）已修。
上面 6 项留待真机，不阻塞 W1.4 收口。

## 7. 自动化 fixture 从哪来（要重新生成时看这节）

`app-client/test/fixtures/real_*.json` 是**真后端的响应原文**，不是手写的假对象。
这样测的是「真实数据形状 → 模型解析 → 界面渲染」整条链，而不是「我认为数据长什么样」。

起好 §1 的 ①② 之后，在 `app-client/` 下执行：

```bash
B=http://127.0.0.1:8082
curl -s "$B/api/works?page_size=50"                     -o test/fixtures/real_works_default.json
curl -s "$B/api/works?sort=rating&page_size=50"          -o test/fixtures/real_works_by_rating.json
curl -s "$B/api/works?tag=zzz-not-exist-tag&page_size=5" -o test/fixtures/real_works_unknown_tag.json
curl -s "$B/api/schedule"                               -o test/fixtures/real_schedule.json

# 档期的**上一个季度**：用来验证「切季度真的换了内容」
#   （两个季度各有 60+ 条、标题完全不同，切换后旧标题必须消失）
curl -s "$B/api/schedule?season=202607"                 -o test/fixtures/real_schedule_prev_season.json

# 评分排序的「最后一条全无评分」那一页：先查总数再取末页
#   （这一页是「无评分沉底」的断言依据）
T=$(curl -s "$B/api/works?tag=游戏&page_size=1" | python -c "import sys,json;print(json.load(sys.stdin)['total'])")
curl -s "$B/api/works?tag=游戏&sort=rating&page=$(( (T+49)/50 ))&page_size=50" \
     -o test/fixtures/real_works_rating_tail.json

# 最长标题那条（库里最长 146 字符）：先由 SQL 定位 id，再取列表与详情
curl -s "$B/api/works?q=If%20Letters%20Had%20Pants&page_size=5" -o test/fixtures/real_works_long_title.json
```
