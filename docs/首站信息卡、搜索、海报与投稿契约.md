# 首站信息卡、搜索、海报与投稿契约

> 接 [`首站作品关系页契约.md`](首站作品关系页契约.md)。同样是「同事不读首站源码也能做」的规格。
> 源码出处标函数名与行号（2026-11-09 版本），我方数字是生产实测。
> 四块里两块只差小补（信息卡、搜索），两块要新表（海报名单、作品申请）。

## 一句话

信息卡实测只有 7 个键、其中 4 个能直接加列；搜索是「多路 LIKE + 三档相关度」，数据我们全有、缺的是查询；海报轮播和作品申请都要新增表，按红线走确认，我只出规格不动实现。

## 一、详情页信息卡（`content_facts`）

### 首站怎么做的

- 表 `content_facts(content_id, key, value)`，`(content_id, key)` 唯一；key ≤50 字、value ≤500 字，空值直接丢弃，**整体替换**（`crud.replace_content_facts`，`crud.py:754`）。
- 写入方是 Bangumi 信息卡解析：`STAFF_SKIP_KEYS` 那批「客观事实」只进 facts、不进职员表，其余键才当人事职位（`bangumi_meta.py:97` 的注释与三个键集）。
- **生产 38,021 行，只有 7 个键**：

  | key | 行数 |
  | --- | --- |
  | 别名 | 11,079 |
  | 官方网站 | 6,559 |
  | 放送开始 | 6,475 |
  | 放送星期 | 4,809 |
  | 播放结束 | 4,726 |
  | 企画 | 3,488 |
  | 制作 | 885 |

- 展示（`templates/detail.html:268`）：折叠区「放送信息、电视台、官网等」，**只有真有 facts 时才出这个入口**（空数据不出假入口）；末尾固定补一行「条目 ID」= `contents.id`。
- 顺序 = 写入顺序（按 id），不是字母序，也不是固定白名单序。
- 值是 URL 时：先去掉空格，把 `:/` 补成 `://`，以 `http` 开头就渲染成外链并只显示域名。

### 我们这边

- 别名已有：`work.aliases`（JSON，同源 1.1 万条）。话数已有：`work.episodes`。
- 放送星期在 `schedule` 表（`weekday` / `broadcast_time`），但只覆盖当季 1,500 条档期，不是全量。
- 缺的是：**官方网站、放送开始、播放结束、企画**（加上「制作」，但那条与我们 `work_studios` 是同一件事，别重复建）。

### 建议（改表属红线，需三人确认，我不动实现）

- 7 个键里 4 个语义固定、且都是短字符串 → **加列**比加键值表省：`work.official_url` / `broadcast_start` / `broadcast_end` / `planning`（企画）。键值表的灵活度换来每次详情多一次 JOIN + 一次排序，而实测键集两年没变。
- 键值表唯一还能留的用途是「以后来源多一个奇怪键」——真到那天再开，不提前摊开。
- 显示规则照抄首站三条：**有才出入口**、末尾「条目 ID」、URL 只显示域名且新窗口打开。
- 放送星期不给 work 加列：`schedule` 已经有，且它是按季的排播数据、不是作品属性。

## 二、搜索（`/contents?q=`）

### 首站怎么做的

两层：**查询理解**（`app/search_query.py`）+ **多路召回与排序**（`crud._content_search_stmt`，`crud.py:3076`）。

查询理解，全是确定性规则、没有模型：

- **类型词**整 token 精确匹配：动画 / 动漫 / 番剧 / 番 / 漫画 / 游戏 / 轻小说 / 小说。
- **题材词**用同义词表，`_segment_genres` 对 token 做**整段贪心切分**：切得干净才算（「治愈日常」→ 治愈 + 日常；「轻喜剧」有剩字 → 放弃，保持关键词）。宁可漏识别，不把标题拆坏。
- **年份**：1950–2049，前后不能贴数字。
- **季数**：第2季 / 第二期 / ⅱ / 2nd，只认 ≥2（「I」「1st」歧义太大）；剥完主体为空就放弃拆分，避免空关键词全表扫。
- 识别失败的 token **原样留作关键词**。最差情况等于旧版纯 LIKE——只放宽、不收紧。

召回三档（`_title_hit` / `_info_recall`）：

| 档 | 命中字段 |
| --- | --- |
| 标题组（rank 3） | `title`、`title_original`、`aliases`（JSON 解包后 LIKE） |
| 信息组（rank 2） | 题材标签名；实体名（作者 / 公司）；角色名或声优名（三路 EXISTS，任一命中） |
| 兜底（rank 1） | `summary` LIKE |

- 排序：`rank DESC` → 有效评分 DESC → id ASC。**有效评分**：评分人数 < 50 按 0 参与排序，人数为 NULL 保留原值（`rating.py:31` 的 `MIN_RATING_COUNT = 50`）。
- 用户显式点了排序（评分 / 收藏 / 最新）时，**显式排序压过相关度**。
- 季数命中要求标题类字段（title / 原名 / 别名）**任一**变体命中。

### 我们这边

- 现在只有 `title LIKE`。缺：原名、别名、标签、公司、声优、简介五路，以及相关度排序。
- 数据全都有：`work.title_original`、`work.aliases`、`tags`、`work_studios`、`work_staff` / `work_characters`。**这条不用抓数据，纯查询改造。**
- 题材同义词表我们**没有**（首站是 `tagging.GENRE_TAGS` / `GENRE_ALIASES`，一张要人维护的词表）。这是最贵的一块，建议放到最后一档。

### 建议分三步

1. 多路召回 + 三档排序（纯 SQL）。关键词短（接口已限长）时直接用 `LIKE '%kw%'`，与首站同路子。
2. 年份 / 类型 / 季数解析。都是确定性正则，能单测，收益立刻可见（「2019年 动画」这种搜法现在等于全表扫）。
3. 题材同义词、复合 token（治愈动画 / 搞笑番）。**要先有词表**，没有词表就先别做——照抄首站的词表等于抄一份别人的维护负担。

### 一个要先压的坑

`LIKE '%kw%'` 走不了索引。首站库 120MB，我们 `work` 是全量导入规模（55 万级），扫一遍的代价高一个量级。端点上线前先按最坏输入（长词、无命中）压一次，别按命中率高的样本估。

## 三、首页海报轮播（`home_posters`）

### 首站怎么做的

- 两张表：`home_posters(content_id, sort_order, source)` 存**一份全站生效名单**；`home_poster_config` 单行存模式（off / auto / manual）、频率（daily / weekly）、轮转游标、最近一次结果（`models.py:1427`）。
- 名单是**全站唯一一份**：所有访客看到同一顺序；访客在页面上左右切换是纯前端状态，不写库、不回传。
- 候选来自**最新季度的档期**（`category` 为空的季度数据）：关联到作品的必须 `type=anime` 且有本地封面；没关联上的档期条目用外链海报、跳转按标题搜索（`home_posters.list_candidates`）。
- 候选稳定序：评分降序（无评分排最后）→ 星期 → 标题。轮转 = 从游标取 `COVERFLOW_SIZE=12` 条，游标前进 `min(12, max(候选数-12, 1))`。
- 展示：一屏可见 5 张（C 位 + 左右各 2），共 12 条。
- 首页取数（`business_pages.py:162`）：**优先生效名单，名单空则回落当季实时候选**——不落库、不改配置，保证默认状态下首页不是死的。
- 默认模式是 **off**（关闭自动更新）：不跑定时、保留现有名单；auto 才按频率重算；manual 下定时任务一律不碰。
- 更新是「先生成并校验，再单事务整批替换」；失败保留旧名单，绝不把首页换成空白。定时在 `RUN_HOUR=6` 之后、60 秒内重复触发直接跳过、flock 防并发。

### 我们这边

- 没有轮播，也没有这两张表。客户端首页四块（最近浏览 / 本日新番 / 高分 / 最新资讯），没有 hero。
- 当季档期我们有：`schedule` 表带 `season_code` / `weekday` / `work_id`，候选可以**现算**。

### 建议（新表属红线）

- **先不做名单表**。候选现算就能出 12 条（第 1 步），「轮转 / 名单 / 三种模式 / 定时任务」是运营能力，等真有人要手动指定再上第二张表。首站这套里一半复杂度在运维（flock、游标、去重窗口），不是产品需要。
- 若要做名单，最小形态：一张 `home_poster(work_ref, sort_order)`，配置塞 `app_config`（我们已有这张表 + 后台），**不另开配置行表**。
- 封面必须有——首站这条是硬条件（没封面上英雄位就是一片空白）。我们的封面是服务端回源 + 磁盘缓存，候选过滤按「封面可解析」判，不是按 `cover_source_url` 非空判。
- 客户端：hero coverflow 一屏 5 张、12 条数据、点击进详情；切换是前端状态，不请求服务端。

## 四、投稿与纠错（`/submit`、`/contents/{id}/edit`）

### 首站怎么做的

- 两个入口：`/submit` 新增作品、`/contents/{id}/edit` 修改作品。**都要登录**，未登录 303 跳登录页（`submission_pages.py` 路由级 `require_login_page`）。
- 提交**只写 `content_submissions`，不动 `contents`**；管理员审核通过才落业务数据。
- 表单字段：`title` / `type` / `summary` / `year` / `media` / `episodes` / `source_material`。
- **评分不可提交**——`contents.rating` 只由外部数据源维护；表里那个 `rating` 字段只是「提交时目标作品的当前评分」快照，给审核页对照原值用。
- 枚举：media = TV / 剧场版 / OVA / Web / 游戏 / 小说 / 漫画；source_material = 漫画原作 / 小说原作 / 游戏原作 / 原创；year 1900–2100；episodes ≤10000。
- 修改申请里**留空 = 不改动原值**：审核通过时只覆盖非 NULL 的列，只改简介的申请不会顺手把年份清空。
- 新增申请撞上同名作品 → 拒绝并引导「请去那部作品页申请修改」。
- 状态 pending / approved / rejected，只存审核人、时间、驳回说明、通过后实际写入的作品 id；**只有 pending 能审**，重复审核报错，防止写两次。
- 结果用 PRG：成功 303 跳个人空间「作品申请」标签页。

### 我们这边

- 我们的 UGC 只有评论 / 举报 / 审核（`ugc_comment` / `ugc_report` / `ugc_review`），**没有作品申请**。
- 这是四块里最贵的一块：新表 + 提交端点 + 后台审核 + 客户端表单，还要接一条「审核通过后写 `work`」的新写路径。

### 真正的风险不在表单，在写路径

`work` 表到现在**只有导入服务一个写入方**（"只有 Java 写入"写在 V1 建表注释里）。加一条「用户申请通过后写 work」等于开第二个写入方，必须先把这几件事定下来，否则会和导入打架：

1. `work_id` 怎么生成——导入侧有自己的生成规则，投稿不能自己编，要复用同一个生成器。
2. `site_listed` 给多少——用户新建的作品默认算不算「已收录」，直接决定它出现在哪些列表里。
3. 与导入的覆盖关系——下一轮导入遇到同名 / 同 source_id 的作品，是覆盖用户提交的内容，还是跳过。
4. 封面——用户提交没有封面，详情页需要占位而不是 404。

这四条定不下来，表单做得再顺手也会把库搅乱。所以这块**只出规格、不动实现**，属于「跨模块数据结构变更」，走三人确认。

## 五、验收（不读源码也能验）

| 打开 | 期望 |
| --- | --- |
| 有官网 / 放送信息的作品 | 详情页出现「放送信息、电视台、官网等」折叠区，末尾一行「条目 ID」 |
| 没有任何 facts 的作品 | **不出现**那个折叠入口，也没有空的「条目 ID」行 |
| 官网是 URL | 显示成域名外链，新窗口打开；不是把整条 URL 糊在正文里 |
| 搜「2019年 动画」 | 落到年份 + 类型筛选，不是把整串当关键词扫全表 |
| 搜某声优名 | 召回他参演的作品，且排在「简介里恰好提到这名字」的前面 |
| 搜「游戏王」 | 不被拆成「游戏」类型筛选，仍按标题命中 |
| 搜一个长词、零命中 | 有响应时间上界（压测值），不超时 |
| 首页 | 有 12 条海报、一屏可见 5 张、点进去是详情页；名单为空时首页不是空白 |
| 未登录点「申请修改」 | 跳登录，登录后回到原页面 |
| 提交后 | 作品内容**没有变**，只多一条待审核记录 |
| 只改了简介提交并审核通过 | 年份 / 媒介 / 话数原值保留，没被清空 |
