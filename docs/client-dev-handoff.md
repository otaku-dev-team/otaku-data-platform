## 3. 参数速查

列表接口 `GET /api/works`：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `q` | 关键词 | 标题搜索。**注意参数名是 `q`**，不是 `keyword` |
| `type` | `anime` / `comic` / `game` / `novel` | 作品类型。**是 `comic` 不是 `manga`**，传错返回 400 |
| `tag` | 标签名 | 单标签精确匹配，**已废弃**，新代码别用 |
| `tags` | 逗号分隔，最多 10 个 | 多标签 **AND**。与 `tag` 同传返回 400 |
| `sort` | `id` / `rating` / `year` | 默认 `id`；非法值返回 400 |
| `min_rating` | 0–10 | 评分下限；无评分一律排除；越界返回 400 |
| `year` | 1900–2100 | **年份等值筛选**（不是排序）；无年份的会被排除 |
| `page` | 从 **1** 开始 | 不是 0-based |
| `page_size` | 默认 20，上限 50 | 超 50 静默截到 50；传 0 回落 20 |

响应为 `{page, page_size, total, total_pages, items}`。

**所有 JSON 字段统一 snake_case**（`work_id`、`cover_url`、`release_year`、`basis_tags`），
Dart 侧别按 camelCase 取。

实测样例：`q=鲁路修` → 10 条精确命中（23:50 时是 6 条、00:02 时 7 条，同一关键词 15 分钟涨了 4 条）；
`type=game` → 6,527 条（同样在涨，别写死）。

## 4. 四个必须先知道的事实

**① 默认排序是最老优先，不是最热。** `sort` 缺省值为 `id ASC`，即按入库顺序升序。
后果是首页第一屏永远是**最早导入的那批**，看上去像"数据很旧很难看"，其实不是 bug。
首页/列表页请显式传 `sort=rating` 或 `sort=year`。

**② 封面现在基本拿不到图。** 三件事叠加：`cover_url` 本身只有约 **3.5%** 非空
（随机 600 条抽样；且分区间极不均匀，前段约 19%、中段 0%）、回填仍在进行、
封面回源白名单尚未重启生效——**即使 `cover_url` 非空，`/api/covers/{work_id}` 实测仍 404**。
后两个原因都在后端侧处理，客户端按"无图占位"实现即可——
**这正是最终形态需要的三态兜底，不是临时方案**。

**③ `total` 会持续变化。** 导入进行中。2026-10-28 00:05 实测 **45,174 条**，
速率约 **389 条/分钟**（60 秒窗口实增）；全量目标 557,847，还差约 51 万。
不要写死条数，不要对"第 N 页第 M 条是某作品"做断言——翻页内容会随数据增长漂移。
连搜索命中数都会变：`q=鲁路修` 23:50 是 6 条，00:05 已是 10 条。

**④ 元数据有缺口，属上游数据本身缺失，且新导入的行更缺。** 随机 600 条抽样：
title 100%、release_year 97.3%、tags 78.5%、**rating 74.7%**、封面 3.5%。
但完整率**随入库批次骤降**：前段（老批次，已回填）rating 约 98%、tags 约 99%；
尾段（最新导入）rating 约 44%、tags 约 41%。所以别把某个百分比当固定前提去设计空态
（旧版写的「rating 34–36%」是当时的单点值，现已不成立）。
`sort=rating` 的可见效果是：评分恰为 10.0 的有 **241 条**，前面整整 50 条全是 10.0，
往下翻才见 9.x——不是排序坏了。

## 9. 社区接口（评论 / 点评，2026-10-30 全量上线）

作品页底部两个 tab，**两套接口、两张表，不要互相转换**：

| | 评论 | 点评 |
|---|---|---|
| 语义 | 讨论流，可多条、可回复 | 对作品的评价，一人一条 |
| 打分 | 无 | 1–10，可只打分或只写文字 |
| 端点 | `/api/works/{id}/comments` | `/api/works/{id}/reviews` |
| 未开启社区 | 整块不渲染，跳来源站原页 | 同左 |

进页面先查 `GET /api/site/features`：`ugc_enabled=false` 就跳原页，不要渲染空评论区。

### 9.1 评论：一次请求拿到「楼层 + 前 3 条回复」

`GET /api/works/{work_id}/comments` 的 `items` 是**顶层评论**：

- `reply_count`：该楼层已发布的回复总数；
- `replies`：最早 3 条预览（对话顺序）；
- `total` **只算顶层**——别拿它当「评论 + 回复」的总数。

渲染：楼层下直接铺 `replies`；`reply_count > 3` 时显示「查看全部 N 条回复」，
点开调 `GET /api/works/{work_id}/comments/{comment_id}/replies`（分页，最早在前）。

### 9.2 发评论 / 回复

`POST /api/me/comments`，body `{work_id, body, parent_id?}`。

`parent_id` 为空 = 顶层评论；有值 = 回复那条**顶层评论**。只支持一层，
回复一条回复会 `400`（这不是 bug，是设计：两层足够「评论 + 追评」）。

### 9.3 编辑 / 删除

- `PATCH /api/me/comments/{id}` `{body}`：只有正文可改。**响应里顶层评论的 `replies` 是空数组**——
  请只替换这一条本身，不要整条覆盖成「零回复」；
- 先审后发的站点，编辑后会回到 `pending`（重新审核），提示「已提交，审核后显示」；
- `DELETE /api/me/comments/{id}` 幂等 `204`；删顶层会**连带隐藏该楼层的回复**（楼层撤回语义，
  行仍保留，站主导出能看到）。

### 9.4 点评：三个数字别混用

`GET /api/works/{work_id}/reviews/summary`：

| 字段 | 含义 | 用法 |
|---|---|---|
| `total` | 点评条数（**含只写文字不打分的**） | 「N 人点评」 |
| `rated` | 其中打了分的 | 「N 人打分」 |
| `average` | 只对打了分的求均值，**可为 null** | 没有打分时显示「暂无评分」，**不要显示 0** |

`distribution` 只含有数据的分数（不补 0），可直接画柱子。

**与作品自带的 `main_rating`（来源站聚合分）是两套口径**：并列展示、各自标注来源，
不要相加、平均或互相覆盖。

发表：`POST /api/me/reviews` `{work_id, rating?, body?}`，两者至少一项。
重复提交 → **`409 REVIEW_EXISTS`**，引导去编辑原点评，不要弹「失败」。

编辑：`PATCH /api/me/reviews/{id}`，**省略的字段沿用原值**——只改评分不会清空正文。

### 9.5 错误码速查

| HTTP | code | 客户端该做什么 |
|---|---|---|
| 400 | `CONTENT_REJECTED` | 机器审核判为不合规（**未落库**）：提示「修改后再发」，把 `message` 里的理由带上；改完可直接重发，不用刷新列表 |
| 403 | `FORBIDDEN` | 「只能操作自己的内容」或「本站未开启社区」 |
| 404 | `COMMENT_NOT_FOUND` / `REVIEW_NOT_FOUND` | 内容已删或不存在，刷新列表 |
| 409 | `REVIEW_EXISTS` | 引导编辑原点评 |
| 429 | `RATE_LIMITED` | 「发言太快」，按 `Retry-After` 提示 |

### 9.6 两个容易踩的

- `author` 对**已注销账号**显示「已注销用户」——不要用它做用户跳转；
- `status` 只在你刚发的那条上可能是 `pending`（先审后发）；公开列表里永远是 `published`。

### 9.7 真实响应样张（别照着契约猜形状）

[`docs/samples/ugc-samples.json`](samples/ugc-samples.json) 是**线上真请求**抓下来的 7 份原样响应
（楼层列表、回复分页、发回复、编辑、点评列表/创建/概览），抓完已清库。写解析代码时对着它看，
比对着 YAML 猜快得多——尤其是「哪个字段在哪一层」这类事。

同一份文件末尾有 `_gotchas`，就是上面 9.1–9.6 里那几条容易被当成 bug 的行为，一句话一条。

## 10. 站点账号：`identity_source` 与「断开与网站的连接」（2026-11-07 上线）

W1 登录页给后端的三条输入已全部回齐（细节见 `w1-login-dual-entry.md` §5）。

**① `User.identity_source`**（`/api/auth/me`、`/api/auth/login`、`/api/auth/site-login` 都有）

```json
{ "user_id": "U-...", "username": "site_12345", "display_name": null,
  "created_at": "2026-11-07T09:00:00Z", "identity_source": "otaku_site" }
```

- `null` = 平台账号；`otaku_site` = 站点授权建的账号。**同一个账号三处返回值一致**，
  不随「这次是哪种登录方式」变化。
- `AccountUser` 加一个可空字符串即可；账号菜单据此显示身份来源小字、并决定要不要显示「断开与网站的连接」。

**② `POST /api/auth/site-unlink`**（无请求体）

| 结果 | 含义 |
|---|---|
| `204` | 已断开。**当前会话也被撤销**——立刻清本地令牌回登录页，不要再打 `/me` |
| `409 NOT_SITE_LINKED` | 当前账号是平台账号，没有站点连接可断（入口本来就不该显示） |
| `401` | 没登录 / 令牌已失效（重复点第二次就会是它，属正常） |

断开后账号与收藏/评论/浏览**都还在**；同一个站点身份重新授权会**接回原账号**（`user_id` 不变）。

**③ 文案别写错**：后端**不代理站点吊销**（只存站点令牌的 SHA-256，调不动站点 `revoke`）。
站点那边最长 1 小时自然过期。所以写「已断开」或「站点授权将在 1 小时内自动失效」，
**不要写「已立即吊销」**——那是不成立的承诺。

**④ 会话寿命**：平台会话仍是 30 天、不滑动，与站点令牌（1 小时）**解耦**。
客户端不需要判断站点令牌临期，继续只做「401 → 静默重走授权一次 → 再失败引导重新登录」。

## 11. 详情页「系列作品」：`GET /api/works/{work_id}/series`（2026-11-09 形状有变，#557）

```json
{
  "series_key": "4281",
  "series_name": "物语系列",
  "items": [
    { "relation": "same_series", "work": { "work_id": "...", "title": "化物语", "release_year": 2009, "...": "同 WorkSummary 8 字段" } }
  ]
}
```

> ⚠️ **形状变更（2026-11-09，#557）**：`items` 的每一项从「裸 WorkSummary」变成
> `{ relation, work }`。变更理由是每张卡都要显示「前作 / 续作 / 衍生作 / 同系列」，
> 而标签不属于作品卡本身。**此前客户端没有任何地方调用这个接口**（`grep -ri series lib/` 零命中），
> 所以没有兼容负担；已经写了模型的，只需在解析时多包一层 `work`。

- **没有系列不是错误**：`series_key` / `series_name` 都是 `null`、`items` 为 `[]`，HTTP 仍是 200。
  按 `items.isEmpty()` 隐藏整个区块，不要按 404 处理；
- **`series_name` 可能为 `null`**（作品先导入、系列行后到）。这时**隐藏标题**，
  别拿 `series_key` 当名字显示——那是来源站内部 id；
- `relation` 取值固定 4 个：`prequel` 前作 / `sequel` 续作 / `spin_off` 衍生作 /
  `same_series` 同系列。**中文文案由端上映射**，不要按标题猜。
  目前**只会拿到 `same_series`**：前作/续作/衍生作的关系数据还没落库
  （数据集 schema 有 `work_relations`，publisher 不写）。这不是占位假值——它们确实同系列；
  数据落地后只会多出另外三个取值，形状不变，可以先按「这 4 个值都认识」写；
- `items` **包含当前作品**（系列是完整清单，客户端自己高亮/置灰当前项）；
- 排序是**档位 → 年代升序**（前作/续作 → 衍生作 → 同系列，同档内年份升序、年份未知最后），
  不是评分——观看顺序语义；
- 已下架、未收录、成人作品不会出现在 `items` 里；
- 作品本身不存在 → 404 `WORK_NOT_FOUND`（与详情一致）。

数据来源只有数据集通道，所以**新导入、还没跑过数据集同步的作品会没有系列**，这是预期行为。

## 12. 画像九维：`GET /api/me/profile` 的 `dimensions`（2026-11-08 上线）

```json
"dimensions": {
  "tag_focus": 50.0, "exploration": 50.0, "mainstream": 63.2, "pop_spread": 41.7,
  "quality": 72.7, "era_span": 38.4, "fresh": 25.0, "emotion": 55.6, "completion": 66.7
}
```

- **九个键恒存在**，0–100，**50 = 中性/数据不足**。缺失维度给 50，**不是 0**——
  0 画在雷达上是个凹角，会被读成「这方面很弱」；
- 键序固定为上面这个顺序（`tag_focus` → `completion`），雷达轴直接按它画；
- 空画像（新用户）九个都是 50，配合 `sample_size = 0` 一起判断要不要显示「画像还在形成」；
- ⚠️ **`tag_focus` / `exploration` 已决定冻结在 50**（2026-11-08）：这两维要「哪些标签算题材」的
  白名单，仓库和源库都没有分类，且不打算用「全标签」替代（语义会漂）。**这不是故障，别当 bug 报**；
  两轴置灰或隐藏，画出来会让用户以为「你没有口味」；
- **`era_span` / `pop_spread` 的数值会偏顶格**（多数人到 95+）：参考值是按早期样本定的，
  要等真实收藏数据才重标。先照常画，别在文案里强调「你超过了 90% 的人」这类结论；
- **`emotion` 的 50 是「和全站口味一样」，不是「一半治愈一半致郁」**。全站治愈标签本来就比致郁
  常见（约 76:24），所以随手收藏的人落在 50；90 以上是明显偏治愈、20 以下是明显偏致郁。
  文案别写「均衡」——它更像「不挑」；
- `exploration` 的 **10 是真的「只碰一个题材」**（不是缺数据）；缺数据是 50；
  `completion` 的 50 则是「全看过」与「没数据」同值，**必须结合 `sample_size` 一起读**，别单看这一个数；
- 旧字段（`type_weights` / `tag_weights` / `rating_tendency` / `recent_active` / `sample_size`）
  全部保留，`#498` 切到 `dimensions` 时不必一次性删掉端上六轴派生。

## 13. 收藏第 4 态 `dropped`（抛弃，2026-11-08 上线，#496）

```json
PUT /api/me/collections/{work_id}   { "status": "dropped" }
```

- **枚举从 3 个变 4 个**：`want` / `watching` / `watched` / `dropped`。旧的三个取值语义**完全不变**，
  所以现有 UI 不改也能跑；新增的那一档要自己补入口。
- **`dropped` 与「取消收藏」不是一回事**：取消收藏是 `DELETE`（删行，负信号消失）；
  抛弃是保留一条「我看过、但不喜欢」的记录，画像会拿它做**负权重**。
  产品文案建议写「抛弃 / 不感兴趣」，别写「删除」。
- **可以随时改回来**：`PATCH` 到 `want`/`watching`/`watched` 都行，不会被锁死（漏斗种子也不锁）。
  这正是「用过才知道不喜欢」的正常路径。
- **不进画像分母**：被抛弃的作品不算进九维（口味版图），但会让对应题材的权重变负。
  所以「抛弃越多，画像越准」，不是「抛弃越多，画像越空」。
- **站主后台**也加了 `dropped`：用户详情里的收藏聚合多一个 `collections.dropped` 字段
  （与 `none` 分开统计——否则「被否掉」会被算成「没分类」）。
- 漏斗（#492）三态映射到我们这边是：看过 → `watched`、在看 → `watching`、抛弃 → `dropped`。
  （#492 原文写的是网站侧的 `seen/want/drop`，落地时按这张表换。）

## 14. 查「我的点评」：`GET /api/me/reviews?work_id=...`（2026-11-08，#531）

```json
GET /api/me/reviews?work_id=W-xxx
→ { "page": 1, "page_size": 1, "total": 1, "total_pages": 1,
    "items": [ { "review_id": "42", "status": "published", "rating": 8, "body": "…" } ] }
```

- **没点评过 = `200` + `items: []`**，不是 404。别写「找不到」的错态；
- 分页参数不用传（恒 0 或 1 条），**信封形状与公开列表一致**，可以复用同一个解析；
- **`status` 要区分着用**：`published` 正常显示；`pending` 显示「审核中」；`hidden` 显示
  「已被站点隐藏」；`deleted` 显示「已删除」。**不要一律当成没写过**——否则用户一点「写点评」
  就会撞 `409 REVIEW_EXISTS`，而他又改不了（那条已删）；
- 拿到 `review_id` 才能调 `PATCH` / `DELETE /api/me/reviews/{review_id}`，这正是本端点存在的理由：
  原先只能拉公开列表按作者名比对，**点评超过一页时自己的那条不在第一页**，会误判成没写过；
- 作品不存在 → `404`；漏传 `work_id` → `400`。

> ⚠️ **已知限制（还没修）**：点评软删后**不能重新发表**——`existsByUserAndWork` 把 `deleted`
> 也算「已存在」，`POST` 会返回 `409`，而 `PATCH` 又只对 `published`/`pending` 生效。
> 也就是说「删了就想重写」目前是死路。已在 #531 记录，等定「复活还是硬删」再改。
> 在那之前建议客户端：`status = deleted` 时不要给「写点评」入口，只显示「你已删除这条点评」。

## 15. 漏斗写入：`source=quiz`（2026-11-08，#506）

冷启动漏斗（#492）把标注答案写进收藏时，**多传一个 `source`**：

```json
PUT /api/me/collections/{work_id}    { "status": "watched", "source": "quiz" }
PATCH /api/me/collections/{work_id}  { "status": "dropped", "source": "quiz" }
```

- **省略 `source` = `user`**，老客户端一行都不用改；
- **种子盖不动用户操作**：同一作品上已经有 `source=user` 的行时，`quiz` 的写入**被忽略**，
  返回当前状态、**不报错**。批量写不该为一条种子变成「一半成功」——客户端按返回的
  `status` 显示即可，它就是最终值；
- **反向永远允许**：用户改一条种子（不传 `source` 或传 `user`），那条就变成用户操作，
  之后重跑漏斗再也盖不动它。这正是产品要的「真实操作优先」；
- 漏斗**不需要新端点**：就用现有收藏接口，一个作品一条，`status` 三态映射见 §13
  （看过 → `watched`、在看 → `watching`、抛弃 → `dropped`）。

> 为什么要这个标记：没有它，用户把种子改成「看过」之后，下次重跑漏斗会再盖回种子值，
  而且事后分不清「这个人真看过 100 部」还是「他答了一套题」。

## 16. 首页 hero 海报：`GET /api/home/posters`（2026-11-09，#561）

```json
GET /api/home/posters
→ { "items": [ { …WorkSummary }, … ] }
```

- **最多 12 条，不翻页**；`items` 顺序**就是**展示顺序，客户端按顺序铺 coverflow，
  不要再排序（按评分再排一次会把「星期」这一层打乱，也不该由端上决定展示哪 12 部）；
- **可能是空数组**（`items: []`）：当季还没有「能取到封面」的动画时，**隐藏 hero**，
  不要填假数据、也不要留一块空白——首站那块空白就是这么来的；
- **不会 404、不会 5xx 表示「没内容」**：这个端点只有「成功（可能空）」和「服务端坏了」两种；
- 卡片里的 `cover_url` 仍然指向本服务 `/api/covers/{work_id}`，**不要直连来源站**；
- 服务端返回的每一条都**已经确认封面能取到**（本地缓存可读），客户端不必再判空；
  若真出现 404，按占位图降级即可，不要重试。

> 为什么不是「一次性返回 12 条固定的 id 名单」：本轮不做海报名单表/轮转/定时（运营能力延后），
> 现算的结果在同一份数据下是稳定的——同一季、同一批作品、同一个顺序。
> 真有人要手动指定某几部作品上 hero，再上第二张表，端点形状不变。

## 17. 制作公司页 / 系列页（2026-11-09，#557）

详情页「制作公司」那一行现在有地方可点了。

```json
GET /api/studios/{name}?limit=60&offset=0
→ { "name": "京都アニメーション", "total": 42, "items": [ …WorkSummary ] }

GET /api/series/{key}?limit=60&offset=0
→ { "key": "154", "name": "机动战士高达", "total": 16, "items": [ …WorkSummary ] }
```

**公司页**

- `name` 就是公司名本身（路径段 urlencode），**大小写敏感**：`A-1 Pictures` 与
  `a-1 pictures` 是两家公司。别在端上做 `toLowerCase()`，也别做「找不到就忽略大小写重试」；
- 名字会做 NFKC + 首尾空白归一，所以全角字母、全角空格、复制粘贴带空格的都能查到；
- 查不到 → **404 `STUDIO_NOT_FOUND`**。客户端拿到 404 时显示一张「这家公司还没有收录」的提示页
  （比首站的 404 白页多一层文案），**不要**渲染成「0 部作品」的空列表页
  ——那会让用户以为这家公司真的没作品；
- `total` 是这家公司的**可见作品总数**，`items` 只是一页（默认 60、最多 200）。
  头部那句「本站收录 N 部」用 `total`，不要用 `items.length`；
- 排序是有效评分降序（票数不足 50 按 0 沉底），与列表 `sort=rating` 一致；
- 详情页「制作公司」一行可能有多个名字，每个都可点，各跳一次。

**系列页**

- `key` 是系列键（不透明字符串，**不要解析、不要拼进展示文案**）；
- `name` 可能是 `null`（作品先到、系列行后到）：隐藏标题，或显示「系列」二字，别用 key 顶替；
- `total` 是**总数**，不是 `items.length`——首站系列页头部把截断后的长度当总数，
  超过 60 部就写错，我们单独给了 `total`；
- 排序是**评分降序**（与详情页区块的「年代升序」不同：这里是「哪几部最好看」）；
- 未知 key → 404 `SERIES_NOT_FOUND`。**注意**：有作品、没系列行是常态，那种情况是
  200 + `name: null`，不是 404——别把「没名字」当成「没这个系列」。
