# 验收清单（草案）

> 状态：**草案 · 待评审**。由 Python 负责人于阶段 0 起草。
> 目的是把"阶段 1 / 2 / 3 通过"变成可逐条打勾的动作，而不是口头结论。
> 每条都写明前置条件、操作步骤与**通过标准**；任一前置条件不满足时，该条记为**未验证**，不得记为通过。

## 0. 前置条件

- [ ] 数据源可达：`http://154.8.194.198:8000/docs` 返回 200
- [ ] 三人已确认 [`data-contract.md`](data-contract.md) 与 [`openapi.yaml`](openapi.yaml)
- [ ] Java 后端可从**手机**访问（使用局域网地址，不得用电脑的 `localhost` 充当手机后端地址）
- [ ] Flutter 已安装且 `flutter doctor` 对 Windows 桌面与目标安卓版本均无阻断问题
  - 桌面端需 Visual Studio「使用 C++ 的桌面开发」工作负载
  - 安卓端需 Android SDK 与真机或模拟器
- [ ]  Python 同步作业可在本机运行并可重复执行

## 1. 数据侧验收（阶段 1 起，Python 主责）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| D1 | 导入 50–100 条真实动画数据 | Java 侧作品数与来源映射数一致，无孤立记录 |
| D2 | 同一批次**连跑两次** | 作品数与来源映射数均不增长，第二次 `inserted=0`、`unchanged=N` |
| D3 | 修改样本的 `main_rating` 后再次导入 | `work_id` 不变，仅 `main_rating` 更新，其余字段保持原值 |
| D4 | 把样本的 `summary` 置空后再次导入 | 计为 `unchanged`，**已有 summary 未被清空** |
| D5 | 伪造一条 `title` 为空的记录 | 计为 `rejected`，原因码 `TITLE_REQUIRED`，同批其他记录不受影响 |
| D6 | 提交后 Java 已写入但响应丢失，Python 重试 | 用同一 `batch_id` 重试不产生重复作品 |
| D7 | 不带内部令牌调用导入接口 | 返回 `UNAUTHORIZED`，数据无任何变化 |
| D8 | 换行清洗 | 入库 summary 中不再出现 `\r\n`，统一为 `\n` |
| D9 | 长文本完整性 | 全库最长记录（7225 字）入库后长度不被截断 |
| D10 | 标题去重策略 | 「铁臂阿童木」三条各自成为独立作品；「航海王」动画与漫画各自成为独立作品 |

数据侧当前可独立验证的一项（不依赖 Java）：

```
curl -s "http://154.8.194.198:8000/api/contents?type=anime" | python -c "import sys,json;d=json.load(sys.stdin);print(len(d['items']))"
```

预期输出 `7894`。若数字变化，说明源站有更新，需重跑 D1 并复核 [`data-contract.md`](data-contract.md) 第 1 节的事实表。

## 2. 阶段 1：双端真实浏览

> 手机端与桌面端必须**分别**运行并通过，不得只验证一端。

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| B1 | 作品列表 | 两端都能拉列表，滚动到底可继续加载下一页 |
| B2 | 分页上限 | `page_size` 传超过 50 时按 50 处理，不报错 |
| B3 | 关键词搜索 | 输入标题片段能命中；无结果时显示空状态，不是空白页 |
| B4 | 作品详情 | 展示标题、类型、简介、来源评分；缺失字段显示占位 |
| B5 | 无封面处理 | 首期所有作品均无封面，两端统一显示占位图而非错图或空白 |
| B6 | 超长简介 | 7225 字那一条在详情页可折叠，不撑破布局、不全屏覆盖 |
| B7 | 极短简介 | 「TV二期。」那一条不产生大面积空白区块 |
| B8 | 多行渲染 | 含 `\r\n` 的记录按段落显示，不是挤成一坨 |
| B9 | 重名区分 | 三条「铁臂阿童木」在列表中作为三条独立记录出现，可通过评分或简介区分 |
| B10 | 网络失败 | 断网后可重试，显示明确错误，不静默失败、不崩溃 |
| B11 | 两端同源 | 手机与桌面连同一 Java 实例，看到的数据条数与内容一致 |

## 3. 阶段 2：同账号跨端管理

> 准备账号 A 与账号 B，两台设备（安卓真机/模拟器与 Windows 桌面）。

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| C1 | A 同时在手机与桌面登录 | 两端均保持有效会话，一端登录不把另一端踢下线 |
| C2 | 手机收藏一部作品并设为「想看」 | 桌面刷新后看到相同收藏与状态 |
| C3 | 桌面改为「看过」 | 手机刷新后显示「看过」 |
| C4 | 一端取消收藏 | 另一端刷新后该条收藏**与状态**同时消失 |
| C5 | B 登录查看 | B 看不到 A 的任何个人收藏 |
| C6 | 退出 A 切换为 B | 不残留 A 的个人缓存与凭据 |
| C7 | 请求失败时的表现 | 明确提示失败，界面不显示「已同步」 |
| C8 | 两端同时修改 | 最终结果符合"服务端最后成功提交生效"的约定 |
| C9 | 手机退出登录后 | 桌面仍可正常使用 |
| C10 | 手机重新登录 A | 原有收藏与状态完整保留 |
| C11 | 已取消收藏的作品在过期界面被改状态 | 返回 `COLLECTION_REQUIRED`，提示刷新，不会自动重新收藏 |

## 4. 阶段 3：可靠性与交付

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| E1 | 重复导入相同来源数据 | 作品数与来源映射数均不增长（对应 D2） |
| E2 | 来源样本字段变更后导入 | `work_id` 保持不变（对应 D3） |
| E3 | 写入成功但响应丢失后重试 | 无重复作品（对应 D6） |
| E4 | 坏记录追踪 | 可通过 `batch_id` 定位并重提被拒记录（对应 D5） |
| E5 | 来源不可用 | 保留上次成功数据，不清空作品或个人数据 |
| E6 | 越权写入 | 未持内部令牌的导入请求被拒（对应 D7） |
| E7 | 越权读取 | 普通用户不能读取或修改他人个人数据 |
| E8 | 新人上手 | 团队成员按 README 能独立启动服务并运行两端构建产物 |
