## 1. 问题

13,261 组「标题 + 年份」同时存在于两个来源（例：《永远的大和号 REBEL3199 第七章》bangumi 一条、
otaku_site 一条）。这是「多来源并存」设计的必然结果，`(source, source_id)` 层面**没有重复**，
导入幂等是正确的。副作用在展示层：

- 列表项 `WorkSummary` 只有 7 个字段，**没有 `source`**；
- 而 `Work` 详情**有** `source`（openapi `Work.source`，已知取值 `otaku_site` / `bangumi`）；
- 于是列表与推荐位里，两条记录**逐字相同**（标题、封面、年份、评分、标签都可能一样），
  用户只能点进详情才能发现「这是另一个来源」；
- 收藏也按 `work_id` 记，用户存的是哪一条全凭点中了哪个。

D3 的验收口径是：**标题相同但来源不同时，列表里能区分**。注意它只要求「可区分」，
不要求「合并」——合并属 W2 / 探索项 E1，本方案明确不做。

## 2. 现状盘点（已核对代码，非推测）

| 位置 | 现状 | 结论 |
|---|---|---|
| 列表 SQL `WorkRepository.COLUMNS` | **已经 select 了 `source`** | 数据在手上 |
| `WorkSummaryDto` | 7 字段，映射时**丢掉了 `source`** | 缺的只是一个出口 |
| openapi `WorkSummary` | 7 字段，无 `source` | 需同步 |
| openapi `Work`（详情） | 有 `source`，取值域已写明 | 有现成语义可复用 |
| 客户端 `WorkSummary`（Dart） | 7 字段，无来源 | 需加可空字段 |
| `ListCacheKey` 维度 | type / query / sort / page / pageSize / tag | 来源**不是**筛选维度，缓存键不受影响 |
| `work` 表索引 | `uk_work_source(source, source_id)`、`idx_work_title(title)` | 见方案 B 的成本说明 |

所以这不是「要造能力」，是**把已有的值放到列表上**。

## 3. 候选方案

### 方案 A（推荐）：`WorkSummary` 增 `source`，客户端显示来源徽标

契约：`WorkSummary.source`，类型与 `Work.source` **同名同义同取值域**，非必填（服务端总是返回，
客户端按可空处理）。**不带 `source_id` / `source_url`**：前者契约已写明「不得用于业务判断」，
后者是导航数据，列表用不上。

界面：卡片与列表行的元信息行加一个中性徽标，文字为展示名（`otaku_site` → Otaku、
`bangumi` → Bangumi；未知取值**原样显示**，不猜、不隐藏）。所有条目都显示，不判断是否重复。

成本：后端 1 个字段 + 1 行映射 + openapi；客户端 1 个可空字段 + 1 个小徽标组件。
**纯增量、可回滚**，且对既有客户端零影响（忽略未知字段）。

缓存兼容：hive 里的旧 JSON 没有该字段 → 解析为 `null` → 不显示徽标，其余照常；
下次联网刷新自动补全，**不需要清缓存、不需要改缓存版本**。

风险：来源名对普通用户意义有限，全量显示会让列表多一列噪声。若真机验收认为噪声过大，
退路是「只在同名重复时显示」——但那条退路需要方案 B 的能力，不是纯客户端能做的。

### 方案 B：A + 服务端「该标题另有来源」标记

契约：`WorkSummary.other_sources: string[] | null`，只在确实存在于另一来源时非空。

好处：只有 13,261 组会带标记，列表噪声最小；还能直接支撑 W2 的归并入口
（「这条还有 bangumi 版本」）。

成本：每行一次 `EXISTS (SELECT 1 FROM work w2 WHERE w2.title = w.title AND w2.source <> w.source)`。
`idx_work_title` 已存在，单行是索引等值查找；一页 20 行 = 20 次，量级可接受。
但它的语义是**全库**的，与当前筛选条件无关——用户筛了「动画 + 评分排序」后，
标出来的「另一个来源」可能根本不在当前结果里，文案要写成「该标题另有 bangumi 条目」而不是
「下面还有一条」。要把它做成**当前结果集内**的判定，就得对结果集分组，那是 W2 的活。

判断：技术上可行且不算贵，但多一个契约字段、多一层需要解释的语义；D3 不需要它。
建议与 W2 一起做，届时一并决定「标记」还是「归并」。

### 方案 C（明确不做）：真归并

把两个来源的同名记录合成一个作品实体（一个 `work` 挂多条来源记录）。这触及唯一标识规则，
属探索项 E1，需要别名 / 人工映射与**误合并代价评估**：把两部不同作品合成一条，用户无法自救。
本轮不做，也不在本方案范围内。

## 4. 推荐

**做方案 A，B 留到 W2，C 不做。**

理由：D3 只要求「不让用户把两条不同记录误认为同一部」，A 就够；A 是把详情页已有的语义搬到列表，
不引入新概念，前后端可任意顺序上线；B 的额外价值（降噪、为归并铺路）属于 W2 的目标，
现在做会让一个展示层小改动背上数据侧语义。

## 7. 不做什么（防止方案膨胀）

- 不合并标题、不做基于标题的模糊匹配、不生成「跨源作品」聚合实体（E1 / 契约 §3.2）；
- 不在列表返回 `source_id`、`source_url`；
- 不改列表筛选维度、不加索引、不动 `ListCacheKey` 的维度数组；
- 不为了「好看」给来源配品牌色——颜色会被读成状态，来源不是状态。

补充一条已落实到实现的边界：**来源取值不做映射**。`source` 是什么就显示什么
（`bangumi` 就是 `bangumi`），客户端不替产品发明「本站 / 第三方」的说法——
那是 per-site 适配配置的事，不是这里该决定的。
