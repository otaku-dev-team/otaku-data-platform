# 技术自解优先：能用技术解决的，不麻烦客户

> **状态**：2026-10-26 负责人定调，作为后续方案设计的默认思路。
> 上位依据：[`product-positioning.md`](product-positioning.md)。
> 相关：[`app-registration-approach.md`](app-registration-approach.md)、[`site-continuity-risk.md`](site-continuity-risk.md)。

---

## 1. 原则

**能靠技术解决的，绝不麻烦客户开发接口。**

客户（网站）找我们，是希望少做事而不是多做事。每多要一个接口，就多一次沟通、多一轮等待、多一份对方可能拒绝的风险。所以遇到"这个功能需要客户配合"时，先默认还有一个技术问题要解，而不是先默认要去提需求。

同一件事还有第二条：**平台不碰内容与运营**。

内容只有网站运营在改，平台侧不产生内容、也不做运营决策。这条边界想清楚之后，很多看似复杂的同步问题会直接消失——比如"网站改了、App 也改了谁算"，答案是**改的人只有一个**，不存在两方冲突。

---

## 2. 可复用的做法：承载客户现有的页面

凡冒出"需要客户开放某某接口"的念头，先问一句：**能不能改成承载客户已有的页面？**

客户网站既然在正常运行，它自己一定有对应的页面。我们不去要接口，而是把这个页面放进我们的客户端里：

- 用户感知：全程在 App 内完成，没离开；
- 客户感知：什么都不用做，一个字段都不用改；
- 我们：只做容器，**不经手用户密码、不代写业务数据**，因此不撞"不代持凭据、不回写"的铁律。

已经用这个思路解掉的问题：

| 场景 | 原本以为需要 | 实际做法 |
|---|---|---|
| **App 内注册** | 网站开放注册 API | App 内承载 `/register` 页面（两步：邮箱验证码 + 提交）。密码只在网站页面内，不经我们。详见 [`app-registration-approach.md`](app-registration-approach.md) |
| **站主在 App 改内容** | 网站开放内容写接口 | App 内承载网站后台的编辑页，站主用自己的管理员账号登录一次即可。写入仍发生在网站侧，不丢、不冲突 |

### 什么时候才需要去谈接口

只有在**客户网站根本没有对应页面**时才谈。判据：

1. 客户网站有没有这个功能的 HTML 页面？（有 → 承载；没有 → 才谈）
2. 承载后的体验是否可接受？（网站后台页在手机上可能难看，需实测）
3. 承载是否需要客户侧权限？（如管理员会话，由站主自己登录，不需客户开发）

## 3. 由此看清的一件事：首站是搬运站，不是通用样板

只读探测（2026-10-26）发现：首站 Otaku 的 `/admin` 需登录后访问，而后台下的写操作**只有账号、邀请码、角色管理，没有任何内容编辑接口或页面**。

这印证了它**是搬运站**——内容从上游来，站主不人工改。所以：

- "站主在 App 编辑内容"这个场景，**首站当前不存在**，是**将来原创内容客户**的需求；
- 更重要的：不要把首站的特性当成通用能力（与 `site-continuity-risk.md` §4.1 同理）。

---

## 4. 由此产生的一项待办：首站数据源正规化

我们目前是通过读取 Otaku 的公开接口取数——**这是尚未建立正式客户关系时的权宜之计，不是产品的固有形态。**

正常形态应该是：客户授权 → 提供数据来源（接口或数据库）→ 我们接入。首站现在还停在"我们先做出来再谈"的状态，长期看是合规敞口：对方改结构、加登录墙或追究起来，数据源就断了。

**待办**（需负责人与站主沟通，本文不擅自推进）：

1. 把"读取公开接口"转为**合同约定的授权接入**；
2. 明确历史数据的交付方式（对方给数据库导出，还是我们灌库）；
3. 明确后续新增数据的同步方式（对方推给我们，还是我们按约定频率拉取）。

这件事做完，首站才成为第一个**可复制的客户范式**：授权 → 接入 → 客户端。

---

## 5. 一句话

遇到"要客户配合"时，先当成技术问题去解；解不掉，再去谈。这条比任何单个方案都值钱，因为它决定了我们跟客户的关系是"我帮你省事"还是"我给你派活"。
