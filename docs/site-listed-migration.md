# 只显示首站收录的作品：V28 迁移与实测（2026-11-02）

> **一句话**：11-01 线上应急用 `deleted_at = '2099-01-01'` 借位藏了 18.3 万行；
> V28 把哨兵清掉、把「显示与否」拆成独立的 `site_listed` 列，列表从 **25,729 → 18,676**。
> 迁移在**生产数据副本**上跑过一遍：13.2 秒，四个查询面逐个验过。

## 1. 为什么不能用 `deleted_at` 当隐藏开关

`deleted_at` 的语义是「来源侧删了」（#249），借位的代价有三条，都会在之后某天咬人：

1. 任何按 `deleted_at` 判「存在/已删」的代码都会以为这 18 万部真没了；
2. 正规化时无法与真正的软删区分，只能靠哨兵值反查；
3. 导入的 upsert 会把 `deleted_at` 置空（#249 的规则），**下一次导入就全复活**。

所以 V28 做的第一件事是**把哨兵全部清掉**：bangumi 的 17.2 万行还原成未删除，
误导入的 1.09 万行 `otaku_site` 换成真正的删除时间（保留「删过」的事实，不留哨兵）。

## 2. 迁移做了什么（`V28__site_listed.sql`）

| 步 | 内容 |
|---|---|
| ① | `site_scope(subject_id)` 转正式表（线上那份是应急时手工建的，只有这一列） |
| ② | `work.site_listed`、`work_tag.site_listed`，默认 0 |
| ③ | 清哨兵：bangumi → `deleted_at = NULL`；`otaku_site` → 真删除时间 |
| ④ | 回填：`work JOIN site_scope ON subject_id = CAST(source_id AS UNSIGNED) WHERE source='bangumi'` |
| ⑤ | `work_tag` 冗余列同步（只写值不同的行） |

两个刻意的细节：

- **join 必须带 `source='bangumi'`**：`site_scope.subject_id` 与 `otaku_site.source_id`（content_id）
  是两套号，只按数值 join 会撞出 **3,015 条假匹配**（我在副本上先踩了一次）；
- **`work_tag.site_listed` 不是顺手加的**：标签词表与标签筛选不 JOIN `work`（V25 实测一 JOIN 就是 14 倍），
  不冗余的话词表会冒出「只有未收录作品才有」的标签，点进去是空列表。

## 3. 在真实数据副本上跑（不是猜）

生产 63 MB dump → 本地 MySQL 8.0 恢复 → **让 Flyway 自己跑 V28**（不是手工执行 SQL，
这样连 checksum 与执行顺序一起验）。

| 项 | 结果 |
|---|---|
| dump / 恢复 | 63,114,556 B / **41 s**，stderr 0 行 |
| V28（Flyway `execution_time`） | **13,237 ms** |
| 应用启动（含迁移） | **21 s**（平时 8 s，即迁移占 ~13 s） |
| 迁移前 | `work` 209,428 / 哨兵 183,478 / 存活 25,950 / 列表 total 25,729 |
| 迁移后 | 哨兵 **0** / 存活 **198,511** / `site_listed=1` **18,828** / 可见（非成人）**18,676** |
| `work_tag` | 74,816 行被标为 listed（18,828 部作品的标签） |

### 跑起来之后逐面验

| 面 | 结果 |
|---|---|
| `GET /api/works` | **total = 18,676**（迁移前 25,729） |
| 详情（收录内） | **200** |
| 详情（未收录） | **404**（不返 403，不暴露「有这条但你看不到」） |
| 未收录作品的评论 | **404**（同上，走同一个 work 解析） |
| `GET /api/tags` | 词表只剩 listed 的标签，计数不再虚高 |
| 相关推荐 | 只推 listed（详情 404、推荐却推得出来是最难解释的一种不一致） |

### 成本

| 查询 | 加条件前 | 加条件后 |
|---|---|---|
| 列表计数（全表扫描） | 170 ms | **176 ms** |
| 标签词表 | — | 307 ms（与 V25 记录的同量级） |

只多 6 ms（+3.5%），**没有加索引**：`site_listed=1` 占 9.5%，加索引的选择性不足以抵消回表，
而列表本身走主键顺序扫描、20 条约扫 210 行就够。

### 3.1 另外三个面（11-03 在生产补验）

上面验的是列表 / 详情 / 词表 / 相关推荐。收口后又核了三条**可能漏出去**的读路径：

| 面 | 结果 |
|---|---|
| `GET /api/schedule` | 档期 2,068 条，**断链 0**（`work_id` 指向未收录或已缺失的为 0）；本季 69 条里 66 条 listed、3 条无 `work_id`（走「待定」组） |
| `GET /api/me/collections` | `collection` 表 **0 行**，暂无可泄漏数据。代码 JOIN `work` 但**刻意不过滤** `site_listed`——用户自己收的东西不该因为来源站下架就消失（与详情 404 的取舍，见 §6） |
| `GET /api/works?q=` 搜索 | 与列表共用 `WorkRepository` 的同一个 WHERE 构造器，已带条件；全仓只有 `WorkRepository` / `TagRepository` 出现该列，不存在第二套查询 |

结论：未收录作品目前**没有从任何公开读路径漏出去**。以后再新增读路径，验法与上面一致——
挑一条 `site_listed=0` 的真实 `work_id` 打过去，看是 404 还是 200。

## 4. 写入路径怎么打标

`WorkRepository` 在 `insert` / `updateContent` 时按当前清单算一次：

- 配置在 `app.work.site-scope.self-sources` 里的来源 → 直接 1（站点自己的内容，不存在"收没收录"）；
- 其余 → 查 `site_scope` 主键，命中 1、不命中 0。

自站来源走配置而不是写死站名：这个后端是白标的，代码里出现一个具体站名
既等于替客户做决定，也会被 `scripts/check-site-isolation.py` 拦下来（我第一版就是这么被拦的）。
留空时没有自站来源，全部按清单判——首站现在就是留空（它的作品都在清单里）。

**每次写入都重判**，不缓存：清单是数据侧随时会改的，缓存住会让「改完不生效」重新变成谜。
代价是每行一次主键点查——相比这条链路里已有的 `JSON_TABLE` 拆标签 + 整组重写，可以忽略。

## 5. 开关与回滚

`app.work.site-scope.enabled`（env `OTAKU_WORK_SITE_SCOPE_ENABLED`，默认 `true`）：
关掉只是**查询不过滤**，不改任何数据。集成测试在 `application-it.yml` 里关掉——
测试库没有 `site_scope`，开着会让所有「导入后能查到」的用例凭空变空（那是测试环境缺数据，不是代码错）。

回滚：

- 只想让作品重新出现 → 把 env 设成 `false` 重启（不动数据，一分钟内生效）；
- 想连数据一起退 → 哨兵已清，没有「一键恢复隐藏」的路径，需要重新按清单回填（这正是拆列的目的：
  「显示与否」是数据，回滚应该是**改数据**，而不是借 `deleted_at` 的语义）。

## 6. 已知与后续

- **7,122 条「不在清单却曾经可见」的作品**随迁移一起消失（它们本来就不该显示）；
- 首站下架的作品会留在库里 `site_listed=0`，不显示、不删除——清不清理是数据侧的活，
  **保留的成本量在这里，决定权不在后端**：库 411 MB，`work` 209.7 MB + `work_tag` 146 MB 占 87%；
  存活 198,511 行里 179,683 行（**90.5%**）是 `site_listed=0`，`work_tag` 452,959/527,775 行（86%）挂在这些作品上；
  每晚全量备份 55–61 MB（gz）；
- ~~首站新收但我们库里没有的约 3,500 条，需要一次 `otaku_site` 增量同步~~
  **2026-11-02 实测该说法不成立，已撤**：`site_scope` 18,828 条**全部**在 `work` 里有对应行
  （`scope_matched=18,828`），反方向 `site_has_but_we_not=0`。3,500 那个数是拿老 `otaku_site` 快照
  （15,318）比出来的，按 `bangumi_id` 对齐后**一条不缺**，增量同步可以先不做；
- 一个顺带值得知道的开销：封面回填索引 103,203 条里已收录最多只占 18,828，
  即**至少 6.8 万次封面请求花在了永远不显示的行上**。若最终决定「保留」，
  回填建索引时应按 `site_listed=1` 取，别再继续给不可见行烧上游调用；
- `work_tag` 与 `work` 的一致性由写入路径保证（`replaceTags` 里同步），
  历史数据由 V28 一次对齐；以后再加可见性维度（例如分区、分级），三处必须同时改：
  `work` 列、`work_tag` 冗余列、查询条件。
