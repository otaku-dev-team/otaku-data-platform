## 2. 三条硬事实

1. **契约明文禁止回写**：`docs/identity-linkup-contract.md` §7 写「`nickname` / `avatar_url`
   仅客户端内展示，**不回写、不再分发**」；`V13__site_identity.sql` 文件头同样注明
   「nickname / avatar_url 不落库」。所以「编辑资料」「上传头像」不是没排期，是**与现行契约冲突**。
2. **平台没有文件存储**：`backend-java/src/main/java/` 里没有任何 `MultipartFile` / 上传 / 存储相关代码。
   封面走的是 `/api/covers/{work_id}` **代理来源站**，不落盘。要做头像，等于从零加一套存储 + 访问 + 清理。
3. **平台也没有邮件 / 短信**：`JavaMailSender` / SMTP / 短信在任何模块都搜不到。
   原文提的「邮箱 / 手机绑定」同样不是客户端对接就能完成的。

另：`User` schema 里 `display_name` 的注释已经把这条讲死了——
「平台账号恒为 `null`……站点登录（`site-login`）的 200 响应里会带上站点昵称，**仅供本次展示、不落库**；
同一账号后续 `/api/auth/me` 仍为 `null`」。

原 issue 的验收「菜单不止登出一项」——这一项做完就满足，且不依赖任何人。

## 4. B 项：资料展示，三条路

| | 做法 | 代价 / 冲突 |
|---|---|---|
| A | 站点提供 profile API，平台代理 | 与「平台只读拉取来源站、不代理来源站接口」冲突（同 #377 的结论） |
| B | 平台自建资料表 + 资料编辑 | 与网站资料形成**两份真相**，且直接违反 §7「不回写」 |
| **C（若必须展示，推荐）** | 客户端**本地缓存**登录时拿到的 `nickname` / `avatar_url`，不回写、不再分发 | 符合 §7 字面；但**换设备 / 重装即丢失**，且多端不一致，必须在 UI 上说明 |

如果接受「资料页只有 username + 账号信息」，那就**只做 A 项**，B 明确不做——
这是最省事、也最不容易返工的路线。

## 5. C 项：头像上传为什么不能顺手做

即便拍板允许回写，成本也远不止一个端点：

1. 存储：本地磁盘 + nginx 静态服务，或对象存储（平台目前两者都没有）；
2. 接入：上传端点 + 大小/格式校验 + 缩放（多尺寸）；
3. 安全：图片内容审核（成人 / 违规）、防盗链、清理策略；
4. 与网站账号的关系：头像是网站账号的属性，平台存一份就成了第二真相源。

建议**明确移出本 issue 范围**，要做得单独立项，并按「新增跨模块能力」走三人确认。
