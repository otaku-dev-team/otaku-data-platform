## 1. 这份文档解决什么

#503 的验收要求是"开关关闭/开启可配置，无需改代码"——也就是**闸门本身**。闸门（`ugc_enabled`，默认关）已就位，
但"什么时候开、开多大、没有管控能力时怎么办"是缺口。本文补这部分口径：

- **开放条件**：哪些能力到位了，才允许普通用户写 UGC；
- **灰度节奏**：从"全关"到"全开"分几步、每一步进/退的触发；
- **无管控能力时的处置与回退**：对应历史决策"先不开放"——当机器审核/人工审核都没接时，平台怎么守、怎么退。

## 2. 闸门现在是什么样（现状，非推测）

| 项 | 现状 | 依据 |
|---|---|---|
| `ugc_enabled` | 默认**关**；普通用户看不到写入入口、调用被拒 | #503 验收口径 |
| 机器审核接入位 | **就绪但未接**（`OTAKU_UGC_MACHINE_PROVIDER=none`），线上行为与未接入一致 | `ugc-machine-moderation.md` §1、§5 |
| 内测/测试账号 | 可绕过开关灌数据、验证画像信号（#490 评分轴） | #503 范围 |
| 评论 `ugc_comment` | 已实现（讨论流，可多条、可回复） | 阶段 2 验收 |
| 举报 `ugc_report` | 已实现（工单 + 导出 + 下线删除） | `ugc-retention-proposal.md` |
| 点评 `ugc_review` | **未实现**，方案留档待拍板 | `ugc-review-proposal.md` |
| 留存/删除 | 口径已定、代码已落地（软删、清理作业、注销匿名化、站点下线出证） | `ugc-retention-proposal.md` §6 |

一句话：**现在普通用户写不了任何 UGC，但灌数据的通道、内容留存与下线机制都在。** 缺的是"面向公众开放时的内容管控"。

## 3. 开放条件（门禁清单）

闸门要从"关"翻到"开"，必须满足下面三组条件。任一组不满足，普通用户侧保持关闭——
**这是 `ugc_enabled` 翻 true 的前置承诺，不是建议。**

### 3.1 平台侧基础能力（应已具备）

| 条件 | 当前 | 说明 |
|---|---|---|
| 内容留存/删除机制 | ✅ 已落地 | 软删、清理作业、注销匿名化、下线出证——没有它，开了也无法履行合规义务 |
| 举报通道可用 | ✅ 已实现 | 用户能举报他人内容；举报工单可被站主处理并导出 |
| 审计留痕 | ✅ 已实现 | `ugc.*` 审计、导出审计、下线审计，便于追溯与出证 |

### 3.2 管控能力（**当前缺口，开公众前必须补齐**）

| 条件 | 当前 | 说明 |
|---|---|---|
| 机器审核已接入 | ❌ `provider=none` | 接 http 端点 + 冒烟四条通过（见 `ugc-machine-moderation.md` §6）。否则每条 UGC 零筛查 |
| 人工审核兜底 | ❌ 无队列 | 机器判 `review`（拿不准）一律落 `pending`，但**谁来清 pending** 目前没有机制。必须有一条站主/运维可处理的路径，否则"先发后审"站点的 `pending` 永远没人动 |
| `on-error` 策略按站选定 | ⚠️ 有默认值 `pass`，未逐站确认 | 机审挂掉时 `pass/review/reject` 三选一，需站点明知并签字（严格站选 `review`/`reject`） |

> 为什么机器审核接入不等于"管控到位"：接入位只是把文本送出去拿个 `pass/review/reject`。
> `review` 落 `pending` 后若无人处理，先发后审站点等于没有人工介入时机。
> **所以"人工审核兜底"是与机器审核并列的硬条件，不是可选优化。**

### 3.3 站点侧合规确认（责任主体）

内容合规责任主体是**网站**，不是平台（§A）。因此每个站点在翻开该站 `ugc_enabled` 前，必须：

- 站点方明知并确认：UGC 内容合规责任在站点，平台只提供机审接入位与举报/留存机制；
- 选定本站的 `on-error` 策略与发布策略（`post` 先发后审 / `pre` 先审后发）；
- 确认已有处理举报工单与 `pending` 人工审核的人力/流程。

平台**不替站点下合规结论**——只把确认动作做成开关生效的前置步骤。

## 4. 灰度节奏（四档 + 现状）

从"全关"到"全开"分四档。每一档都定义**覆盖谁、进入要满足什么、什么信号触发退出/回退**。
档位切换只改配置（`ugc_enabled` + 白名单 + 机审 provider），**不要求发版**。

| 档位 | 覆盖人群 | 进入条件 | 退出/回退触发 |
|---|---|---|---|
| **P0 关闭（现状）** | 仅内测/测试账号（绕过开关） | — | — |
| **P1 内测账号灰度** | 内测 + 白名单测试账号，真实内容但小圈子 | 3.1 三项已具备 | 任一基础能力异常即回 P0 |
| **P2 小比例公开灰度** | 例如 5% 新用户（可配） | 3.2 三项已具备（机审接入 + 人工兜底 + on-error 选定）+ 站点合规确认 | 机审命中率/误杀异常、举报积压超阈值、出现漏审违规外溢 |
| **P3 全量开放** | 所有普通用户 | P2 稳定运行一段时间（建议 ≥ 2 周）且无 P2 退出信号 | 出现重大漏审/监管问询 → 退回 P2 或 P0 |

### 4.1 各档要点

- **P0 → P1**：不接机审也能走（内测账号可控、内容量小），但**只限白名单**。这是验证画像信号（#490）和客户端入口的低成本窗口。
- **P1 → P2**：这是真正的风险跃迁点——内容开始流向公众。必须 3.2 全绿，否则不进。P2 期间重点盯三个信号：
  1. **机审命中率**：`pass/review/reject` 分布是否合理（全 `pass` 说明适配器可能没真接上）；
  2. **举报积压**：站主/运维清 `pending` 与举报工单的时效；
  3. **漏审外溢**：公众可见的明显违规（靠巡检 + 用户举报反推）。
- **P2 → P3**：稳定期无上述信号再全开。全开后 `on-error` 与机审仍持续生效，闸门的"开"是**可随时翻回的常态**，不是一次性动作。

## 5. 无管控能力时的处置与回退

### 5.1 当前（无管控）的处置

现状就是 3.2 三项全缺、`provider=none`。处置只有一句：**普通用户侧保持 `ugc_enabled=false`**——
这与历史决策"无管控能力时先不开放"一致。内测/测试账号继续走绕过通道灌数据、验画像，不受影响。

### 5.2 即便临时开，也必须有的最小兜底

若因特殊原因需要在机审/人工兜底未齐备时临时对部分人群开放（例如 P1 内测），至少满足：

- 仅限白名单，**不流向公众**；
- 举报通道仍可用（用户能报，平台能导出交站点）；
- 留存/删除机制在线（出问题能隐藏/删除具体内容）；
- 明确这是"临时、受限"，不是"管控到位"。

**不允许**在未接机审、无人工兜底的情况下直接进 P2/P3。

### 5.3 回退方案（核心安全属性）

`ugc_enabled` 是配置开关，不是代码分支。**回退 = 把开关翻回 false，无需改代码、无需发版、即时生效。**

| 场景 | 回退动作 | 已写入数据怎么收 |
|---|---|---|
| 机审服务商故障 | 翻 `ugc_enabled=false`（或仅收紧到 P1） | 已 `published` 内容按 `on-error` 既有判定保留；可逐条 `hidden` 处置 |
| 漏审违规外溢 | 翻回 P2/P0 + 对涉事内容 `hidden`/删 | 同上；举报工单继续处理 |
| 监管要求 | 翻回 P0 | 留存机制保证可导出/下线交还（见 `ugc-retention-proposal.md`） |
| 机审接入本身回退 | `OTAKU_UGC_MACHINE_PROVIDER` 改回 `none` 重启 | 代码路径回到"一次布尔判断"，不需要回滚版本（见 `ugc-machine-moderation.md` §8） |

回退后**不丢数据、不留半成品状态**：`published` 内容仍可见可管，`pending`/`hidden` 仍在队列，
下次重开时继续处理。这是闸门设计刻意保证的——开/关是流量阀门，不是数据生命周期开关。

## 6. 责任边界（不替站点下结论）

- 平台提供：capability 开关、机器审核**接入位**（不绑死服务商）、举报通道、留存/删除/下线出证机制、审计。
- 站点负责：内容合规主体责任、机审服务商的采购与合同、"什么样算违规"的策略、处理 `pending`/举报的人力。
- 平台**不**在代码里写"什么内容违规"、不替站点选死一家机审厂商、不下合规定性结论。

## 8. 已定口径（初版，待三人确认）

| 问题 | 结论 | 落地 |
|---|---|---|
| 无管控时是否开放公众 UGC | **不开放**（`ugc_enabled` 保持 false），与历史决策一致 | §5.1 |
| 公众开放硬前置 | 3.1 基础能力 + 3.2 管控能力（机审接入 + 人工兜底 + on-error 选定）+ 站点合规确认 | §3 |
| 灰度分几档 | P0 关 → P1 内测 → P2 5% 灰度 → P3 全量，均仅改配置 | §4 |
| 回退成本 | 翻开关即可，无需发版、即时、不丢数据 | §5.3 |

## 9. 不做的事（避免范围蔓延）

- 不把"机器审核接入"等同于"管控到位"——人工兜底是并列硬条件，不在文档里弱化。
- 不在代码里写具体违规判定或绑死机审厂商（责任在站点，见 §6）。
- 不在 3.2 未齐备时进 P2/P3，无论运营压力多大。
- 不把闸门开关和机审接入混为一谈：两者独立配置，机审回退不影响闸门、闸门回退不影响机审接入位。
