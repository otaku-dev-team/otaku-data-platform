# 首站的用户画像与推荐算法（读源码记录）

2026-11-02 读了一遍首站源码。结论先放前面：**画像和推荐都是纯规则，没有模型，也没有对外接口**——它们挂在 HTML 页面路由上（`/me/persona` 那一组），没有 JSON 端点。所以要复用，只能照口径自己实现，不能调。

本文前四节记「照着做需要的口径」和「代码在哪」，第五节记**这两块之间哪里断了、可以怎么接**（那部分是我们自己的判断，不是现状描述）。

细节自己去看源码。

## 2. 画像怎么算

**数据源三合一**，先跨源归一再去重：

- Bangumi 公开收藏（`fetch_user_collections`，公开 API，上限 1000 条）
- 站内收藏 / 标注
- B站追番

**9 个维度**（`persona.py:104`）：题材垂直、探索广度、大众度、冷热跨度、高分率、年代跨度、追新度、情绪取向、完成度。

阈值不是拍脑袋的，每条都带实测记录：

```
mainstream  >= 93   → 主流厨     # 85 时近四成账号撞同一称号；93 = 全站前 7%
mainstream  <  35   → 冷门挖掘机
exploration >= 68   → 博爱       # 60 时约三成人命中
tag_focus   >= 63   → 偏食
58 <= quality < 75  → 口碑党     # 50 时近八成人都带，等于没区分度
quality     >= 75   → 神作党
want/seen   >= 1.5  → 仓鼠       # 想看远多于看过
```

最多取 3 个特征，顺序固定：**热度 → 口碑 → 口味/行为**。顺序是有讲究的——口味特征排在口碑后面会被「高分」槽整批吃掉，深度用户就体现不出来。

称号五层命中：组合毒舌 → 极端值成就 → 簇×特征主表 → 身份兜底 → 回退拼接。每一层都要有兜底，否则会出现「谁都不带特征」。

**画像本身是纯规则**，不联网、确定性可复现。LLM 只用来写「长评文案」，不参与任何判定。

分享卡走 `encode_card` / `decode_card`，名片编成一个 token，不需要登录也能看。

## 3. 推荐怎么选

入口 `build_user_home_picks`（`persona.py:2343`）。

### 两道闸决定用哪套口径

```python
stale = site_total >= profile_total * 1.5 and site_total >= profile_total + 10
# 两个条件都满足，才弃用画像、改走站内实时口味
```

比例闸挡小涨幅，基数闸挡小基数下的百分比抖动。刚同步完 Bangumi 的用户不会因为站内多收藏两三部就翻推荐。

### 总口味 / 近期口味双象

- 近期 = 90 天内有过动作的作品
- 不足 3 条 → 回落取最近 3 条
- 近期命中的题材权重 **2.0 倍**
- **浏览记录不进算法**，注释原话：「浏览≠喜欢，噪音大于信号」

### 打分就一行

```python
score = sum(weights[tag] for tag in matched) * 10 + effective_rating(rating, count)
排序：(-score, -effective_rating, content_id)
```

命中的题材数主导（×10），评分做同分加权。低票作品的评分在排序里按 **0** 算，不给任何加成。

### 四条硬规则

| 规则 | 效果 |
|---|---|
| 避雷标签一票否决 | `tags & avoided` 直接跳过，「宁可少推，不推雷」 |
| 只推有题材标签的 | 无标签无法证明命中 |
| 已收藏 / 已标注剔除 | |
| 系列去重 | 按标题前缀聚类，同系列只占一个推荐位，取最早的一部（推荐位要能从第一季看起） |

标签必须先归一：`expand_genre_names` 把「日常系」「致郁系」「体育竞技」展开成站内真实标签名。不归一就会精确对撞落空，避雷会**静默失效**。

### 兜底

没有可用信号 → 回落站长口味 `list_home_recommendations`，保证推荐位不空。

「近期口味」还有一层兜底：新用户动作太少时取最近 N 条，否则永远算不出近期。

## 4. 照做时最容易漏的五点

1. **评分必须两套口径**。展示用 `rating_shown`（人数不足出「--」），排序用 `effective_rating`（低票按 0）。只有一套就会出现「1 个人打 10 分」既占榜首又被加权推上首页——我们 2026-11-02 刚踩过这个（#370）。
2. **近期口味权重 2.0，但浏览不算信号**。实现成本几乎为零，比上模型稳。
3. **避雷一票否决 + 系列只占一位**。各几行代码，体验差别很大。
4. **标签归一**。不做归一，避雷静默失效、推荐静默落空，且很难发现。
5. **每层都要兜底**。画像没特征、推荐没命中、没有近期动作——每一层不兜底就是一片空白或同一批人撞同一称号。

## 5. 这两块之间的连接，断在哪

先说结论：**问题不在算法，在已经算出来的东西没接进去**。9 个维度算了 9 个，推荐只用了 2 个字段。

### 5.1 画像产出 30 多个字段，推荐只取两样

`build_profile()`（`persona.py:1748`）返回：9 个维度、`top_studios`、`early_share`、`avg_popularity`、`latest_year`、`representative`……

`recommend_from_site()`（`persona.py:2300`）只取：

```python
positive = [tag["name"] for tag in profile["top_genres"]][:8]
avoided  = [tag["name"] for tag in profile["avoided_tags"]]
```

剩下这些**全在推荐里浪费着**：

| 已经算好的 | 本可以用来 | 现在 |
|---|---|---|
| `fresh` 追新度 | 决定推新番还是老番 | 没用 |
| `mainstream` 大众度 | 冷门挖掘机推小众、主流厨推热门 | 没用 |
| `tag_focus` 题材垂直 | 偏食的人少发散，博爱的人多题材 | 没用 |
| `era_span` / `early_share` | 年代分布 | 没用 |
| `top_studios` | 「喜欢京都动画」是很强的信号 | 没用 |
| `avg_popularity` | 冷热区间 | 没用 |

最明显的一处：**「冷门挖掘机」是 `mainstream < 35` 判出来的，但拿到这个称号的人，推荐给他的还是和主流厨一模一样的东西**——称号只用来展示，没用来推荐。

### 5.2 推荐发出去就不管了

`models.py` 里有 `content_favorites`、`content_view_history`，但**没有推荐位的记录**。于是：

- 不知道推荐有没有人点；
- 不知道点的人后来有没有收藏；
- 想调权重只能靠感觉，也没法做 A/B。

补起来很便宜：一张 `recommend_impression(user_id, content_id, served_at, position, source)` 只要记录，不做复杂。「点没点」复用 `content_view_history`，「收没收」复用 `content_favorites`。

### 5.3 打分里评分几乎不起作用

```python
score = sum(weights) * 10 + effective_rating(...)
```

多命中一个题材就 +10，而评分满分才 10。**排序基本等于命中标签数**，评分只在同命中数时当决胜。

这是有意的（注释写了「评分做同分加权」），但副作用是题材匹配的庸作和神作排在一起。想让质量起作用，把 ×10 调小或给评分加系数即可，一个常数的事。

### 5.4 画像是快照

`persona_reports` 存的是上次生成的 payload。用户后来越收藏越多，画像不更新，除非重跑成分检测。实时口径兜了一部分，但**「本命题材 / 避雷」这两样是旧的**。

不用重算全量就能缓解：加一个「画像 vs 最近 20 条收藏」的题材偏差检查，偏差过大时降权旧画像。

### 5.5 建议顺序

**先做 A + B，各半天：**

- **A · 把维度接进推荐。** 不改打分公式，只加候选集筛选：`fresh` 低就排除近两年新作、`mainstream` 低就优先低人气、`tag_focus` 高就限制最多 3 个题材。这三个参数加进 `recommend_contents` 即可，现有结构不用动。
- **B · 加曝光表。** 不记录就判断不了 A 有没有用。

**C · 题材多样性**（8 个推荐位别全是一个题材）——有 `dedupe_series_picks` 的现成写法，照抄几行。

### 5.6 两条别动

1. **浏览不进算法。** 注释写的「浏览≠喜欢，噪音大于信号」是对的，别因为「有数据就要用」加回去。
2. **避雷一票否决。** 「宁可少推，不推雷」尤其对 ACGN 用户成立——推一部雷的代价远大于少推一部。

## 6. 我们要用，还缺什么

我们后端现在只有 `work` / `collection` / `tag`，**没有画像表，也没有推荐**。

要接这套，主信号只有 `collection`，缺的正好两样：

- **`rating_count`**——判断评分可不可信，没有它排序会被假高分污染（#370 已在排）
- **负向信号**——避雷 / 低分 / 抛弃。首站是靠 Bangumi 的个人评分和「抛弃」状态做的，我们目前没有

另外我们的 `collection` 只有 `updated_at`、没有版本号，并发改同一个收藏时服务端只能「后写的赢」——做画像前得先解决这个（见 `docs/开源参考与可借鉴项.md` 收藏同步那节）。
