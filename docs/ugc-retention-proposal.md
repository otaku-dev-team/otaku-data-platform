# UGC 留存与删除策略（方案 · 待拍板）

> 状态：**口径已定（zm 2026-10-30），代码已实现**（#240 B2c③⑤）。最终法务口径仍以站点/合同为准。
> 归属：#240 B2c 剩余项里的「留存策略」。主责 @pyxz0；合规口径由站点 / 法务定，本文只给平台侧可执行的机制与推荐值。
> 相关：`product-positioning.md` §A（代存定位与责任主体）、[`deletion-semantics-proposal.md`](deletion-semantics-proposal.md)（作品软删，与本篇不同层）。

## 1. 一句话

**责任主体是网站，但「留多久、怎么删、怎么交还」必须由平台提供可执行的机制**——现在三样都缺：
软删行永久留着、停服只有导出没有删除路径、用户根本无法注销。本文给出口径选项与落地拆解，
数字待站点 / 法务拍板。

## 2. 现状盘点（2026-10-29 核实，非推测）

| 数据 | 当前行为 | 依据 |
|---|---|---|
| `ugc_comment` published / pending / hidden | 永久保留 | 无清理作业；`@Scheduled` 全局只有会话与设备两个 |
| `ugc_comment` deleted | **永久保留**（软删保行，便于追溯） | `V18__ugc_comment.sql` 注释、`markFloorDeleted` |
| `ugc_report` 工单 | 永久保留（含已 resolve / dismiss） | `V20__ugc_report.sql`，无清理 |
| `console_audit`（含 `ugc.*` 审计） | 永久保留 | `V12__console_phase2_audit.sql` |
| 导出 | 支持 `status=published/hidden/deleted/all`，UTF-8 BOM，上限 5 万行 | `ConsoleUgcService.exportCsv` |
| 站点下线 | 只有导出；**没有删除副本的可执行路径** | 无脚本、无端点 |
| 用户注销 | **不存在**：`app_user` 被 `ugc_report / ugc_comment / collection / user_device / user_session` 五张表外键引用，也没有注销接口 | `information_schema.key_column_usage` 实查 + 全仓无 `deleteAccount` |

三条都是实话，也都在同一个方向上：**定位里承诺的事，执行侧还没接通**。

`product-positioning.md` 原文（停服态）：

> 停止同步 → 客户端下线 → 副本按要求删除 → 数据交还客户。合同写明。

导出这一半做了（B2c①），「按要求删除」这一半没有。

## 3. 三个缺口与各自的性质

### 3.1 软删行没有清理作业（工程债，不涉红线）

`deleted` 是为追溯保留的，但「保留」不等于「永久」。现在没有清理，等于：

- 用户以为删掉了，数据其实一直在库里；
- 表只增不减，几年后 `ugc_comment` 的体积会变成运维问题；
- 一旦站点要求「把我的评论彻底删掉」，我们只能手工写 SQL。

**不涉及产品口径**：保留期取多少是数字，机制（定时清理 + 可配置天数）是工程。

### 3.2 站点下线没有删除路径（承诺缺口）

导出能交还数据，但「副本按要求删除」目前只能由我在服务器上手写 SQL——
不可复现、不可审计、交接给别人就断。需要一份**可执行的下线清单**（导出 → 校验 → 删除 → 出证）。

### 3.3 用户无法注销（红线；口径已定，代码已落）

五张表都有外键指向 `app_user`，且没有注销接口。后果不只是「功能缺失」：

- 用户在客户端里找不到「注销账号」；
- 即便站点要求删号，我们也只能删干净评论再删账号，而「删干净」意味着**连带删掉他在别人楼下的回复**；
- 若面向中国大陆用户运营，《个人信息保护法》的删除权是硬要求，不能靠「暂不支持」长期挂着。

**已定（zm 2026-10-30）**：默认**匿名化保留**——评论行不动，作者显示「已注销用户」，
楼层不塌；物理删留一个默认关闭的开关（`app.ugc.retention.remove-comments-on-account-removal`）。
zm 的原话是「最终要站点/法务认可，我这边先落匿名化，物理删先留开关，不替法务下结论」。

实现见 `V23__account_deletion.sql` + `DELETE /api/me`：置 `deleted_at`、撤销全部会话、发事件；
UGC 侧监听器按开关决定要不要软删该用户评论。

## 4. 口径选项

| | 方案 A · 全留（现状） | 方案 B · 定期物理清（推荐） | 方案 C · 每站可配 |
|---|---|---|---|
| deleted | 永久 | **15 天**后物理删（开发期取值，zm 定；上线前按站点改） | 站点配置 |
| hidden | 永久 | **365 天**后物理删（站主仍可导出留档） | 站点配置 |
| 举报工单（已结案） | 永久 | **180 天**后物理删（未结案不动） | 站点配置 |
| 审计 `ugc.*` | 永久 | **365 天** | 365 天（审计不建议站配） |
| published | 永久 | 永久（只在站点下线或用户注销时处理） | 同 B |
| 成本 | 零 | 一个 `@Scheduled` + 三条 DELETE + 测试 | B + `site` 加一列 |

**推荐 B，并把天数做成配置项**（`otaku.ugc.retention.*`），这样将来接 C 只改配置来源，不改代码。
A 的问题不是「简单」，是「删除不彻底」；C 在多站阶段才有意义，现在做等于提前抽象。

推荐值都是**待确认数字**，不是合规结论——站点与法务若给出不同期限，改配置即可。

## 5. 落地拆解（按是否依赖拍板分组）

### 现在就能做（不依赖口径）

1. `UgcCleanupJob`：范式照 `DeviceCleanupJob`（每天 04:50 UTC，与会话 04:30 / 设备 04:45 错开），
   只清 `deleted` 且 `updated_at < now - retention` 的行；先只清评论，工单与审计等口径确认再加。
2. `scripts/site-offboarding.sql`：按站点导出校验后的删除清单，逐表 DELETE + 保留审计，**带 dry-run**。
3. 导出口径写进契约注释：`status=all` 含 deleted，说明「导出是交还的凭据」。

### 等拍板（红线 1）

4. 「已注销用户」的展示语义（匿名化 vs 物理删）——决定评论是否保留、author 怎么显示。
5. 注销接口形态：`DELETE /api/me`？还是站点侧发起？涉及跨模块，需三人确认。
6. 各状态保留天数（§4 的数字）。

## 6. 已定口径（zm 2026-10-30）

| 问题 | 结论 | 落地 |
|---|---|---|
| 注销后评论保留还是删 | **匿名化保留**，作者显示「已注销用户」，楼层不塌；物理删留开关，默认关 | V23 + `DELETE /api/me` + UGC 监听器 |
| 保留天数 | 全做成配置项，**开发期先 15 天**（方便测清理链路） | `app.ugc.retention.deleted-days` |
| 站点下线出证 | 做，`scripts/site-offboarding.sql` 只删 UGC，执行完出「已删除 N 行」确认函 | 脚本已建；确认函模板见 §5 |
| 「看过才能评」 | **不强制**，UI 引导 | 影响点评方案（见 `ugc-review-proposal.md`） |
| 点评与评论 | **不打通**，两个 tab：点评打分、评论讨论 | 同上 |

zm 的注：「用户注销权」是红线级法务项，物理删 vs 去标识化最终要站点/法务认可——
我们先落匿名化，物理删留开关，不替法务下结论。

## 7. 不做的事（避免范围蔓延）

- 不做「用户自助注销」的客户端流程——那是 W1 的活，本文只定后端语义。
- 不做数据归档（冷存储）——当前体量（评论数百条级）远未到需要归档。
- 不替站点做合规判断（实名、资质、内容审核主体）——那些是合同条款，不是代码。

## 7. 站点下线确认函（模板，执行完再填）

> 用途：站点停止合作时，把「数据已交还、副本已删除」这件事落到纸面。
> 执行 `scripts/site-offboarding.sql` 后填写，双方各留一份。

```
                     UGC 数据副本交还与删除确认函

致：<站点名称>
事由：<站点域名> 停止使用本平台客户端服务，UGC 数据副本的处理确认

一、数据交还
  1. 导出接口：GET /api/console/ugc/export?status=all（含已删除评论）
  2. 导出时间：<YYYY-MM-DD HH:MM>
  3. 导出条数：<N> 条（published <a> / pending <b> / hidden <c> / deleted <d>）
  4. 交付方式：<文件 / 链接>            接收人：<姓名>

二、副本删除
  1. 执行时间：<YYYY-MM-DD HH:MM>
  2. 执行方式：scripts/site-offboarding.sql（dry-run 对账通过后执行）
  3. 删除范围：ugc_comment <N1> 条、ugc_report <N2> 条
  4. 保留项：console_audit（审计留痕，不随站点删除）<N3> 条
  5. 不在本脚本范围：收藏、账号、设备令牌（按合同另行处理）

三、确认
  平台方：<姓名>    <YYYY-MM-DD>
  站点方：<姓名>    <YYYY-MM-DD>
```

注意两点：
- **先导出、后删除**，顺序不能换（导出是对账依据，删完再导就是空文件）；
- 删除会写一条 `site.offboard` 审计，写明 `comments=N reports=M`，这份审计**故意不删**——
  它要比被删的数据活得久。
