## 0. 一句话

适配网站特色功能是底座的一等能力，不是项目制补丁：**机制先于需求就位**，需求到来时优先是「配置 + 部署」，万不得已才是「产品大改」。

## 1. 拍板依据（负责人 2026-10-24）

两条，都是产品层判断：

1. 齐平原则：**网站没有的，我们也没有；网站有的，我们也要适配。** 客户端与网站齐平——不发明网站没有的功能，也不遗漏网站已有的能力。（第一次适用：D3，见 §8）
2. 提前建设：适配网站特色功能是大部分网站都会提出的要求。不能等需求来了再大改产品；适配能力（分级、适配包、模板位、部署通道）现在建好，将来才可能是快速部署。
   边界修正（负责人）：特色功能需求部分可枚举、重复出现，也有大特色（站点独有的一次性大需求）。目标是**尽量用快速部署能力接住，实在不行才大改**——不是所有需求都能被机制化，详见 §2。

## 2. 为什么不能「来了再改」

- 每次需求驱动的大改 = 契约波动 + 客户端发版 + 数据迁移 + 全站回归。项目已经付过这笔学费：初期定位模糊造成的技术误判，最终是定位文档 + 契约 + 对外叙事三处返工（PR #129）。
- 特色功能需求部分可枚举、重复出现（首站的池子已经列在差距清单里，后续网站大概率同型），但也有大特色——站点独有的一次性大需求。前者机制化是纯赚；后者的价值在于**尽量用快速部署能力接住，实在不行才大改**。
- 大特色的处理规则：优先把需求收敛进 L1 / L2（配置或适配包能表达，就不动核心）；确实必须 L3 的，走契约流程并把代价写清楚；每次 L3 落地后复盘「能否沉淀为 L2 能力」——防止每个大特色都是一次性大改、机制越用越薄。
- 与对客户的承诺直接相关：我们承诺的是「授权即可上线、周期显著短于自建或采购」。若每个特色功能都要产品级改造，**「周期短」不成立**。

## 3. 适配什么：三层分级

复用商务口径的三档评估，落到技术分级：

| 级 | 名称 | 典型内容 | 改动面 | 量级 |
|---|---|---|---|---|
| L1 | 配置级 | 品牌资源（应用名 / 图标 / 包名 / 主题）、目录范围、字段显隐与排序默认值、功能开关、回原页路径模板 | 纯配置，零代码 | 当天 |
| L2 | 适配级 | 站点有、底座没有的特色功能：详情富字段、角色 / 声优、Staff、系列关系、人物页、 制作公司页、档期分类、登录后内容（收藏 / 历史 / 个人页） | 适配包条目 + 契约补丁 + 客户端模板 | 以周计 |
| L3 | 底座级 | 新端点族 / 新数据模型（档期、资讯即此级先例） | 核心演进，走红线流程 | 以迭代计 |

判定规则：**能配置不建表，能适配包不改核心，必须动核心的走契约流程**。契约补丁沿用已验证的先例（#113 档期、#127 资讯）：公开端点 + 内部导入 + schema，**一个功能一组补丁，各自可独立回滚**。

大特色也走这三级：目标是把它收敛成 L2（适配包能表达）；**L3 是兜底，不是默认入口**。

## 4. 适配包：一个站点一个包

适配包是「这个站的全部站点特定决策」的单一来源。产品层要求它能表达：

| 维度 | 必须能表达 |
|---|---|
| 品牌 | 应用名、图标、包名、主题（定位产品要求 2：品牌资源按站区分） |
| 目录范围 | 收录哪些来源的记录、是否包含第三方来源记录（D3 的变量在此，见 §8） |
| 功能开关 | 哪些功能在本站启用；未启用的不进 UI |
| 端点映射 | 站点页面 / 接口 → 我们的接口（含抓 HTML 时的页面模板） |
| 字段映射 | 站点字段 → 契约公共字段 / `custom_fields`（兼容通用化方向，不把内容语义焊死） |
| 展示模板 | 列表 / 详情 / 实体页的呈现方式（`display_template` 演进位） |
| 身份 | 授权端点就绪度；未就绪 = 平台账号过渡 + 预留切换路径（定位 §4.4） |
| 回原页 | 路径模板（`source_url` 人读页规则，null 时不渲染入口） |

**边界（红线，不动）**：

- 适配包由我们运营。**不向站主开放站点配置与接入能力**（定位 §1.2：接入与配置新站点是底座核心能力，开放即服务价值归零）。
- 私有化交付 = 核心 + 该站适配包的运行态；**不含**适配工具、多站能力、底座平台能力（A2 硬边界：只交付客户自己用的那一个端）。

## 5. 数据链路：特色功能怎么进来

三条现实路径（差距清单 §九已结论）：

1. 站点侧只读 JSON 出口（首选）——站点归同一负责人，可增设 `/api/contents/{id}/facts` 一类只读出口，数据站点已有、无需回源第三方；
2. 抓 HTML（站点无 JSON 出口时）——贵（1.8 万条 ≈ 3 小时以上、42% 断连率），但限流 / 退避重试 / 失败记账已在 sync 层，直接复用；
3. 第三方 API（Bangumi）——需只读令牌，Issue #124，暂缓。

统一入口：来源适配器（契约 §4.7）→ `/internal/import/**` → 幂等 upsert（`NULL` 不覆盖、抓不到 ≠ 删除）。**新增数据通路不改核心写入语义。**

## 6. 契约与客户端：加功能不改产品

- 契约补丁模式（#113 / #127 先例）：公开端点 + 内部导入 + schema，按功能拆 PR，各自可回滚；openapi 是 CI 契约校验的输入，改 schema 同步行为说明。
- 字段演进位：站点专属字段进 `custom_fields`，展示走 `display_template`（通用化提案的两层抽象）。当前不实施通用化，但新决策须兼容——**不把内容语义再次焊死**。
- 客户端：功能开关驱动渲染；本站未开启的功能不出现。参照提醒功能的诚实模式（桌面端没有就说没有，不给点了没反应的开关）。
- 兼容：老客户端忽略未知字段；旧缓存缺字段解析为 `null`（#120 方案 A 已论证，无需清缓存、无需改缓存版本）。

## 7. 生命周期与快速部署

```text
需求 → 探针（站点有什么：端点 / 页面 / 字段 / 填充率）→ 分级（L1 / L2 / L3）
     →（L2 / L3）契约补丁走红线流程 → 适配包条目 → 客户端模板
     → 单站验收清单 → 部署 → 复盘（是否值得升为公共能力）
```

「快速部署」的产品要求：

- 单站独立部署（定位产品要求 1）：一个站点一个部署单元，站与站之间互不影响；
- 适配包发布与核心发版解耦：L1 / 多数 L2 = 适配包更新，不走核心发版；
- 适配包独立回滚：某个站的某个功能出问题，回滚该站适配包，不动核心、不波及他站；
- 每站一套验收清单（对齐 ROADMAP 的验收记录模式），验收通过才进生产。

探针结论必须来自实测或站主明确答复，未验证的一律标注「未验证」；差距清单 §七 / §八 的复现方式可直接复用。

首站已探明的功能池（差距清单 P0–P4；P0 年份已端到端完成，档期与资讯已在合并队列）：

- P1 标签筛选 + 搜索扩面（依赖原名 / 别名 / 公司 / 声优字段先落）
- P2 新番档期（后端 / 同步 / 客户端在合并队列第 1–2 批）
- P3 详情富字段（站点 DB 有、JSON 不给；路径 = 站点侧只读出口优先）
- P4 资讯（后端 / 同步 / 客户端在合并队列第 1–2 批）
- 未入池：人物页 `/cast/{person_id}`、制作公司页 `/studios/{name}`、`/creators/{name}`（源码实测路由真实存在）、档期分类 `/api/schedule/categories`、登录后内容（favorites / history / persona）

## 8. 与 D3 的关系（齐平原则的第一次适用）

齐平原则回答 D3：客户端与网站齐平。

- D3 的问题（13,261 组「标题 + 年份」双来源记录在列表里分不清）本质是我们的快照混入了非本站记录造成的呈现问题——它不是网站拥有的功能，我们不应对它发明产品语义（归并、聚合实体）。
- 真正的变量是目录范围（本站记录 / 混合快照），它是 per-site 适配配置，不是产品语义。
- **默认值已定（2026-10-24 拍板）：按网站的。** 默认只收录网站自己的记录；要含第三方来源记录，在适配包里显式开启、配来源标识、并记录理由（为什么这个站要含、含哪些）。
- 首站 Otaku 例外成立，理由记录在案：Otaku 是开发中网站、内容不全，且站点自身的数据源就是 Bangumi 档案——我们直接用档案记录，等于与站点同源，有利于开发，不违反齐平原则。来源标识照显（透明度底线）。
- 来源徽标（#120 方案 A）保留为**透明度底线**：目录里只要出现非本站记录，用户就必须能分辨。它不是归并的前奏。
- 归并（方案 C）不做；服务端「另有来源」标记（方案 B）随 W2。**D3 不触发产品改动，触发一次适配包配置项的落位。**

### 9.1 适配包形态与私有化最小集合：正式口径（2026-10-24 负责人拍板）

先明确一条通用边界（不论选哪种形态都成立）：适配包的「值」（八维度的具体配置）可以跟着站点走；适配包的「生产能力」（适配规范、配置校验器、探针脚本、联调流程、契约补丁流程）是平台能力，**永不随私有化交付**。形态之争只决定「值」放哪。

形态三选项：

| 选项 | 做法 | 优 | 劣 |
|---|---|---|---|
| 1 · 主仓目录 | `sites/{site}/` 放主仓，构建时按 `--site` 烘焙单站产物 | 零额外基建；契约补丁与站点配置同仓，改功能一次看完 | 多站后主仓膨胀；私有化剥离靠构建纪律保证，不是天然属性 |
| 2 · 独立仓 | 每站一个适配仓，主仓留 manifest 锁版本 | 交付单元干净（A2 边界天然成立）；可做客户级访问控制；客户可长期持有自己的适配包 | 两仓版本 skew；契约补丁要跨仓；只有一个站就建是 over-engineering |
| 3 · 混合 | 见上方通用边界 | 是边界不是选法 | — |

**建议：选项 1 + 四条约束 + 拆仓触发条件**。约束：① 适配包目录自包含（八维度不散落主仓其他位置）；② 核心代码零站名硬编码（站名只出现在 `sites/` 下）；③ 构建系统产出单站部署单元；④ CI 做剥离校验（单站产物不含其他站内容）。拆仓触发条件（任一发生即拆）：第二站接入、首个私有化客户要求持有自己的适配包、站间出现保密 / 权限需求。理由：现在拆是 YAGNI；目录自包含后，拆仓是一次机械迁移。

私有化交付最小集合：原则 = 「让这一个网站独立跑起来并自行运维的最小集合；**用来再生产站点的东西一律不在里面**」。

- 交付：单站构建运行态（后端；同步仅含本站 source 适配器；客户端品牌烘焙；schema + 迁移；部署产物；运维文档）+ 本站适配包实列（八维度取值）+ 本站数据（作品快照 + 用户与账号数据——按定位 §1.2 归属表，内容与数据归网站，必须可携带）+ 本站验收记录。
- 不交付：适配规范与工具、多站路由 / 管理、其他站的任何内容、核心源码与生产能力（代码交付以运维接管为限，见口径第 2 点）、完整客户端构建链（口径第 3 点）、身份切换工具（口径第 4 点）、源码买断（明确不在私有化模式内）。

正式口径四点：

1. **形态 = 选项 1（主仓目录）+ 四条约束 + 拆仓触发条件**。约束：① 适配包目录自包含（八维度不散落主仓其他位置）；② 核心代码零站名硬编码（站名只出现在 `sites/` 下）；③ 构建系统产出单站部署单元；④ CI 做剥离校验（单站产物不含其他站内容）。拆仓触发条件（任一发生即拆）：第二站接入、首个私有化客户要求持有自己的适配包、站间出现保密 / 权限需求。
2. 源码 = 运维接管（跑起来、备份、跟随我们的发布升级），且代码交付有界限：只交付运行与运维必需的代码与配置（部署产物、站点配置、迁移脚本、运维文档），不交付核心源码与生产能力（适配规范、校验器、探针、联调与契约补丁流程）。若客户要求代码接管（自己改），走单独商务；即便给源码，A2 红线不松——**给了代码也不给能取代我们市场地位的东西**。
3. 客户端构建链 = 代换为主、资源包为辅：品牌资源（应用名 / 图标 / 包名 / 主题）默认由我们代换烘焙；可附带本站品牌资源包供客户存档与核对。**完整构建链不交付**——它属生产能力，外流即外泄「品牌按站配置」的机制。
4. **身份切换工具（账号映射、收藏迁移）算平台能力，不交付**：用户数据是客户的，工具是我们的；身份切换的实施作为服务做（我们执行迁移，客户持有数据）。

## 10. 不做什么（防膨胀）

- 不向站主开放站点配置 / 接入新站的能力（红线）；
- 不建跨站功能市场或「功能插件商店」；
- 不为假想需求提前实现具体功能——只建机制（分级、适配包、模板位、部署通道）；
- 不改已落地的作品型逻辑、字段、契约与 W3 口径（「以前做的先不改」）；
- 不因本文启动通用化（generalization-proposal 的触发条件不变）。

## 附录 B：齐平验收标准（9 成）

> 性质：§3 三层分级 / §8 齐平原则的量化验收表（2026-10-24 立项）。**开发期只作自检标尺，不作验收闸门**；启用时机 = 要签单 / 要上架 / 站主决定关停 / 要对外承诺。

### B.1. "9 成"怎么算（评分模型）

#### B.1.1 达成度分级（每一项）

| 级 | 代号 | 分值 | 含义 |
| --- | --- | --- | --- |
| 原生 | N | 1.0 | 客户端内完成，交互与能力与站点等价 |
| 降级可用 | D | 0.6 | 客户端内完成，但能力 / 交互有可感知简化（不跳转、不缺核心动作）。**仅限"实在做不了/不划算"的项** |
| 跳转 | J | 0.0 | 只能在浏览器打站点页完成 → **B 模式禁止出现** |
| 不支持 | X | 0.0 | 没有 |

#### B.1.2 判定规则（B 全面转入模式）

1. 一票否决：见 §B.3「核心项清单」。任一核心项为 `J` 或 `X` → **直接不达标**（不看总分）。
2. 无跳转：全清单**不允许任何一项为 `J`**。B 模式下"回网页"不算达成。
3. 加权总分 ≥ 90%：`Σ(权重 × 分值) / Σ权重 ≥ 0.90`。
4. 权重：核心 = 3 / 重要 = 2 / 一般 = 1。**核心项必须 `N`**；**UGC 全系必须 `N`**。`D` 只允许用于确实做不了或明显不划算的项——判定口径：实在做不了 / 做了没人用 / 没性价比 / 没想到 / 需单列；不能拿"不纳入"当偷懒借口。
5. 9 成的分母 = 站点功能全集（账号 + 功能两维）；`N` 覆盖 ≥90%。剩下 10% 的松弛**只能来自上述"做不了 / 不划算"的项**，且每项记录理由（不能拿它当偷懒的口子）。**运营能力不进本分母，见 §B.8 门槛**。

> 既有「明确不纳入」清单已复审：结论见本附录 C。用得上的收回通用方案；**"基于当前进度写的不承诺"统一改判为「进度项」**（开发期只记进度，承诺口径等开发接近完成 / 签单 / 上架时再定）。不要用进度当产品边界，也不要把清单当"可以考虑开发"的许愿池。

> 直白说：**9 成 = 所有核心功能 + UGC 都原生 + 总分 ≥90% + 一个跳转都没有**。剩下 10% 只准给"实在做不了 / 不划算"的项，且要记理由，不能拿来凑数。

## 附录 C：排除清单复审记录（2026-10-24）

> 用途：说明「哪些不做被收回、哪些是红线、哪些只是进度」——供后续 review 追溯判据，不改任何功能实现。

### C.0 一个前提：开发期不用"当前进度"当"承诺"

负责人定：**"不承诺"是开发差不多之后才定的口径**，现在拿进度写"不承诺"，等于把没做完的东西提前焊死成产品边界；反过来，什么都写"可以考虑开发"又等于没有清单。
所以本次复审新增一类判定——**进度项**：只是"现在还没做"，**既不等于不做，也不进承诺**。承诺与否，等开发接近完成 / 要签单 / 要上架 / 要正式对外时再定。

### C.1 判定口径

| 判定 | 含义 |
| --- | --- |
| **应收回** | 其实该做，收回通用方案（`N` 目标） |
| **待数据** | 源数据暂不可得（如 JSON 未出口），**数据到位即纳入**，不是永久排除 |
| **进度项** | **现在没做（开发进度），不当作"不承诺"、不当作排除**；成熟后再定承诺口径 |
| **设计选择** | 出于语义 / 架构 / 红线的主动决定，不是"还没做" |
| **单列** | 不放进通用方案，作为独立 roadmap 项 |
| **做不了** | 技术 / 合规上做不到 |
| **红线保留** | 定位 / 铁律，不改 |
