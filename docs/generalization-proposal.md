## 0. 背景与动机

- **现状**：平台当前 `WorkItem` / 后端 `work` 模型与客户端 UI 均为「内容 / 作品型」设计；第一个接入站 Otaku 是动漫作品站。已实现的端点（列表 / 详情 / 同标签推荐 / 封面 / 收藏 / 排序 / 标签 / 搜索）全是浏览作品范式。
- **目标（负责人 2026-10-23 确认）**：平台要能服务「真·任何**条目型、可公开只读抓取**」的站——作品 / 影视 / 图书 / 资讯 / 电商商品 / 论坛帖子 / 博客，而非仅作品型。
- **矛盾点**：现有 `WorkItem` 字段（`title / summary / release_year / cover / tags / rating / work_type`）把内容语义焊死；客户端 UI 为作品设计。接电商（价格 / SKU）或论坛（作者 / 回复数）会卡住，硬塞会丢信息或语义错乱。
- **本文主张（未来方向）**：用**最小侵入的两层抽象**（公共集 + `custom_fields` + `display_template`）让平台从「作品型底座」演进为「通用条目型底座」，**不推倒重来、不破坏已验证的逻辑**——**这是未来演进方向，当前不实施**。

---

## 1. 范围与边界

**适用**：任何「条目型 + 可公开只读抓取」的站。

**明确排除**（不纳入本期，部分由铁律约束）：
- 纯交互型（聊天 / 游戏 / SaaS 后台）——不适合快照模型；
- 需登录才能看的内容（**铁律：不抓登录后内容**）；
- 需回写的站（**铁律：只读、不回写、不代持凭据**）。

**不破坏的既有约束**：
- 三条铁律、快照语义（「抓不到 ≠ 已删除」、来源侧消失不删库）；
- W3 已定口径：`cover_source_url` / `rating_*` / `release_year` / `summary` 字段**不动**，封面 2.7% / 评分 36.2% 的覆盖率结论不受影响。

## 2. 核心设计

### 2.1 数据模型：最小公共集 + `custom_fields`（后端 `work` 表）

**保留公共字段（一字不改）**：`source`、`source_id`（唯一键 `uk_work_source`）、`source_url`、`title`、`cover_source_url`、`cover_cache_key`、`cover_cached_at`、`work_type`、`tags(JSON)`、`rating_*`、`release_year`、`summary`、时间戳。

**新增一列**：`custom_fields JSON` —— 站点专属字段容器。
- 作品型站：`custom_fields` 可空或存扩展（bangumi 关联已由 `source_id` 承载，无需进 JSON）。
- 电商站：`price` / `sku` / `stock` 进 `custom_fields`。
- 论坛站：`author` / `replies` / `last_reply_at` 进 `custom_fields`。

**约束**：
- `custom_fields` 只存**展示用**字段，不参与主键 / 快照唯一性（主键仍为 `source + source_id`）；
- 写入遵守现有幂等 merge（`NULL` 不覆盖、同 `source_id` 重跑恒定）；
- 不引入站专属结构化列（避免 `work` 表膨胀）；确有「按某字段筛选 / 排序」需求时，单独提案将该字段升为结构化列（见 §2.4 例外）。

### 2.2 站类型与字段映射（同步层）

- 引入「站类型」`station_type`（枚举，初期 `generic` + `acg` 即可，其余按需扩展：`book` / `shop` / `forum` / `blog` …）。
- 适配器配置增加**字段映射规则**：声明「来源字段 → `custom_fields` 的 key / 类型 / 清洗方式」。公共字段（`title` / `cover` / `source_url` / `work_type`）仍走现有 `to_work_item` 硬映射，或后续平滑改为声明式。
- **新增站成本** = 写 `Source` 类（拉取 + 限流 / 重试 / 失败记账复用）+ 声明字段映射。抓取层已解耦，这部分轻量。

### 2.3 客户端渲染：`display_template`（属 W1，最大投入）

- 后端为每个作品返回 `display_template`（初版 = `station_type` 或独立字段）。
- 客户端按模板渲染：
  - `work`：现有作品 UI 原样保留；
  - `generic`：**兜底模板**——标题 + 封面 + `custom_fields` 键值列表渲染，保证任何新站「看得过去」、不裂图不空白；
  - 后续按需加 `product` / `thread` 专用模板。
- 初期只实现 `work` + `generic`，新站进来至少有可用呈现。

### 2.4 端点演进

- 列表 `/api/works`、详情 `/api/works/{id}`、搜索：返回「公共集 + `custom_fields` + `display_template`」，**保持通用，不新增站点专属端点**。
- **例外（不在本期）**：若某站需按 `custom_fields` 某字段做结构化筛选 / 排序（如「按价格排序」），需将该字段升为结构化列 —— 这一步触红线 1，单列提案确认，不夹在通用化里。

## 3. 分阶段实施

| 阶段 | 内容 | 交付 | 触红线 |
|---|---|---|---|
| **0（未来启动）** | 启动通用化时：确认架构 + 落契约（`custom_fields` 列、`station_type`、`display_template`、映射约定） | 本文件 + 契约文档更新 | 是（数据结构） |
| **1（最小证实）** | 接一个**非内容型**第二站（论坛帖子 / 电商商品），用 `custom_fields` + `generic` 跑通 同步→入库→列表→详情 | 端到端打通 + 痛点记录 | 否（用现有抽象） |
| **2（深化）** | 据阶段 1 痛点，决定是否加 `product` / `thread` 模板、是否升结构化列 | 模板 / 列演进 | 可能 |
| **3（客户端打磨 W1）** | 多模板渲染稳定，体验对齐各站类型 | 多模板 UI | 否（W1 内部） |

**阶段 1 不依赖生产服务器**：可在开发机 / 本地用只读公开 API 验证，符合「服务器先按没有算」的决议。

## 4. 对现有契约 / W3 口径的影响

- **W3**：封面 / 评分字段不动；`custom_fields` 不影响已定覆盖率结论（封面 2.7% / 评分 36.2% / 简介 84%+）。W1.5 兜底验收（D1 稳定占位）依旧成立。
- **契约（红线 1）**：需更新 [`openapi.yaml`](openapi.yaml) 与 [`stage1-minimal-contract.md`](stage1-minimal-contract.md) —— 新增 `custom_fields`、`display_template`、`station_type` 字段与语义。
- **客户端（W1）**：需新增 `generic` 模板，由 @riceyu02 排期协调（W1 主责）。

## 5. 代价与风险（如实列）

- **客户端多模板是最大投入**，且归 W1（@riceyu02），需跨工作流协调排期。
- `custom_fields` 是 JSON 列，**按它筛选 / 排序能力弱**——确有需求时得升结构化列，触发后续 schema 演进。
- 数据结构变更触红线 1，须三人确认，不实然改库。
- 阶段 0–1 不依赖生产服务器，可在开发机验证。

## 7. 结论

用「最小公共集 + `custom_fields` + `display_template`」两层抽象，让平台从「作品型底座」平滑演进为「通用条目型底座」：**不破坏现有已验证的作品型逻辑与 W3 口径，用接第二站来驱动深化，避免凭空 over-engineering（YAGNI）**。通用化的真实成本在客户端多模板（W1），数据层改动极小且可逆。

> **当前状态重申**：本文仅为未来目标存档，**不立即实施**；已落地的作品型逻辑、字段、契约与 W3 口径保持不变（「以前做的先不改」）。后续任何架构或数据结构决策**须兼容本方向**——即在新增站点 / 调整模型 / 扩展端点时，预留 `custom_fields` + `display_template` 的演进空间，不把内容语义再次焊死。
