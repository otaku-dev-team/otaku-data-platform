# 数据库直读：从客户库里取数而不是爬

> 结论先行：**能从库里拿就别爬，但拿的方式要选对**。首站（同机 SQLite）走「派生库只读」，
> 第三方客户走「一次性开放窗口 + 我们自己的导出器」，两者共用同一个中间格式 `sync-dataset`。
> 结构强耦合的解不是「让客户别改表」（做不到），而是**把耦合压进一个声明式映射文件**，
> 并让破坏性变更停机。

## 一、为什么不是「让网站开放接口」

爬取面只剩两块，但都很贵：

| 数据 | 现状 | 代价 |
| --- | --- | --- |
| 作品列表 / 档期 | 已有 JSON 接口（`/api/contents`、`/api/schedule`） | 无，已消费 |
| 详情富字段（原名/别名/媒介/话数/制作/放送/Staff/声优/系列/企画） | **只在 HTML 里** | 1.8 万条 = 1.8 万次请求，站点 42% 的页会断连 |
| 资讯 | `/api/articles` 404，**只有 HTML** | 列表 + 详情双倍请求，且要跟着模板改 |

而这些字段**站点库里本来就有**（`contents` 21 列 + 5 张关联表），只是没进 JSON。
为它们做 1.8 万次 HTML 请求，是在为「接口没出口」付重复的代价。

## 二、两个正交的维度：交付形态 ≠ 数据入口

这里最容易犯的错，是把「私有化部署」当成「能拿到库」。这两件事无关：

- **交付形态**回答「东西装在哪」：我们托管，还是交付到客户环境。
- **数据入口**回答「数据从哪来」：同机库、短窗口派生库，还是 REST。

私有化客户完全可以把网站放在云上、把我们的系统放在自己机房——不同机、拿不到库，数据仍走
REST；反过来持续服务模式下首站同机，却能直接读库。**决定入口的只有一件事：客户能不能、
愿不愿意让我们读到他的库**，与交付形态无绑定关系。

因此取数形态按「入口」分档，不按「部署模式」分档：

| 数据入口 | 成立条件 | 安全边界 | 效率 |
| --- | --- | --- | --- |
| **同机派生库只读** | 网站与后端同机（首站现状、客户自建） | 好：库物理上不含用户表 | 最好：文件读，秒级 |
| **短窗口派生库** | 跨机但客户愿意开窗口（第三方常见） | 好：同上，且窗口结束即失效 | 好：一次全量，之后靠增量 |
| **REST 接口** | 客户不给库（含私有化但不同机） | 最好：按需授权、可限流、可审计 | 受分页与限流约束 |
| 直读生产库 | 不采用 | **差**：SQLite 无授权体系，等于拿到整数库 | 最好 |

三条可用入口**汇流到同一个 `sync-dataset` 收敛层**（§三），下游导入通道不变。所以
「私有化在客户里占多数还是少数」不改变架构，只改变**先实现哪一条增量机制**——这个未知
不需要提前赌（见 [`open-decisions.md`](open-decisions.md) B5）。

### SQLite 的硬限制（这是选型的关键，不是偏好）

MySQL 可以 `GRANT SELECT` 到某几张表；**SQLite 没有账号与授权体系**——谁有文件读权限，
谁就能读整库。首站的库里同时躺着 `users`（密码哈希）、`oauth_tickets`、
`app_access_tokens`、`content_favorites`、`persona_reports`、`email_verification_tokens`、
`phone_verification_codes`。

所以「给我们一个只读账号」在 SQLite 上不存在。**只能物理隔离**：网站侧用
`VACUUM INTO` 生成一份只含公开内容表的派生库，我们只读那份。敏感数据是「拿不到」，
不是「不去拿」——后者靠自觉，前者靠结构。

> 跨机（第三方客户）时，客户给的是**一次性开放窗口**（dump 文件 / 临时只读账号），
> 我们用自己的导出器在窗口内跑完，之后靠增量维持。窗口期拿全量，长期靠轻量出口。

## 三、结构耦合怎么解

「客户别改表」是幻想。真实风险是两种，分开治：

| 风险 | 表现 | 治不了会怎样 |
| --- | --- | --- |
| 列/表消失或改名 | `SELECT col` 直接抛异常 | 整批导入失败，或静默拿到错主键 |
| 取值/类型漂移 | `type` 从"动画"改"anime"、评分从十分制改百分制 | **不抛异常，静默写坏数据**——比崩更危险 |

### 四层，各管一段

1. **标准数据集（`sync-dataset v1`）**：12 张表，schema 由我们定义并版本化。
   客户有 90 个字段也是这 12 张表——每站独有的富字段进 `works.extra_json` /
   `work_facts`（键值表，天然容纳任意事实）。**绝不为某个客户新建列**，
   否则每接一站就改一次我们的表，耦合只是换了个地方疼。
2. **声明式映射（`mappings/*.json`）**：源表 → 标准字段。接新客户只加一个文件，不改代码。
   能 join 的关系用一条 SQL（`mode: query`）表达，不给映射语言自造 DSL——
   多一种语法就多一处要维护、要测试的东西。
3. **三档缺列处置**（照抄 Airbyte 的 schema change management）：
   - `degrade`：置空继续。富字段、可选字段用它。
   - `reject`：该行拒绝。标题这种「有了才成立」的字段用它。
   - `break`：**整批停机**。主键与增量游标必须用它。
     > 为什么必须有 `break`：主键列被改名时若按 degrade 放行，我们能导出一张
     > 「能写入、但每条都指向错主键」的表，导入器会当成全量新增，
     > 静默产生几十万条重复脏数据。崩掉远比这个结果好。
4. **结构指纹 + 质量统计**：表/列/类型的稳定哈希（只算公开表，客户新增日志表不误报）。
   每字段记空值率、类型转换失败数、越界数、未知枚举值。数据照收，但报告里必须现形。
   空值率告警设最小样本量（50 行），否则小表全是噪音，真信号被淹。

### 破坏性变更默认拒绝落盘

`BreakingSchemaChange` 抛错时**一个字节都不写**（先写 `.tmp` 再 `os.replace`，
未成功就不产出）。越过需要显式 `--allow-breaking`，并且报告里会写明「已越过 N 项」。

## 四、参照的工业实践（为什么不直接用一个）

| 项目 | 星 | 判断 |
| --- | --- | --- |
| dlt | 5.4–5.9K | 能力最对口（SQL 源 + schema evolution + incremental），但会拉进 sqlalchemy/alembic/pendulum 约 10 个依赖；产物带 `_dlt_*` 元列、嵌套自动展开，形态不受我们控制，最后仍要写 transform |
| Airbyte | 15–20K | 每个 connector 跑独立 Docker 容器 + JVM 平台 + 元数据库。我们 2C2G（磁盘 51%、跑着 MySQL+后端+网站）跑不动 |
| dbt | 10K+ | 需要 warehouse/adapter，重 |
| sqlite-utils | 2.2K | 只管写入/upsert/transform，不管 schema 映射与演化 |
| Singer / Meltano | 高 | 比 dlt 更重 |

**没有能直接用的**，原因很实在：它们的目标端都是数据仓库（Snowflake/BigQuery/DuckDB），
而我们的目标端是**自家 REST 后端 + 9 字段契约**。它们追求「全量原样入仓」，
不负责「把 90 个字段收敛成 9 个」——那层契约收敛只有我们自己能写。

抄的是三样东西：Airbyte 的四档处置、dlt 的 `SchemaEvolutionError`（破坏性变更要抛错
不要静默）、dbt 的「映射用 SQL 表达」。

## 五、落地状态

已实现（`sync-python/src/sync/dataset/`）：

| 文件 | 职责 |
| --- | --- |
| `schema.py` | 标准数据集 12 表 DDL + 版本 + 源表白名单/禁区 |
| `mapping.py` | 映射加载与校验、结构探测、指纹、三档降级 |
| `exporter.py` | 一致性快照、类型转换、质量统计、原子落盘、版本校验 |
| `mappings/otaku.json` | Otaku 的映射（`contents` 21 列 + 5 张关联表 + 资讯 + 档期） |

CLI：

```bash
python -m sync --export-dataset \
  --source-db /opt/acgn-test-platform/local_dev.db \
  --mapping src/sync/dataset/mappings/otaku.json \
  --dataset-out runs/dataset.db
```

本机实测（网站库开发规模副本，11 作品 / 13 标签 / 6 资讯 / 6 档期）：
49 行，结构指纹 `8e99573f3965f427`，一致性快照成功，13 项 dataset 测试 + 全量 213 项绿。

已确认打通：`work_type` 中文→契约枚举、`rating_scale` 常量、`title_original`
（`/api/contents` 永远不给的原名）、`alias`/`media`/`episodes` 等富字段，
以及 `articles.body` 正文——资讯不再需要解析 56 KB HTML。

## 六、待办

1. **`contents` 没有 `updated_at`**（实测 21 列里只有 `meta_fetched_at`）——
   增量同步的前提是源侧补这一列或加触发器，否则只能全量重扫或内容哈希比对。
   这是整件事唯一需要改客户表结构的地方。
2. **MySQL 源**：第三方客户多为 MySQL，需要 `information_schema` 探测 + 可选驱动
   （`pymysql` 纯 Python）。当前只实现 SQLite，接口已按「探测函数可替换」预留。
3. **导入器接线**：数据集 → 现有 `POST /internal/import/batches`（后端零改动，
   `works` 前 9 列就是 ImportItem）。`work_tags` 聚合成 `tags[]` 在导入侧做。
4. **线上规模实测**：线上约 299 页 × 60 ≈ 1.79 万条（未实测确认），
   派生库体积与耗时待服务器上跑一次再定，不按估算写死。

## 七、边界

- 数据集**只收公开内容**：源表白名单 + 禁区检查（`users`/`token`/`favorite`/`persona`
  等命中即拒绝构建映射），`articles` 按 `is_published = 1` 过滤未审核草稿。
- 搬库**替代不了日常增量通道**：库只在窗口期可读，长期仍需要一个轻量出口
  （每天一个快照文件，或 REST + `updated_since`）。
- 库入口**不能替代接口入口**：第三方客户不可能长期给库，库只在窗口期或同机时成立，
  多站通用的兜底仍是接口。
- 但库入口**也不是私有化专属**：判据是「是否同机」，不是「是否私有化」。把这两件事
  混为一谈，会在私有化客户不同机时算出错误的交付预估（见 §二）。
