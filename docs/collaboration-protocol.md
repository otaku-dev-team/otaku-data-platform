# 协作协议：并行开发 · 阻塞不停车

> 生效：2026-10-27 ｜ 修订：2026-10-27（新增 §1.5「确认默认同意」，PR 是通知不是闸门） ｜ 负责人：zm ｜ 适用：otaku-data-platform 全员与协作智能体
>
> 上位依据：[`project-charter.md`](project-charter.md)（模块自主权 §3.1、红线 §3.2、合并平等 §3.5、看板 §6）；[`deployment-schedule.md`](deployment-schedule.md)（预建项与并行流）。
> 本文不新增授权、不改动红线，只把"多方向并行时遇到阻塞怎么处理"写成可执行的约定。

---

## 0. 一句话原则

**多方向并行是常态；遇到阻塞先上报、立刻切到别的能做的开发，绝不空等。**

阻塞多半来自外部（服务器采购、同事公钥未回、合同未签），不归当前干活的人控制节奏。空等浪费排期；上报是为了让对的人知道，切走是为了保住进度。

**补充（2026-10-27，zm 定调）：PR 是通知，不是闸门。** 发 PR 即视为已通知全体，默认所有人知悉并同意；**沉默不构成阻塞，不需要催、也不需要等任何人点头**。这条覆盖本节与 §1 里的"第三人确认未到"一类——那种等待本身就是多余的。

---

## 1. 阻塞分三类，应对不同

| 类型 | 典型例子 | 动作 |
|---|---|---|
| **外部阻塞** | 服务器采购审批、同事公钥/出口 IP 未回、合同未签 | 在对应 issue/PR 公开上报 → 立刻切到不依赖它的开发 |
| **依赖阻塞** | 等另一模块产出（如客户端烘焙链等后端 base url 约定、等适配包 CI 先落地） | 上报"等什么 / 谁负责" → 先做完本模块**不依赖那部分** |
| **红线阻塞** | 需三人确认的跨模块/数据结构变更（§3.2） | 上报并**停下该项**（不绕过）→ 切到其他非红线开发 |

核心：**除红线外，阻塞不停工**；红线类阻塞只停那一项，不停全局。这与 [`project-charter.md`](project-charter.md) §3.2 末句一致——"发起（确认）不等于等待批准，可以先做不影响他人的准备工作"。

---

## 1.5 确认默认同意（PR 是通知，不是闸门）

> **2026-10-27 zm 定调，团队默认执行。**

| 情形 | 规则 |
|---|---|
| 提 PR 征求意见 / 求复核 | **默认所有人同意**。PR 发出来即已通知，未回复 = 无异议 = 通过 |
| 催确认、等人点头 | **不催、不等**。反复 ping 不会改变对方的外部节奏，还会把排期卡在形式上 |
| 「三人确认」类事项 | 按 §3.5 执行即可：合并门槛只有 **CI 全绿 / 不碰红线 / PR 里说清楚** 三条，**任何一人可合任何人的 PR**（含自合）。不需要专门去收集三个人的签字 |
| 真有异议 | 在 PR 里直接写明分歧与依据，先按"对来源站与用户最有利、且不破坏铁律"的方案执行（§5 决策原则），分歧记档后修 |

**这条不放松红线本身**：§3.2 的四类红线仍然是边界，触碰了仍要按流程走；只是**"确认"不再是一个需要等待的闸口**。换句话说：**确认 = 知悉，不是审批**（章程原文），知悉默认可得。

**冲突归作者解，不代劳**：分支与 main 有冲突时，由 PR 作者 rebase / 解冲突。这是他的分支与他的代码，平台侧不代改（章程 §3.1 模块自主权）。平台侧该做的是**把根因与可操作信息给到作者**（哪几个文件、与 main 哪些提交撞了），让他能自己快速解掉。

## 2. 上报规范

- **渠道：只在 GitHub**（issue 评论 / PR 评论），不私下找同事。项目惯例是 GitHub 单一协作场所（见 §6），私聊会让阻塞状态对团队不可见。
- **四要素**：①卡在哪；②为什么卡（缺什么 / 等谁）；③我已做了什么规避或准备；④预估何时能解 / 需要谁动。
- **语气**：陈述事实，不催促、不重复 ping。对的人看到自然会动；重复 at 不会改变对方的外部节奏。
- 上报即视为"我已把阻塞交出去"，之后该干别的干别的。

---

## 3. 切走到哪

- 优先从 [`deployment-schedule.md`](deployment-schedule.md) 的预建项清单里挑**当前不阻塞、且属于自己模块或已获授权**的项。
- 切走前在 issue/PR 留一句："先切到 X，阻塞项等 Y"——让团队知道你没消失，只是换了活。
- **模块自主权不变**（§3.1）：别人模块的事不替做，仍走 issue 指派 + 负责人自开工。切走的开发必须落在自己负责范围内，或已按流程取得授权。
- 如果所有"自己模块且不阻塞"的活都做完了，再回头看阻塞项有没有松动；仍然没松动就如实标注"全部在等外部"，不硬上。

---

## 4. 与现有铁律不冲突

- 三人确认、不代合、不代签、"确认 = 知悉非审批"、密钥不入库——**全部照旧**（§3.5、§3.2）。§1.5 明确的是「确认默认同意、沉默不阻塞」，**不是取消红线**：§3.2 四类红线仍是边界，触碰仍要按流程走，只是不必再等一个形式上的点头。
- "马上继续其他开发" **不等于** "绕过阻塞硬上"：红线类该停就停，只是停一项不停全部。
- 合并平等（§3.5）不变：能合的门槛仍是 CI 全绿 / 不碰红线 / PR 说清楚；阻塞期间别人合了的 PR，自己回来时先 `git fetch` + 对齐 main，再继续。
- **冲突由 PR 作者自己解**（§1.5 末段）：平台侧不代改别人的分支，但要把根因信息给到作者。

## 5. 已按此运转的实例（备查，非新规）

- **预建四条并行流 A/B/C/D**：A（后端运维，#195→@pyxz0）、B（客户端烘焙，#196→@riceyu02）、C（CI 剥离校验，随 #195）、D（sync VNDB，zm 自领）。互相独立，任一阻塞不影响其余。
- **#193 / #190（作品年份筛选 / 设备令牌端点）**：zm 以契约主责确认，CI 全绿。按 §1.5，**不再等第三人点头、不催**；实际卡点不是确认而是**分支与 main 冲突**（#208 标签词表改了同样的 `WorkRepository`/`WorkService`/`CountCache`/`WorkController`），由作者 rebase 解。
- **P7 VNDB 适配器（zm 自有模块）**：契约 §4.6 允许「加适配器 + 一个 source 取值」且 source 取值不受限，故 openapi/后端/客户端零改动，不构成契约变更 → 不进红线流程，CI 绿后按 §3.5 自合。
- **服务器采购（P1）外部阻塞**：属 W6 休眠项，按"服务器先按没有算"的决议（§7）不阻塞其他工作流；采购到位前，依赖它的 P2/P3/P4 可先写代码（不依赖真机），但不能验收。

## 6. 给协作智能体（agent）的提醒

- 你是"助手"不是"第六个人"：代发上报评论、代建 issue 可以，但**不替模块负责人写他们的代码、不代合 PR**。
- 检测到阻塞时：先在对话里向 zm 说明"卡在哪、建议切到哪"，由 zm 确认后再行动；不要自作主张跨模块开工。
- 切走后保留上下文：把"哪几项在等什么"记进项目日志（`.workbuddy/memory/`），下次回来不丢状态。
