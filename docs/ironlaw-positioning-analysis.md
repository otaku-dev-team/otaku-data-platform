## 0. 一句话结论

当前契约把"平台 ↔ 来源站"的关系写成**单向供给**（网站 → 平台 → 客户端），
与负责人定的真实定位——"我们服务来源站及其用户、且用户要能无缝回到相应来源站"——**叙事相反**。

技术约束（只读 / 不回写）本身正确，需改的是**叙事口径**，并补一个让"回流"能落地的
`source_url` 字段。

---

## 1. 问题是什么（Problem）

### 1.1 矛盾点一：叙事把来源站摆成了"上游供给方"

铁律 1（`stage1-minimal-contract.md` 第 38 行）原文：

> 1. **单向**：网站 → 平台 → 客户端。平台**不向网站回写任何数据**，客户端**不直接访问网站**。

`plan-v2.md` 第 91 行标题：

> **## 4. 现有网站如何服务于项目**

这两处都把来源站定位成"服务项目的供给者"，平台是被动接收方。
这与负责人定位相反：我们是用来源站的公开数据，**去服务来源站的用户**，不是被喂数据。

### 1.2 矛盾点二：契约里没有"用户回流"的位置

负责人要求："我们基于来源内容吸引来的用户，也必须能一键无缝回到相应来源站原页。"
但当前契约：

- 没有任何"回到来源站原页"的机制或字段；
- "客户端不直接访问网站"被当成铁律，没有区分"不抓取数据"和"不阻止用户跳转回流"；
- 等于默认把用户**锁在平台内**（围墙花园），与"无缝回网站"直接冲突。

### 1.3 矛盾点三：多来源站（多客户）前提缺失

未来可能接入多个来源站。届时"回流"必须**按来源站对应**（A 站作品回 A 站原页），
当前契约没有这个口径，只在第一阶段单站语境下写死。

---

## 2. 原因是什么（Root Cause）

1. **起草时的焦点偏差**：阶段 1 契约起草时（2026-10 初）焦点是"最小闭环 + 数据边界"，
   于是把重点放在"我们只拿作品元数据、不碰网站用户数据"，措辞自然成了"单向 / 网站服务我们"。
   当时还没做阶段 2（账号 / 收藏），"平台是来源站体验增强层 / 用户服务层"这个产品定位没写进契约。

2. **定位散落、未统一**：其实 `README.md` 第 1 节已经是"面向多个独立网站的跨平台方案、各站独立运营"，
   反而更正确；但契约（铁律 1）和 `plan-v2.md` §4 没同步，导致"供给叙事"残留。

3. **"不回写"被误读为"隔离 / 锁住"**：旧措辞没区分两件事：
   - 平台**不抓取 / 不回写数据**——对来源站边界的尊重，**必须保留**；
   - 平台**不阻止用户跳转回来源站**——这是回流，**是鼓励的**。
   旧措辞把两者混为一谈，使"回流"在契约层面没有立足之地。

4. **技术事实从未变**：平台对来源站只读、不代持凭据、不直连库、不抓登录后内容、
   客户端不直连抓取——这些一直是对的，只是叙事把它们讲成了"主从 / 被供给"。

---

## 3. 现在的方案（Solution，草案）

### 3.0 原则（负责人定）

1. 我们服务来源站及其用户（增强层，不强求迁移 / 重复录入）；
2. 基于来源内容吸引来的用户必须能**一键无缝回到相应来源站原页**（非围墙花园）；
3. 多来源站时，回流按 `source` **对应到各自来源站**（A 站作品回 A 站原页），
   复用已有的 `(source, source_id)` 两层标识与 §4.6 / §9 多站扩展。

### 3.1 铁律 1 重写（`stage1-minimal-contract.md` 第 38 行）

**旧：**
> 1. **单向**：网站 → 平台 → 客户端。平台**不向网站回写任何数据**，客户端**不直接访问网站**。

**新（草案）：**
> 1. **来源站边界（尊重，非主从）**：平台以**只读**方式从来源站取得公开作品元数据，
>    **不向来源站回写、不代持来源站凭据、不直接连接来源站数据库、不抓取登录后内容**——
>    这是对来源站边界的**尊重与服务前提**，不是主从关系。
>    **非围墙花园（双向流转）**：平台是来源站的**体验增强层 / 用户服务层**，取公开数据是为给来源站的用户
>    提供更优的浏览、检索、收藏与跨端体验；来源站既有用户可顺滑使用平台，
>    **我们基于来源内容吸引来的用户也必须能一键无缝回到相应来源站原页**。
>    客户端**不直接访问来源站**仅指禁止**抓取数据**，不禁止**用户在浏览器跳转回来源站**
>    （回流正是鼓励行为）；未来多来源站时，回流须按 `source` **对应到各自来源站**。

### 3.2 新增 `source_url` 字段（让"回流"可落地）

**现状**：详情接口返回 10 字段
（`work_id`、`work_type`、`title`、`summary`、`cover_url`、`tags`、`main_rating`、`source`、`source_id`、`updated_at`），
**没有来源站原页地址**，"回流"无法在客户端实现。

**新增（草案）：**
- §2.1 字段表增加一行：

  | 字段 | 类型 | 必填 | 谁产生 | 说明 |
  | --- | --- | --- | --- | --- |
  | `source_url` | string | **可空** | **Python 提交** | 来源站作品原页地址，用于客户端「在来源站查看 / 回流」入口；由 Python 按适配器 `base_url` + 该 `source` 的详情页路径模板推导；客户端可在此地址打开浏览器跳转回来源站原页（非数据抓取）；无则 `null` |

- §6.2 详情响应：把 `source_url` 纳入返回字段。
- 列表接口（③）**不加**该字段（保持 6 字段精简，回流入口放在详情页即可）。

### 3.3 `plan-v2.md` §4 重写（第 91 行标题 + 开头）

**旧标题：** `## 4. 现有网站如何服务于项目`

**新标题（草案）：** `## 4. 来源站的角色：平台如何服务来源站及其用户`

**开头重写方向（草案）：** 协作关系 / 非围墙花园 / 多站按源回流；
下方 4.1、4.2 小节保持不变。示例开头：

> 现有网站：[Otaku](http://154.8.194.198:8000/)。其角色是首批作品数据来源与产品参考，原有网页继续独立运营。
> 平台不是来源站的替代品，更不是锁住用户的围墙花园——平台取来源站公开数据，是为了**给来源站的用户提供更优的
> 浏览、检索、收藏与跨端体验**，并让用户能**一键无缝回到相应来源站原页**。
> 我们与来源站是协作关系：来源站既有用户可顺滑使用平台（不强求迁移或重复录入）；
> 我们基于来源内容吸引来的用户，也始终保留回到来源站的入口。平台对来源站只读、不回写、不代持凭据，是尊重与服务前提。

### 3.4 `README.md` §1（第 7–16 行）

定位已是"面向多个独立网站、各站独立运营"，**基本已对齐**，
建议补一句："平台不锁住用户：用户在平台内可一键无缝回到相应来源站原页（非围墙花园）。"

## 4. 改了的后果 / 影响面

- **保留不动的**：所有技术底线（只读、不回写、不代持、不直连库、不抓登录后、客户端不直连抓取）。
  这些是对来源站的尊重，不因叙事反转而去掉。
- **真正新增的工程项只有 `source_url` 一个字段**，横跨三个模块：
  - Python：按 `base_url` + 该 source 详情页路径模板推导并提交；
  - Java：存储并在详情接口返回；
  - Flutter：渲染「在来源站查看」回流按钮。
  属跨模块结构变更，**必须三人确认**。
- **已落地代码不受影响**：阶段 2 实现已绕过旧措辞；本次仅改文档叙事 + 加一个可选字段。
- **落地前提**：需确认来源站**人读详情页 URL 路径**。
  契约目前只文档化了 API 路径 `/api/contents/{id}`，未文档化网页路径（如 `/contents/{id}`）。
  需站主确认路径模板，或先用 API 地址兜底。

## 6. 实现差距结论（第三步产出，2026-10-21）

只核对现有适配器、详情响应模型与测试，**未改任何业务代码**，结论如下。

### 6.1 已具备的能力（无需新增）

- **Python 侧 `source_url` 字段已存在**：`sync-python/src/sync/models.py:35`
  `SourceRecord.source_url: str | None = None`。
- **两个适配器均已生成该值**：
  - Otaku（`source.py:168`）：`f"{base_url}/api/contents/{source_id}"` —— 这是 **API 地址，不是人读原页**；
  - Bangumi（`bangumi.py:178`）：`https://bgm.tv/subject/{id}` —— **真实人读原页**，可直接用。

### 6.2 现有缺口

| 环节 | 现状 | 是否需改代码 |
|---|---|---|
| Python 提交（接口②） | `models.py:70–76` `to_payload()` 只输出 7 个字段，注释明确 `source_url`「仅作本地记录，**不提交**」 | 是（本模块，约 1 行） |
| Java 详情响应 | `WorkDto.java` 仅 10 个字段，**无 `source_url`** | 是（@pyxz0） |
| Java 数据模型 | `WorkRecord.java` **无 `sourceUrl` 列**（DB 仅有 `cover_source_url`，无来源原页列） | 是（@pyxz0，需迁移还是适配器计算待定） |
| 客户端 | 无「在来源站查看」入口；`null` 时不应显示 | 是（@riceyu02） |
| 测试 | `test_source.py:41` 断言 API 地址；`test_bangumi.py:143` 断言 bgm 地址 | 视后续口径决定是否调整 |

### 6.3 结论（本次不实现，仅给差距）

1. **契约层已完成**（本次修订）：`source_url` 已定义为详情响应可空字段，列表接口保持 6 字段不变。
2. **代码层存在真实缺口**，涉及 Python、Java、Flutter 三端，属跨模块变更，需三人确认后分步实现。
3. **Otaku 站当前值是 API 地址而非人读原页**。按契约新规则「不能通过猜测生成地址」，
   需与站主确认人读详情页路径后再决定：**替换为真实原页**或**置 `null`**。
   Bangumi 适配器已是真实原页，不受影响。
4. 兼容性决定已写入契约：**不因该字段立即做数据库迁移**，由架构方决定是适配器计算还是后续持久化。
