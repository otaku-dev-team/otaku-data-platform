# 首站收录口径与资讯过滤（存档）

**这份文档存的是首站的口径，不是我们的实现规格。**

为什么单独存档：这几条规则的**唯一真相源在首站的代码里**——`scripts/import_bangumi.py`
的 `is_acgn_game_payload()`、`scripts/news_filters.py` 的三条规则。首站改了，我们不会
自动知道；而「这部作品为什么在库里」「这条资讯为什么被挡掉」的答案全在这里，事后
没有第二处可以查。

所以这份的作用是**分叉锚点**：给一个「首站当时是这么定的」的可核对快照，配 §5 的
核对命令。发现对不上时，先怀疑首站变了，再怀疑我们记错。

- 归档时间：2026-11-01
- 口径定稿时间：游戏收录 v3 = 2026-10-23；资讯三条规则 = 2026-10-25
- 上游位置：首站仓库 `scripts/import_bangumi.py`、`scripts/news_filters.py`

---

## 1. 游戏收录口径 v3（2026-10-23 定稿）

入口：`scripts/import_bangumi.py` 的 `is_acgn_game_payload(payload) -> (bool, str)`，
返回「是否收录 + 命中的分类文案」。**纯标签 / 标记判定，不联网。**

### 1.1 五类优先级（顺序即优先级，第一条命中就返回）

| # | 分类文案 | 判据 | 说明 |
|---|---|---|---|
| 1 | `galge/视觉小说` | `GALGAME_TAG_RE` 命中 tags | 只读 tags，不出网 |
| 2 | `原作关联(选品标记)` | `payload["_site_related_ip"] is True` | **外部打的标记**，不是本函数算的 |
| 3 | `改编/联动` | `ADAPTATION_TAG_RE` 命中 tags | 改编 / 原作 / 漫画化 / 动画化 / 小说原作 / 游戏化 / 联动 / コラボ |
| 4 | `二游/动漫风` | `ANIME_STYLE_TAG_RE` 命中 tags | 手游 / 二次元 / 动漫 / 美少女 / 乙女 / 女性向 / BL游戏 / 恋爱 / ADV |
| 5 | `日式RPG/同人独立` | `(JRPG_TAG_RE 或 INDIE_TAG_RE)` **且** `_japanese_signal()` | 两个条件必须同时成立 |
| 6 | `宽泛兜底(高rank)` | `MARGIN_TAG_RE` 命中 **且** `1 ≤ rank ≤ 1000` | 用于捞头部边缘作品 |
| — | `非ACGN向游戏` | 以上全不中 | 不收录 |

`rank` 取自 `payload["rating"]["rank"]`，且必须是 `int`（显式排除 `bool`——Python 里
`True` 是 `int` 的子类，不挡会让 `rank=True` 被当成 1 通过）。

### 1.2 判定词表的原文

```python
GALGAME_TAG_RE     = gal\s*game|ギャルゲ|美少女游戏|美少女ゲーム|visual\s*novel|视觉小说
ADAPTATION_TAG_RE  = 改编|原作|漫画化|动画化|小说原作|游戏化|联动|コラボ|コラボレーション
ANIME_STYLE_TAG_RE = 手游|手机游戏|二次元|动漫|美少女|乙女|女性向|BL游戏|恋爱|ADV
JRPG_TAG_RE        = RPG|角色扮演|日式|日系|JRPG|冒险|奇幻|科幻
INDIE_TAG_RE       = 同人|独立游戏|サークル|社团
MARGIN_TAG_RE      = 日本|同人|社团|独立|萌|悬疑|恐怖|音乐|节奏|格斗|射击|策略|
                     模拟|养成|经营|建造|解谜|像素|治愈|校园|奇幻
JP_SIGNAL_RE       = [\u3041-\u3096\u30a1-\u30fa]|日式|日系|日本|ジャパン|Japan
MARGIN_MAX_RANK    = 1000
```

全部大小写不敏感。`JP_SIGNAL_RE` 的字符区间是平假名与片假名——**文件名 / 译名里出现
假名**也算日系信号，不只看标签。

### 1.3 三个结构要点

1. **顺序就是优先级，不是加权求和。** 一条 galge 标签足以让「带 RPG 标签但不日系」的
   作品进库；反过来，同时带 `MARGIN_TAG_RE` 和低 rank 也可能被第 5 类先接走。
   加分类时只能往中间插，插错位置会改变已有条目的分类文案。
2. **`_site_related_ip` 是外部标记。** 全流程两段：选品端先用本函数做免联网预过滤，
   未命中的再联网查原作关联、打上这个标记、重跑一次；服务端 `map_subject` 的总闸
   同样调本函数。**两端口径完全一致，标记不可伪造绕过。**
3. **兜底类刻意限 rank。** 不加 rank 限制会把「日本产的一切游戏」全收进来；
   1000 是「上线后据实可调小」的起始值。

### 1.4 口径之外：为什么不扩到所有游戏源

2026-10-25 用户定过一条边界：**不要把游戏准入闸门扩到所有游戏源**。「普通游戏的
联名 / 行业综述」这类内容按资讯侧的三条规则处理（见 §3），不在收录口径里管。

## 2. 配套：非游戏条目怎么判

游戏口 v3 只管 `type == 4`。其余类型走 `resolve_book()` / `resolve_content_type()`，
**同属进口径，一并记下免得只记一半**。

| Bangumi `type` | 落库 `content_type` | 规则 |
|---|---|---|
| 2 动画 | `anime` | 直接收 |
| 4 游戏 | `game` | 再过 §1 的 v3 五类 |
| 1 书籍 | 看 `platform` | 见下表 |
| 3 音乐 / 5 三次元 / 6 真人 | — | **不收** |

书籍按 `platform` 细分：

| `platform` | 结果 |
|---|---|
| `1001` / 字符串含「漫画」 | `comic` |
| `1002` / 「轻小说」 | `novel`，`book_kind = light_novel` |
| `1002` / 「小说」 | 走 `classify_book()` 再判 |
| `1003` 画集 / `1004` 其它 | **丢弃** |

`classify_book()` 的判定顺序（强 → 弱）：

1. tags 里有「轻小说」→ `light_novel`
2. infobox 有文库 / レーベル 字段，或值命中已知轻小说文库（電撃文庫 等）→ `light_novel`
3. 日本出版物（日文假名 / 日系出版社）→ `literature`（**日本普通小说**）
4. 中文出版社写法 → 丢弃（中译本、欧美古典、中国古典名著都在 Bangumi 的
   「小说」platform 里，本站不收）

两个已固定的取舍：

- **`book_kind` 是标注，不是第五种类型。** 2026-10-19 曾把文学拆成独立类型，后来退回：
  用户视角两类都在「轻小说区」翻，拆类型要动导航 / 筛选 / 统计 / 我的空间的类型枚举，
  换来的只是角标能表达的一眼区分。
- **启发式宁可留、不可误删。** 边界件判成 `literature` 留在站内（可见、可人工改），
  也好过漏判成轻小说污染轻小说区，更不要误删一本真日本书。

一个实现细节值得记：「出版社」的判定**只看 infobox 的值，不看键名**——infobox 里键名
就叫「出版社」，把键一起算进来会让每一本书都被判成中文书。

## 3. 资讯三条过滤规则（2026-10-25 定稿）

入口在 `scripts/news_filters.py`。需求原话两条：**「普通游戏的联名不在乎」**、
**「网站的自营信息我们不要」**。

### 3.1 三条规则

| 规则 | 函数 | 判据 | 为什么这么写 |
|---|---|---|---|
| **源站自营** | `self_op_reason(source_key, title, summary)` | 按源查 `SOURCE_SELF_OP_WORDS` | 媒体自办活动 / 自家周边 / 自家会员体系，**不是资讯** |
| **周报 / 一周综述** | `weekly_digest_reason(title, summary)` | 命中 `_WEEKLY_DIGEST_WORDS` 即拒 | 标题把一周新闻堆一起，**没有单一事件** |
| **普通游戏的联名周边** | `collab_merch_reason(title, summary, terms)` | 联名标记 × 实物形态 × **没有 ACG 证据**，三件齐备才拒 | 普通游戏外设联名与 ACGN 无关 |

### 3.2 三个设计选择（改之前必须看）

**(a) 自营词表按源分表，不塞总词表。**

```python
SOURCE_SELF_OP_WORDS = {
    "gcores": ("核聚变", "核电波", "核聚变游戏节", "核市奇谭", "ggg", "机核商城", "机核会员"),
}
```

「核聚变」是机核的自办展会品牌。塞进总词表的话，**别的源报道机核活动**也会被一起
挡掉——那是正经资讯。所以按 `source_key` 查表：只说「本源自营」，不说「这个词有毒」。

**(b) ASCII 品牌词用单独的边界规则。**

自营词命中用 `_self_op_word_in_text()`：ASCII 词**只要求左侧边界**。因为「GGG完整曲目
与阵容公开」「gpass会员」是常态写法，右边直接接中文；而词表通用的双边界规则（为
`tga` 那种字母偶然组合设计）会漏掉它们。

**(c) 周报规则不看内容，命中即拒。**

触乐「本周行业大事：…《塞尔达传说》重制版公开新预告…」曾被分类器判成「重大官宣」
（`major=2`，命中「重制+公开」）走了豁免额度入库。**堆砌里提到作品名不等于官宣**，
所以这条规则一旦命中栏目名就直接拒，不再看它提到了什么。

### 3.3 联名规则：ACG 证据表刻意不收泛词

判据是 `联名标记 × 实物形态 × 没有 ACG 证据`。ACG 证据 = 站内 ACGN 游戏词表命中
（作品名 / 别名 / 系列 / 角色 / 创作者），**或** `_COLLAB_ACG_SIGNALS` 强体裁信号命中。

```python
_COLLAB_MERCH_MARKS = 联名|聯名|联动款|限定款|纪念款|コラボ|コラボレーション
_COLLAB_MERCH_GOODS = 手柄|键盘|鼠标|鼠标垫|耳机|机箱|游戏手柄|周边|手办|公仔|
                      抱枕|立牌|徽章|挂件|联名款|コントローラー|ゲームパッド|...
_COLLAB_ACG_SIGNALS = ギャルゲー|ビジュアルノベル|ノベルゲー|乙女|美少女|魔法少女|
                      変身ヒロイン|アニメ化|アニメ|动画|ノベライズ|コミカライズ|ゲーム化
```

**`_COLLAB_ACG_SIGNALS` 刻意不收「角色 / キャラクター / 动画 / 恋愛 / アイドル」这类泛词。**
这是上线当天踩出来的坑：本地用例用空摘要测「八位堂 × 古墓丽影联名手柄」正确拒绝，
上服务器一条都没命中——因为当时拿 `_GAME_ACG_SIGNALS` 当证据，那张表里有泛词「角色」，
而那条文章摘要写着「她不是游戏里一个虚拟的**角色**」，被当成 ACG 证据放行了。
现在用真摘要钉住：用例 `test_generic_role_word_is_not_acg_evidence`。

### 3.4 作用域：只对媒体源的「游戏」类生效

```python
_MEDIA_RULE_SOURCE_TYPES = ("媒体编译",)
_MEDIA_RULE_CATEGORY     = "游戏"
```

对外入口 `media_game_rule_reason()` 先判作用域，不匹配直接返回 `None`。**官方 PR
（作品方自己发的活动 / 纪念公告）与动画 / 漫画 / 轻小说 / 综合动态的既有判定完全
不变**——这三条规则只补「媒体写游戏类内容」这一块。

暴露对外入口的另一个目的：**存量清理脚本与抓取链路共用同一份口径**，规则改一处
两边同时生效。

## 4. 改口径时的联动点

口径不是一个函数，是「词表 + 规则 + 调用点 + 清理脚本」四件绑在一起：

| 改什么 | 还要改哪里 |
|---|---|
| 加自营品牌词 | `SOURCE_SELF_OP_WORDS[source_key]` 加一行即可；新源要新键 |
| 换周报栏目名 | `_WEEKLY_DIGEST_WORDS`——触乐靠栏目名命中，换名（如「一周要闻」）要补词 |
| 改收录分类 | 只能往 §1.1 的优先级中间插，插错位置会改已有条目的分类文案 |
| 改任一条资讯规则 | 存量已入库的不会自动重判，要跑 `cleanup_news_junk.py`（默认预览，`--apply` 必须带 `--backup`） |
| 扩作用域 | 动 `_MEDIA_RULE_*` 前先想清楚「官方 PR 会不会被误伤」 |

`cleanup_news_junk.py` 的设计：扫全库命中即删（文章 + 标签 / 作品 / 实体关联；
收藏行按 `ArticleFavorite` 的设计保留），复用同一批函数。

## 6. 与我们的关系：只跟取数，不复刻口径

**我们这边不复刻这几条规则。**

- works / people / work_cast / articles / schedules 都已经通过 `mappings/otaku.json`
  同机直读首站的库——**进没进库由首站判，我们读结果**。自己再实现一套只会出现两套口径。
- 首站继续演进资讯管线时，我们要跟的是**取数通道**，不是搬代码。
- 只有一件事会用到这些知识：将来做「搜索语义解析」时需要题材同义词（`GENRE_ALIASES`
  60 条 + `GENRE_KEYWORDS` 38 条），那时只搬这两张，不动收录与过滤规则。

所以这份存档的用途只有一个：**回答「为什么」。** 有人问「这部游戏为什么不收」
「这条资讯为什么没上」，答案在这里，不必去猜。
