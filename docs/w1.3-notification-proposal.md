## 1. 目标与验收的拆解

原文（[`client-enhancement-plan.md`](client-enhancement-plan.md) §6）：

> E1 客户端能采集并在登录后注册设备令牌。E2 触发事件时用户收到系统通知。
> E3 点击通知正确跳转到对应内容。E4 登出 / 换设备时令牌失效或解绑。

这四条**全部是「服务端推送」的验收**——它们默认「通知由服务端发起」。W1.3a 走的是另一条链（设备本地排程），所以它需要自己的验收，而不是拿 E1–E4 硬套。

| 验收 | 含义 | 落在 | 现在能否验证 |
|---|---|---|---|
| E1 | 登录后注册设备令牌 | W1.3b | 后端端点就绪后 |
| E2 | 触发事件收到系统通知 | W1.3b | **需部署（#78）**，本地联调只能验「送到 FCM」，验不了「用户收到」 |
| E3 | 点击通知跳转正确 | W1.3a / W1.3b 共用深链路由 | 可用桩载荷本地验 |
| E4 | 登出 / 换设备令牌失效 | W1.3b | 端点就绪后 |
| **F1** | 追更作品在播出日收到本地提醒 | W1.3a | **需真机** |
| **F2** | 未标记 `watching` 的作品不提醒 | W1.3a | 单测可验 |
| **F3** | 关闭开关后不再提醒，已排程的取消 | W1.3a | 单测 + 真机 |
| **F4** | 档期数据缺失时**不排程、不推断「今天没更新」** | W1.3a | 单测可验 |

> F1–F4 是 W1.3a 的验收口径，由我在 W1 内自定（章程 §3.1）；不替代、也不放宽 E1–E4。

## 3. W1.3a · 本地提醒（建议先做）

### 3.1 形态

> 每天固定时刻一条：「今天有 N 部在追的番更新」

不按播出时刻逐条提醒，**按天汇总一条**。

**为什么是汇总而不是逐条**：

1. `broadcast_time` 是站点原文（形如 `P 22:00`，见 [`站点能力差距清单.md`](站点能力差距清单.md) 第 125 行），**时区语义未定义**。按它算具体时刻，等于替数据编一个假设。
2. 逐条精确提醒在 Android 12+ 需要 `SCHEDULE_EXACT_ALARM` 权限；汇总提醒用不精确闹钟即可，差十几分钟对「今天有更新」这件事没有影响。
3. 用户的真实问题是「今天有什么可看」，不是「22:00 整要打开 App」。

### 3.2 数据流

```
collections(status == watching)  ∩  schedule(当前季度, work_id != null)
    → 未来 14 天逐日：weekday 命中？→ 当天固定时刻排一条本地通知
```

- 每次 App 启动、收藏变化、档期刷新时重算并重排（先 `cancelAll` 再按新结果排）。
- 只排**未来 14 天**，不做无限重复：档期按季度变，长期重复会在换季后继续报旧番；14 天覆盖「两周没打开 App」的常见情况，超期自然停止。
- `work_id` 为空的档期条目**跳过**——它连本地详情都跳不了，提醒了也点不进去。

### 3.3 边界（与铁律对齐）

- **数据缺失不排程，也不发「今天没有更新」**。抓到 0 条可能只是没同步过，不能替数据下结论（铁律 3）。
- 通知只写「N 部」与作品标题，**不含来源站任何用户数据**（铁律 2）。
- 只用平台已返回的档期响应，不新增对来源站的访问（铁律 1）。
- 桌面端先 **no-op**：Windows 本地通知需要 AUMID / MSIX 打包配合，会牵动 W6（部署，当前休眠），不在这一轮范围。桌面用户暂时没有提醒，这一点会写进看板，不假装有。

### 3.4 客户端改造点

| 项 | 说明 |
|---|---|
| 通知网关抽象 | 接口 + Android 实现 + 桌面 no-op，测试注入假实现（照 `WorkCache` 的分层范式） |
| 权限 | Android 13+ 首次开启开关时申请 `POST_NOTIFICATIONS`；拒绝后开关保持关闭并说明原因 |
| 开关 | 放「设置」页（已有 `/settings`），设备级、**不按账号分桶**——和主题同类，是这块屏幕主人的选择 |
| 排程 | 纯逻辑部分（哪天有更新、跳过哪些条目）抽成可测函数，不依赖插件 |

## 4. W1.3b · 设备令牌端点（契约草案，需确认）

### 4.1 端点

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/me/devices` | 注册或更新本设备令牌（upsert） |
| `GET` | `/api/me/devices` | 列出本账号已登记设备（**不返回 token**） |
| `DELETE` | `/api/me/devices/{device_id}` | 解绑本设备（幂等，204） |

**为什么是 `/api/me/devices` 而不是 `/api/devices`**：个人数据已经在 `/api/me/collections` 下有先例；`/api/devices` 会被读成「平台的设备目录」，语义不同。原文 §6 给的两个选项中，这个更一致。

### 4.2 请求与响应

`POST /api/me/devices`（Bearer 鉴权，复用 `AuthFilter`）

```json
{
  "device_id": "3f2b9c1e-...",     // 客户端生成，安装级；重装后变
  "platform": "android",            // android | windows（ios 预留）
  "provider": "fcm",                // fcm | apns（预留）
  "token": "<provider 下发的令牌>",
  "app_version": "1.4.0+12",        // 可选，排查用
  "enabled": true                   // 可选，默认 true
}
```

响应 `200`（已存在则更新）/ `201`（新建）：

```json
{
  "device_id": "3f2b9c1e-...",
  "platform": "android",
  "enabled": true,
  "created_at": "2026-10-23T12:00:00Z",
  "updated_at": "2026-10-23T12:00:00Z"
}
```

**响应永不回显 `token`**：那是凭据，客户端本来就有，回显只增加泄露面。

`GET /api/me/devices` 返回同一形状的数组；`DELETE` 返回 `204`（设备不存在同样是 204，与收藏删除的幂等口径一致）。

### 4.3 语义（这几条比字段名重要）

1. **upsert 键是 `(user_id, device_id)`**，不是 token：token 会轮换，`device_id` 不会。
2. **`token` 全局唯一，跨账号转移**：同一台设备换账号登录时，新账号注册同一 token，**旧账号的这条记录必须失效**。否则前一个用户退出后，这台设备仍会收到他的推送——这和收藏缓存按账号分桶是同一类问题，只是后果更直接（通知会显示在锁屏上）。
3. **token 轮换**：客户端在 `onTokenRefresh` 时重新 `POST`，服务端按 `device_id` 覆盖。
4. **失效不删**：provider 返回 `UNREGISTERED` / `INVALID_ARGUMENT` 时置 `disabled_at` 并停止发送，保留记录便于排查；由清理任务在保留期后清除（照 `SessionCleanupJob` 的范式）。
5. **每账号设备上限**（建议 10），超出返回 `409 DEVICE_LIMIT_EXCEEDED`，避免无限登记。
6. **`DELETE` 幂等**，重复删同样 204。
7. **登出时客户端主动 `DELETE`**，然后才撤销会话：`POST /api/auth/logout` 的语义不动（它不知道 device_id，加参数就是改契约）。删失败不阻断登出。

### 4.4 表（若批准）

```sql
-- Flyway 版本号待定：main 当前到 V7，#102 占 V8、#109 占 V9，本表取 V10；
-- 落库前需按实际合并顺序复核一次（版本号是共享资源，后合的必须更大）。
CREATE TABLE IF NOT EXISTS user_device
(
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     BIGINT UNSIGNED NOT NULL COMMENT 'app_user.id',
    device_id   VARCHAR(64)     NOT NULL COMMENT '客户端生成的安装级标识',
    platform    VARCHAR(16)     NOT NULL COMMENT 'android | windows | ios',
    provider    VARCHAR(16)     NOT NULL COMMENT 'fcm | apns',
    token       VARCHAR(512)    NOT NULL COMMENT 'provider 下发的令牌，视同凭据',
    app_version VARCHAR(32)     NULL,
    enabled     TINYINT(1)      NOT NULL DEFAULT 1,
    created_at  DATETIME(3)     NOT NULL,
    updated_at  DATETIME(3)     NOT NULL,
    disabled_at DATETIME(3)     NULL COMMENT 'provider 判失效的时间；不删除，保留排查',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_device (user_id, device_id),
    UNIQUE KEY uk_device_token (token),
    KEY idx_device_user (user_id, enabled),
    CONSTRAINT fk_device_user FOREIGN KEY (user_id) REFERENCES app_user (id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci COMMENT '推送令牌按安装登记，跨登录存在';
```

### 4.5 为什么不用 `user_session` 承担

会话是「一次登录一行、退出即撤销」，令牌是「一块安装一个、跨登录存在」。硬塞进会话表会导致两个方向都错：退出登录后令牌跟着被撤销（下次登录前收不到），或者为了保住令牌而不撤销会话（撤销语义被污染）。

顺带说明：`user_session.device_label` **不能**直接当 `device_id` 用——它只是展示用的自由文本，且现在恒为 NULL（§2）。这次也不打算回填它，属于另一件事。

### 4.6 provider 选型（现实约束）

- **FCM**：标准、免费，但境内 Android 无 GMS 时不可靠，投递无法保证。
- **国内厂商通道**（个推 / 极光 / 各 OEM 推送）：需要商务账号 + 多套 SDK，成本远大于本轮收益。
- **结论**：`provider` 字段先留位，实现押后。若届时仍要推，建议**先只覆盖有 GMS 的设备**，并在文档里如实写明覆盖率，不承诺「全设备可达」。

## 5. 事件与载荷（W1.3b，一并冻结形状）

```json
{
  "v": 1,
  "type": "new_works",
  "batch_id": "2026-10-23-01",
  "count": 42,
  "work_id": null
}
```

- `v`：载荷版本。以后加字段不改 `type`，客户端按 `v` 决定能否解析。
- `type` **未知时**：照常展示通知，点击进首页——不认识就忽略，不能让旧客户端崩在解析上。
- `work_id` 有值且本地库存在 → 进详情；否则进首页（**不造死链**，与档期页「跳不了就只展示」同一条规则）。
- `count` 只用于文案，客户端不作为业务依据。
- **限频**：每用户每天最多 1 条；同一 `batch_id` 不重复推（服务端按批次去重）。
- 通知标题与正文由服务端出，客户端不改写（改写在多语言时会分裂成两套文案）。

## 8. 不做什么（防方案膨胀）

- **不做关注 / 订阅模型**：`watching` 已经存在，就是用户表达「在追」的方式，不再造第二套。
- **不做通知历史 / 收件箱 / 未读红点**：那是另一个产品功能，不是「触达」。
- **不做富媒体、分组、免打扰时段**：免打扰交给系统 DND。
- **不做 iOS**：本仓库没有 iOS 端，APNs 无从谈起（`provider` 字段只是留位）。
- **不做桌面推送**：FCM 不覆盖 Windows，本地通知要 AUMID/MSIX，等 W6。
- **不做站内信 / 邮件兜底**。
- **不做按标签 / 系列的定向推送**：需要用户兴趣模型，现在没有。
