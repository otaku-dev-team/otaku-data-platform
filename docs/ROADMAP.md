定位问题：契约铁律 1 把关系写成「单向：网站 → 平台 → 客户端」，`plan-v2` §4 标题为「现有网站如何服务于项目」——把来源站摆成上游供给方，与「我们服务来源站及其用户」的真实定位相反，且不支持用户回流。

### 8.1 分支与 PR 清理规则（2026-10-22 定）

**合并后的分支不代删。** 远端残留分支一律**开 PR 交原作者判断**（关闭 / 补回 / 放着），由作者自己合并或关闭——涉及别人的分支，代删会影响对方的本地工作区与分支视图。

例外：**零差异**的已合并分支（内容 100% 在 main，删除不丢任何东西）可直接清理，但需在 PR 或记录中留痕。

**判断"内容是否已在 main"不能只看 diff 形态**：squash 合并 + 后续重构会让 diff 显示成「新架构 vs 旧架构」的双向差异（`+N/-M`），看起来像 main 缺功能，实际是分支停在重构之前。要逐文件核对能力（函数、字段、结论是否已在 main 存在），而不是只看行数。
