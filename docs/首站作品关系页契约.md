## 一、制作公司页 `/studios/{name}`（数据齐，只缺端点）

### 首站怎么做的

- 路由 `@router.get("/studios/{name}")`，`name` 就是公司名本身，**没有 id**，路径段 urlencode（`business_pages.py:1059` → `studio_detail`）。
- 查询 = `content_studios JOIN contents ON content_id`，`name` **精确等值**（`crud.list_contents_by_studio`，`crud.py:1484`）。不模糊、不前缀、不走标签。
- 排序 `rating DESC, id DESC`。
- **不截断**，返回该公司全部作品；头部写「本站收录 N 部该制作公司的作品（按评分排序）」。
- 查不到 → **404 页**（`page_common.render_missing`，`status_code=404`），不是空态页。
- 卡片就是全站海报卡（封面 / 类型签 / 标题 / 评分 / 收藏 / 年份）。**没有「职责」行**——`content_studios` 只有名字，没有 per-work 职责（`studio.html` 注释原话）。

### 我们这边

- `work_studios` 生产 **4,269 行**，与首站 `content_studios` 4,270 行同源同字（导入即该表，见 `V15__work_relations.sql`）。
- 客户端详情页已经有「制作公司」一行（`work_detail_page.dart:475`），但是纯文本、不可点。
- **缺的只有反查端点**，没有别的。

### 建议契约（形状归 pyxz0 定，我不代签）

```
GET /api/studios/{name}
→ { "name": "京都アニメーション", "total": 42, "items": [WorkSummary …] }
```

- 名字按 NFKC + strip 归一后等值匹配（与首站 `normalize_entity_name` 同规则，`crud.py:2263`）。**大小写敏感**——`A-1 Pictures` 和 `a-1 pictures` 是两家公司，别做 `LOWER()`。
- 查不到 → 404，错误码建议 `STUDIO_NOT_FOUND`，与作品不存在同款语义（不给探测接口）。
- 排序 `rating_value DESC, work_id DESC`；可见性口径直接复用列表（成人 / 已下架 / 未收录剔除），不另立规矩。
- **与首站的一处有意的不同**：建议带 `limit`（默认 60）+ `total`。首站是全量不分页，但「动画制作」这类名字下可能几百部，客户端是二级页，一次全给不划算。这条要不要接受由 pyxz0 定，我不替他拍。

### 客户端

详情页「制作公司」一行改成可点 → 公司页。公司页照 `studio.html`：标题 + 一行计数 + 海报卡网格。**别造空态页**——首站直接给 404，我们保持一致。

## 二、系列页（数据没落地，端点可以先写）

### 首站怎么做的

- 系列是独立表 `series(id, name)`，作品侧只有 `contents.series_id`，**一部作品最多属于一个系列**（`models.py:1167`）。
- 系列页是 `/creators/{name}` 的系列视图：`rating DESC, id ASC`，`limit=60`（`business_pages.py:1126` → `crud.list_series_contents`）。
- 详情页「系列作品」区是**两个来源合并**（`crud.list_series_section`，`crud.py:2728`）：
  - 真实关系：`content_relations` 的前作 / 续作 / 衍生作，双向查询后**归一到本作视角**（A 是 B 的续作 ⇒ B 是 A 的前作）；
  - 同系列：`series_id` 相同，标「同系列」；
  - 两边重复时**关系标签优先**，`series_id` 只做兜底。
- 排序：前作 / 续作（档 0）→ 衍生作（档 1）→ 同系列（档 2）；**同档内年份升序**（年份空排最后）、再按 id 升序。
- 详情页推荐区会**排除系列区已经出现的作品**，两个区块不重复占位（`business_pages.py:928` 附近）。

### 我们这边

- `GET /api/works/{id}/series` 已有（#411，`WorkSeriesDto` = `{seriesKey, name, items}`），语义与首站一致，**不用改**。
- 但生产 **`series` 0 行、`work.series_key` 全空** → 这个接口现在对所有作品都返回 `series_key=null` + 空 items。首站那边 `series` 有 941 行。
- 客户端详情页**没有「系列作品」区**（`grep -r series lib/features/detail` 零命中），后端这个接口目前没人调。

### 按顺序要做的三件

1. **数据先落地**（我领）：数据集 v3 已定义 `works.series_key` 与 `series(series_key, name)`，publisher 也有产出逻辑（`sync-python/src/sync/dataset/publisher.py:287` `_series_names_for`），缺的是一次重发 + 导入。这一步没跑完之前，系列相关的页面在端上就是空的——**空是预期，不是 bug**，别在空库上验。
2. **端点**：`GET /api/series/{key}` → `{key, name, total, items}`。系列名查不到**不算错**（作品先到、系列行后到，首站一样给 null 语义）。
3. **客户端**：详情页系列区（用已有 `/works/{id}/series`，但要做到关系标签得后端先把 `relation` 带出来，现在只给 items）+ 系列页。

### 别抄这个 bug

首站系列页头部写「共 `len(contents)` 部作品」，而 `contents` 已经被 `limit=60` 截断——**超过 60 部的系列，页面上的数字是错的**（`creators.html` 系列视图）。我们给 `total` 单独一个字段，数字从总数的来源取。

## 三、作者 / 公司索引 `/creators`（先查一个数再定）

### 首站怎么做的

- `/creators` 索引页两块（`business_pages.py:1076` → `creators_index`）：
  - **实体花名册**：`entities JOIN content_entity_links` 按实体分组计数，`count DESC, name ASC`；chip 上带**类型徽标**（个人 / 公司 / 协会）+ 计数。
  - **系列列表**：`series JOIN contents` 计数，`count DESC, name ASC`；chip 上只有名字 + 计数。
- `/creators/{name}` 的消歧顺序（`business_pages.py:1097` → `creator_detail`）：**先按实体名查**，命中就是实体页；否则**按系列名查**；**都不中 404**。两条都是 NFKC + strip 精确匹配，大小写敏感。
- 实体页每张卡多一行「职责」（这部作品里他是原作 / 动画制作 / 导演…，同一作品多个职责全带上，`crud.py:2505` → `list_entity_contents_with_roles`）；系列页没有这行。
- 实体页有「查看全部作品 →」，跳 `/contents?creator={name}`；列表页要支持 `creator` 筛选参数。

### 我们这边

- `people` **19,399 行**（有 `entity_type` 列）、`work_staff` **183,388 行**、`work_characters` **75,745 行**。首站侧是 `entities` 17,919 行 + `content_entity_links` 46,498 行。
- 没有「按名字查实体」，也没有「实体 → 作品（带职责）」的端点。人物页只支持按 `person_id` 查。
- **有一个数我还没拿到**：`people.entity_type` 里公司 / 协会各占多少。生产查询被云侧命令通道拦了两次。没查到就不当已知——这个数决定索引页做多大（首站的实体是 1.7 万行，真要平铺就不是一屏 chip 的事）。

### 我的建议（最小路径，待定）

- 人的索引（声优 / Staff）走 `people`；**公司不另建 entities 等价表**，直接用 `work_studios` 的 distinct name + 计数。公司页本来就用这张表，两个入口一个真相，少维护一套同步。
- 索引页先只给「计数前 N（比如 200）+ 搜索」，不做全量平铺。
- 以上三条要等 `entity_type` 分布查清再定，这份里不拍。

## 四、人物页 `/cast/{person_id}`（两端都有，只对齐口径）

- 首站（`business_pages.py:1006` → `cast_detail`）：按 Bangumi person_id 反查 `content_credits` 与 `content_cast`，各自 `rating DESC, id DESC`；**按作品合并成一行**，每行两个 persona 行「配音」「职责」；头部三处计数（参与作品 / 配音记录 / 制作记录）；**无 limit**；查不到 404。
- 我们：`GET /api/persons/{personId}` 已有（#455），`PersonDetail` 的形状注释就写着「照来源站 `cast_detail()` 定」，`personId` 当**不透明字符串**（`bgm:` / `pname:` 前缀键，见 `docs/person-id-unification.md`）。
- 剩下的是客户端对齐：每卡两行 persona、头部三处计数用服务端给的 `castCount` / `creditCount`，**别在端上数**（端上数会把「一作品多职责」重复计）。

## 五、验收（不读源码也能验）

| 打开 | 期望 |
| --- | --- |
| 详情页点「制作公司」 | 进公司页，标题是公司名，卡片按评分从高到低 |
| 公司页换个不存在的名字 | 404，不是空白页 |
| 公司页某公司只有 1 部作品 | 就是 1 张卡，没有空行、没有空态文案 |
| 公司名大小写改一位 | 404（大小写敏感），不是模糊命中 |
| 详情页有系列的作品 | 「系列作品」区顺序：前作 / 续作 → 衍生作 → 同系列，同档内年份升序 |
| 推荐区 | 不出现系列区已经展示过的作品 |
| 系列页 | 同系列作品按评分降序；超过 60 部时头部数字是**总数**，不是 60 |
| `/creators/{name}` | 实体名与系列名同名时，**走实体页**（先实体后系列） |
| 人物页 | 头部三个数；配音和职责都有的同一部作品只出现一张卡 |
