## 3. 重复：三类，只有一类需要处理

### 3.1 跨源同名 —— 设计内

13,261 组标题同年份同时存在于两个来源（例：《永远的大和号 REBEL3199 第七章》
bangumi 一条 + otaku_site 一条）。这是「多来源并存」设计的必然结果，
`source` + `source_id` 层面没有任何重复（重复组 0），**导入幂等是正确的**。

副作用（要处理）：`/related` 同标签推荐会把这两条都返回，推荐位出现同一作品
两次。修法在后端：related 按标题去重，或客户端展示层合并。属观感问题，不是数据错误。

### 3.2 bangumi 内部同标题同年份 —— 源数据特性

3,577 组。抽样看是 bgm.tv 自身就有的多条目：`_summer`（subject 562748 / 28430）、
`.hack//世界的彼方`（30302 / 149998）—— 不同条目页、不同 ID，可能是不同版本
或重复创建的条目。**没有脚本化的判据**能自动区分「真重复」和「不同版本」，
人工抽样判断成本高于收益，建议保持原样（列表里看到两条同名，点进去内容不同，
用户能自己分辨）。

### 3.3 问号标题 —— 虚警

10,537 条标题含问号（bangumi 10,393 + otaku_site 144）。看着像字符集损坏
（`?` 是乱码的典型形态），实际抽查 `HEX()` 证明是**全角问号 U+FF1F**
（`EFBC9F`），如「请问您今天要来点兔子吗？」。标题本身合法，**不用修**。

## 4. 异常与边界值（均判定为合理）

| 现象 | 数量 | 判断 |
| --- | --- | --- |
| `rating_value = 10` | 10,351 | bgm 小众高赞作品的常见形态；不影响正确性，但会让「评分最高」排序前几名扎堆满分 |
| `release_year > 2026` | 253 | 未播出/预定条目，合理 |
| `release_year < 1950` | 1,016 | 早期动画/漫画，合理 |
| `tags` 含 `/` | 19 | 正常标签文本（如「OVA/剧场版」），非格式错误 |
| `summary` > 2000 字 | 11,803 | 上限是 64K，无越界风险 |

## 5. 真缺口（按影响排序）

### 5.1 bangumi 零封面 —— 最大

`cover_source_url` 覆盖率 0.0%（原因见 Issue #61：档案包 `subject.jsonlines`
字段里没有 `images`）。直接后果：57 万条里 97% 的条目在列表里是占位图，
**上线前不解决会很影响观感**。补法待调研（官方是否另有含 images 的 dump /
能否批量取）。

### 5.2 评分覆盖偏低

bangumi 只有 34.4% 有评分。「评分最高」排序对 65% 的条目无效（沉底）。
如果上线主打排序，要么接受、要么补抓评分（成本高，不建议）。

### 5.3 related 同名重复

见 3.1。小改动，可顺手修。

## 6. 结论

**数据本身可以对外用**：无损坏、无越界、幂等正确，标题/年份/标签覆盖都在
79%–100%。要带上线的两件事：① 封面缺口要么先补、要么在上线清单里写明
「97% 条目无封面」；② related 去重（小修）。

搜索命中率（只有 `title LIKE`）不在这份体检范围内，但它和封面一样属于
「对外可用性」问题，建议单独评估。
