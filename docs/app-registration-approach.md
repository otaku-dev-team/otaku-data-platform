# App 内注册的技术方案（不依赖网站开发）

> **状态**：方案已定（2026-10-25，负责人拍板依据：不要求网站提供开发能力、产品体验不妥协）。
> 上位依据：[`product-positioning.md`](product-positioning.md) §4、[`open-decisions.md`](open-decisions.md) 备查表。
> 相关：[`site-owner-console-proposal.md`](site-owner-console-proposal.md) §3.1 / §8.1、Issue #173。

---

## 1. 三条硬约束（本方案必须同时满足）

| # | 约束 | 来源 |
|---|---|---|
| 1 | **不要求网站提供开发能力**——不能用"请站点开放注册 API"作为前置 | 负责人 2026-10-25 |
| 2 | **产品能力不妥协**——App 内要能完成注册，不能靠"引导用户自己去网站"交差 | 定位 + 拍板 |
| 3 | **不撞铁律**——绝不代收用户密码转发、绝不持网站服务凭据 | 定位：授权关系判据 |

## 2. 实测事实（2026-10-25 只读探测，未提交、未建号）

网站**已有完整的注册能力**，只是返回 HTML 而非 JSON：

| 端点 | 方法 | 用途 | 响应 |
|---|---|---|---|
| `/register` | GET | 注册页 | `text/html` |
| `/register/code` | POST | 发送邮箱验证码（`email` / `username` / `invite_code` / `next`） | `text/html` |
| `/register` | POST | 提交注册（`username` / `password` / `confirm` / `email` / `code` / `invite_code` / `next`） | `text/html` |

- **两步流程**：先"发送验证码"（邮箱收码）→ 再"完成注册"。
- **表单字段已知**：`username` / `password` / `confirm` / `email` / `code` / `invite_code` / `next`。
- **校验规则写在页面上**（`data-min-user=3` / `data-max-user=50` / `data-min-pwd=6` / `data-max-pwd=128`）。
- **无 CSRF token**（唯一隐藏域是 `next`）——少一个脆弱依赖。
- ⚠️ **`next` 不接受外部指定**：传任意值服务端一律回写 `value="/"`（防开放重定向，是正确实现）。因此**不能**靠 `next` 直接跳到授权地址，必须改用导航监听（见 §3）。

结论：**不需要网站做任何开发**——它现有的 HTML 注册流程已经够用。

## 3. 方案：App 内 WebView 承载网站注册页

### 3.1 流程

```
用户在 App 点「注册」
  → App 内 WebView 打开网站 /register
  → 用户在网站的页面里填：用户名 / 密码 / 确认密码 / 邮箱 / 邀请码
  → 点「发送验证码」→ 网站发邮件（仍在该 WebView 内）
  → 用户查邮箱取码、填回 → 点「完成注册」
  → 网站注册成功并跳转（next 强制为 /），网站会话 Cookie 建立
  → App 监听导航事件，判定注册完成
  → App 随即发起 OAuth authorize（网站已登录 → 幂等静默重定向）
  → 回到 App（com.otaku.app:/oauth2redirect?ticket=…）→ 平台后端换令牌 → 建会话
```

用户感知：**全程在 App 内完成注册，注册完直接就是登录态**。

> **实现补充（2026-10-28 实测，Issue #238）**：客户端不需要单独拼 `/register`。
> 实测 `/oauth/authorize`（未登录）返回 **303 → `/login?next=<授权完整地址>`**，
> 而登录页里带 `<a href="/register?next=…">` 且 next 被保留。所以 WebView
> **只加载 authorize 一条地址**即可：登录 / 注册由站点自己在同一个 WebView 里
> 路由，注册完成后回到 authorize 再回跳，cookie 全程同域。
> 客户端据此省掉了「先开 /register、再手动发起 authorize」的拼接与判定。
> 见 `app-client/lib/features/auth/site_auth_webview_page.dart`。

### 3.2 为什么这个方案同时满足三条约束

- **不要求网站开发**：用的是它现成的 `/register` 页面与端点，一个字段都不用改。
- **产品不妥协**：用户不离开 App、不手动切浏览器、不重新输一遍账号。
- **不撞铁律**：密码只在**网站自己的页面**里输入并提交，**App 与平台后端都不接触明文密码**——不是"代收密码转发"。

账号创建在网站侧 → 与网站 / App / 站主后台 / 未来形态**天然是同一个账号**，账号全渠道统一原则完整成立。

## 4. 为什么不选「App 原生表单直接 POST」

技术上能做到（无 CSRF、字段明确），但**不可接受**：

1. **撞红线**：用户在 App 原生框里输密码、App 转发给网站，这就是判定依据里明令禁止的**代收用户密码转发**。即使平台后端不落库，客户端已经经手。
2. **脆弱**：响应是 `text/html`，成败只能靠解析 HTML 判断，网站改版即崩——而我们无权要求它保持结构。
3. **收益有限**：邮箱验证码那一步用户本来就得切邮箱，原生表单省不掉这一下。

所以原生表单不是"更好的体验"，而是"用红线换体验"，不换。

## 5. 客户端侧可自主增强的部分（不依赖网站）

以下全部是客户端模块内可决定的实现选择，**不需要网站配合**：

- **视觉融入**：WebView 注入 CSS，隐藏网站导航 / 页脚，只留注册卡片，使其看起来像 App 内页。
- **邀请码**：见 §6。
- **完成判定**：监听导航 / 页面特征判定注册成功；不依赖 `next`（已实测不可用）。
- **注册后自动接授权**：注册完成即发起 authorize，利用"网站已登录 → 幂等静默"直接拿 ticket，省掉用户再登录一次。
- **失败可解释**：邮箱已被占用、验证码错误、邀请码失效等，仍用网站的提示原样呈现。

> 实现细节（用什么组件承载、注入方式、cookie 处理、测试策略）**由客户端模块自主决定**（定位 §7.1），本文件只给边界与路径。

## 6. 邀请码：不是依赖（2026-10-26 更正）

> **更正说明**：初版据"网站是邀请制"推断邀请码为必填，并据此立了 Issue #173。
> 复核注册页原文后确认该推断**错误**，#173 已关闭。

注册页原文（2026-10-26 复核）：

- 「**邀请码（可选）** …… 可以留空直接注册；填了则必须是有效邀请码」
- 「注册账号为**普通用户**，仅能浏览内容平台；**若需管理员权限，请向站长索取管理员邀请码**」

结论：**普通用户注册不需要邀请码，可留空直接提交**。邀请码只与**管理员权限**有关——那是站主后台（见 [`site-owner-console-proposal.md`](site-owner-console-proposal.md) §4.1 站主名单）要考虑的事，与 App 注册无关。

因此 **App 内注册没有任何对外依赖**：不需要网站开发，也不需要站主发放任何东西。

## 7. 网站不可用时的降级与责任边界

> 由负责人提问引出（2026-10-26）：方案把注册承载在网站页面上，**网站挂了怎么办**？

### 7.1 先承认一条物理约束

账号必须创建在**网站侧**（这是账号全渠道统一的硬原则）。因此**网站不可用时，无法创建网站账号**——这不是方案缺陷，而是"账号统一"的固有代价，任何方案都改变不了，除非引入第二套账号。

### 7.2 明确不做什么

**不为此引入平台账号兜底。** 用一个永久性的架构代价（第二套账号、账号不再统一）去换一个低频场景（注册），不划算：注册是一次性动作，网站恢复后重试即可；而账号一旦分裂就再难合回。

### 7.3 影响面要分级（不是"网站挂 = App 挂"）

| 谁挂了 | 影响 | 严重程度 |
|---|---|---|
| **网站**挂 | 只影响两个**低频**动作：新用户注册、已退出用户重新登录。**已登录用户不受影响**——平台会话令牌在有效期内照常工作，客户端离线能力保证断网仍可浏览已缓存内容 | 中 |
| **我们自己的后端**挂 | 全功能不可用（连浏览都做不了） | **高**（属 Issue #78 生产化范畴） |

### 7.4 客户端该做的降级（全部不依赖网站）

- **注册前先探测**：打开注册页前先确认网站可达；不可达就**直接给明确状态**（"网站暂时不可用，请稍后重试"），不让用户填完一整份表单才失败。
- **中途失败要可解释**：保留已填内容、给出明确原因、提供重试；**绝不**静默失败、白屏或无止境转圈。
- **已登录用户不受牵连**：不因网站不可达而强制登出或清空本地数据——与"不把失败当删除"同一条原则。

### 7.5 责任归属与可观测

- **责任**（沿用 B3 口径）：持续服务模式下我们负责**平台侧**运行；**网站本身的可用性由站主保障**——这条须写进合同 / SLA，否则网站挂了会算到我们头上。
- **可观测**：我们已有来源站探测能力（`sync --health`）。网站不可达时我们应比用户先知道，可据此提前提示或临时收起注册入口，而不是等用户来反馈。

---

## 8. 结论

**技术上可解，不需要网站开发，也不需要在体验上妥协。** 关键是认清四件事：

- 网站已有注册能力（HTML 流程 + 邮箱验证码），缺的只是 JSON API——而 JSON API 不是必需的；
- 真正不能碰的是**代收密码**，这条路一票否决；
- **邀请码不是依赖**（普通用户可留空），初版推断有误，已更正；
- 唯一绕不开的是**网站本身的可用性**——它只能靠降级设计与责任划分来消化，**不能靠技术消灭，也不该用第二套账号去换**。
