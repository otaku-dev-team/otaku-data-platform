# 第 1 部分 · 给网站方（通俗版）

## 1.1 一句话

如果你的网站**目前还没有客户端**：为改善用户体验、扩大用户规模，你需要一个 App 或小程序。实现它有三条路径——自建团队开发、采购外包、或接入本平台。

**接入本平台时，你无需为它组建团队或承担开发工作**：技术底座已经建成并通过验证，你只需完成**授权与站点配置**，即可在显著短于自建或采购的周期内，上线**属于你自己网站的客户端**。

用户装上去就是**你的用户**，用你的品牌、看你的内容、用你的账号。

## 1.2 三条路径对比

|  | 自建团队开发 | 采购 / 外包 | **接入本平台** |
| --- | --- | --- | --- |
| 你的投入 | 组建或培养客户端团队；需求、设计、开发、测试全流程 | 预算投入 + 需求沟通与验收管理 | **一次授权**（内容授权 + 可选身份授权），**无需开发投入** |
| 上线周期 | 数月 | 数月（沟通、排期与返工） | **最短**：底座已建成并验证，仅需完成站点适配 |
| 后续维护 | 自行承担：系统升级、机型适配、商店审核 | 持续付费，或自行接手 | **由底座统一维护**，一次升级所有接入站受益 |
| 账号与用户 | 需另行建设 | 多数方案下仍需另行建设 | **沿用你现有的体系**：用户仍然是你的用户 |
| 适用场景 | 具备客户端团队，将客户端作为核心产品经营 | 预算充足、需求高度定制 | **希望以最小投入与最短周期获得客户端，而不专门组建团队** |

**我们的差异化不在于价格，而在于上线周期与你所需投入的工作量。**

### 技术上，我们替你扛掉的部分

- 多端一套代码（手机 + 桌面），**不用写两遍、不用维护两套**。
- 用户请求落在我们这层，你的服务器只承受**一个受控的同步作业**（并发 ≤2、1–2 req/s）。
- 系统升级、机型适配、商店审核，由底座统一处理。
- 账号：**目标是直接用你的**（见 1.3（4）与 1.4），不需要你再建一套。

## 1.3 原理：我们到底做了什么（四条讲清）

### （1）我们只"订阅"，不"修改"

我们的同步程序按约定频率，到你网站**公开的只读接口**把作品信息读一份回来——标题、简介、封面、标签、评分、年份这些。存进我们自己的库。

整个过程**不向你网站写入任何东西**：不 POST、不改你的数据、不需要你的管理员账号、不连你的数据库。
在你的权限视角里，我们只有一个身份：**公开可读的访客**。

### （2）中间这一层，是替你"挡事"的

用户的手机和电脑只跟我们的服务对话，**不直接打你的服务器**。有两个直接好处：

- **你的服务器不会被大量客户端反复请求**。我们只按你给的限速拉一次，之后所有用户读的都是我们库里的数据。
- **你网站临时挂了、维护中、网络抖动，客户端依然有内容可看**。数据是我们库里的快照；而且我们不会因为一次拉不到，就认为"你把作品删了"。

### （3）这是你的客户端，用户本来就是你的

客户端用的是**你的品牌、你的内容**；用户在里面看到喜欢的作品，需要评论、投稿、参与社区时，一键打开你网站上的原页面继续——**从客户端到网站，是同一段体验的延伸，不是从一个产品跳到另一个产品**。

我们不圈用户：用户是你的，我们**不把他变成"平台的用户"**。将来接入多个网站时，每个站有各自的客户端和各自的用户，**互不打通、互不串号**。

### （4）你的账号，直接用来登录（目标状态）

你的网站已经有账号、有收藏、有"想看 / 在看 / 看过"。我们的目标是让用户在客户端里**用你网站的账号直接登录**，登录之后，客户端里的收藏与状态也能和你网站里的保持一致——**用户不需要重新注册一遍**。

这需要你开放一个**授权接口**：登录在你那边完成，密码不经过我们，我们只拿到一张**可撤销的令牌**。这件事的进度与方式见 1.4 与 1.7。

## 1.4 你要做什么（接入清单）

**内容接入**只有四项，而且基本都是你本来就有的东西：

1. **一个能被分页列举的作品列表接口**（公开只读即可），能给出总数。
2. **一个稳定的站内作品 ID**——同一作品每次返回的 ID 相同；**作品删除后这个 ID 不要分配给别的作品**。
3. **ID、标题、类型这三项必须有值**。
4. **没有的字段要如实说"没有"**（返回空或不返回该字段），**不要填 `""`、`0`、`"暂无"`**——假的空值会一路显示到用户屏幕上，比留白更难看。

加分项（有则用，没有也不影响接入）：封面图地址、标签、评分、最后更新时间。

**身份接入（可选，但它决定用户是否"丝滑"）**

5. **一个授权接口**：让用户在客户端里用你网站的账号登录。可以是标准的 OAuth2 / OIDC，也可以是一个"签发一次性登录票据"的简单接口。要点只有一条：**登录在你那边完成，用户密码不经过我们**，我们只拿到一张**可撤销的令牌**。
6. **（可选）读 / 写"我的收藏与状态"的接口**：让用户在客户端里的收藏与你网站里的保持一致。**只在用户本人授权下使用**；你不开放也不影响接入，只是收藏暂不同步。

**限速你说了算。** 并发数、每秒请求数、每日配额按你的要求配在我们这边，超出自动减速，我们不会去试探你的上限。首个站点的当前约定是：**并发 ≤2、每秒 1–2 次请求、每天不超过 5 万次**。

## 1.5 我们绝不做什么（这是你的安全感）

| 我们不会 | 对你意味着 |
| --- | --- |
| 不向你网站**写入 / 修改 / 删除**作品数据 | 作品数据只是单向流出的副本，**源头永远在你手里**（用户的收藏与状态若要回写，必须你开放接口 + 用户本人授权，见 1.4） |
| **不要**你的管理员账号、数据库密码、后台权限 | 我们不代持你网站的任何凭据 |
| **不直连**你的数据库 | 只走你公开的接口或约定的导出方式 |
| **不抓取**需要登录才能看的内容 | 只取公开作品数据 |
| **不擅自读取或复制**你网站的用户账号、收藏、浏览历史、评论 | 这些归你。只有你开放接口、且用户本人授权后，我们才按授权范围使用——**目标是直接用你的账号，不是另建一套** |
| **不把多个网站合并**成一个大站 | 每个网站是独立服务对象，各站数据与用户不串 |
| **不锁住用户、不抢用户** | 用户始终是你的，我们不设围墙；需要网站原生能力时一键到你的原页 |
| **不假装有还没做的功能** | 只承诺当前已实现、且写进契约的能力 |

还有一条很重要：**我们不替代你。**
通用能力（浏览、搜索、收藏、跨端同步）由我们统一做；你网站独有的能力（比如你的评论区、你的社区玩法）**不强行复制**——需要时单独适配，做不到就明确写"客户端暂不支持，请回网站"。

## 1.6 对你和你的用户的好处

**对你（网站方）**

1. **授权即可接入**：不用改代码、不用开写权限、不用迁数据——你需要完成的是**授权与站点配置**。
2. **周期短、无需组建团队**：无需招募开发人员、无需编写需求文档，系统升级、多端适配、商店审核均由底座统一承担。
3. **服务器减压**：用户请求落在我们这层；封面图由我们缓存后对外服务，不再反复回你的站。
4. **可用性加成**：你站点临时不可用时，客户端仍有内容可看（快照不清空）。
5. **主权不变**：内容、账号、用户、品牌全在你手里，随时可以要求停止同步、下线客户端。
6. **可携带**：底座是通用的，以后你要换客户端形态（Web / 桌面 / 后续原生 App），数据接入不用重做。

**对你的用户**

1. 手机、电脑都能用，**收藏和「想看 / 在看 / 看过」跨端同步**。
2. **不用重新注册**：目标是用他在你网站的账号直接登录；授权接口就绪前先用客户端账号过渡，之后可切换（见 1.7）。
3. 看到喜欢的作品，**一键到你网站的原页**看详情、参与讨论、投稿——从客户端到网站是连贯的。
4. 打开更快（列表与封面由我们这层缓存），你的网站也不容易被挤慢。

## 1.7 网站方常见问题

**Q：你会不会分走我的流量和用户？**
A：客户端只展示作品元数据，详情页的「在来源站查看」把用户送回你的页面。我们不承接评论与社区，不做内容替代，用户归属不变。

**Q：你会不会拖垮我的服务器？**
A：不会。客户端不直连你，只有我们一个受控同步作业按你给的限速访问（默认并发 ≤2、1–2 req/s），重试带退避，遇到限流或 5xx 会主动退让。

**Q：我的用户要迁移到你们平台吗？**
A：**不迁移，也不需要迁。** 用户仍然是你网站的用户，不是"平台的用户"。
客户端的账号有两档：① 你开放授权接口后，用户**直接用你网站的账号登录**；② 授权接口就绪前，先用客户端账号过渡（此时是两套账号）。**我们要的是 ①，不打算长期停在 ②。**

**Q：那我的用户现在能"丝滑"使用吗？**
A：**这是我们要做到、但尚未完成的部分。**
你的站点账号、收藏、"想看 / 在看 / 看过"都有，但它们目前是**网页表单 + 会话 cookie 实现的，没有对外的 JSON 接口**（我们做过只读核验）。所以现阶段客户端用的是自建账号——用户要注册一次，**这确实不够丝滑**。
要做到真丝滑，只需要你补一个**授权接口**（登录在你那边完成，密码不经过我们），再可选开放"读 / 写我的收藏与状态"。这是我们的下一步，不是口头承诺，会写进接入清单一一验收。

**Q：我改版 / 换域名 / 改字段名怎么办？**
A：我们的适配器是**按站点配置驱动**的，改配置不改代码。结构真变了我们会**报错停下来**（不会静默把空结果当成"作品都没了"），改完配置即可恢复。

**Q：我不想做了，怎么退出？**
A：停止同步 + 下线客户端即可。你的数据本来就在你那里，我们这边的副本可以按你的要求删除。

**Q：数据会有错吗？**
A：我们对"缺失"和"没有"分开处理：你没给某个字段，我们**不会**拿 0 或"暂无"去填空，也**不会**因为一次拉取失败就覆盖掉已有的好数据。缺失就是缺失，界面显示占位。

**Q：现在做到哪一步了？**
A：首个接入站点（Otaku）的端到端链路已打通，并通过接口层验收：浏览、搜索、详情、账号、收藏跨端同步均可用。
**还没做到的**：用你网站的账号直接登录客户端（等你开放授权接口）、收藏与网站双向同步、多站点同时接入、离线、推送、原生 App 商店发布——**这些都不做承诺**。

# 第 2 部分 · 给团队（技术细节与设计理由）

## 2.1 架构与数据流

```text

  独立运营、独立用户体系            独立运营、独立用户体系
        │ ① 只读拉取                      │

┌──────────────────────────────────────────────────────┐
```

**四个接口的分工**

| # | 接口 | 方向 | 实现方 | 边界 |
| --- | --- | --- | --- | --- |
| ① | 来源接入 | 来源站 → 平台 | Python 适配器（**只读**） | 只取作品元数据；不写入、不碰用户数据、来源站零改造 |
| ② | 数据写入 | Python → Java | Java | 按 `(source, source_id)` 幂等 upsert；字段缺失不覆盖 |
| ③ | 作品列表 | 客户端 → Java | Java | 分页 + 搜索 + 排序；7 字段，**不含 `summary`** |
| ④ | 作品详情 | 客户端 → Java | Java | 按 `work_id` 取 12 字段，含 `source_url`；不存在返回 404 |

## 2.2 关键设计决策与"为什么"（原理核心）

### 2.2.1 只读拉取，不做推送、不做回写

- **决策**：来源接入采用 **pull（平台定时拉）**，不要求来源站改造来推数据；平台**永不向来源站写入**。
- **理由**：① 来源站侧**零改造**、不给平台开任何写权限，接入摩擦最小；② 边界最小——出问题时影响范围只在我们自己的库；③ 主权叙事正确：我们是服务方，不是把来源站当数据供应商。
- **代价**：数据是**快照**而非实时代理，存在同步延迟；也因此必须实现"拉不到就保留上一次"的降级规则。

### 2.2.2 两层标识：`(source, source_id)` 定位，`work_id` 对外

- `work_id` 由 Java 首次创建时生成，**此后永不变**（改标题、换封面、改评分都不换 ID）；客户端**只当不透明字符串**，禁止解析结构。
- `(source, source_id)` 是 Python 与 Java 之间的定位依据，Java 侧建**唯一约束**。
- **为什么不用标题去重**：实测 anime 内重名 55 组（「铁臂阿童木」×3）、跨类型同名 341 组（「航海王」既是动画也是漫画）——按标题合并**必然误判**。
- **为什么不解析 `work_id`**：一旦客户端依赖其结构，Java 换生成方式就会全线崩。

### 2.2.3 幂等 upsert + `null` 三态

- 同一批重跑（同一 `batch_id`）**结果一致、不重复入库**；同一 `(source, source_id)` 重复提交是更新不是新增。
- **三态语义**：`null` = 本次没数据（**不覆盖**已有值）；`[]` = 明确为空（可清空）；有值 = 覆盖。
- **为什么**：来源站经常出现部分字段拉不到（简介 502、标签为空）。如果用缺失值覆盖，一次抖动就会把库里的好数据冲掉，且**不可回滚**。所以定死"缺失不覆盖"，宁可保留旧值。
- **Otaku 的特例**：该站 `tags` 只有 `[]` 一种空值，无法区分"真没标签"和"还没录入"（抽样 38.5% 是空），适配器统一把 `[]` 转 `null` 按"未提供"处理——**宁可保留旧值，也不误删**。

### 2.2.4 封面由后端代理 + 本地缓存，客户端绝不直连

- 客户端拿到的 `cover_url` 是**平台代理地址**（`/api/covers/{id}`），不是来源站地址。Java 缓存未命中才回源一次，之后由平台直接服务。
- **实测依据（不是拍脑袋）**：来源站 `/media/*` 与 `/covers/*` **均不带 `Access-Control-Allow-Origin`**（Flutter Web 直连必然跨域失败），`Cache-Control` 仅约 43 分钟（客户端拿不到长缓存）。两条独立证据都指向"必须平台代理"。
- 回源遵守来源站限流（≤2 并发、1–2 req/s），且只回源白名单地址。

### 2.2.5 适配器配置化：加一个站 = 加一份配置 + 一个 `source`

- 每站一份配置：`source` / `base_url` / 类型列表 / 分页参数 / 限流参数 / 字段映射。**改配置不改代码**。
- 跨站唯一键始终是 `(source, source_id)`；不同站相同 `source_id` 是**两个作品**。第一阶段**不做跨站合并**。
- 这是"一套底座服务多个独立网站"能成立的技术前提——**复用的是代码，不合并的是业务**。

### 2.2.6 `source_url` 按源打开原页：必须是人读页，不是 API 地址

- 详情接口返回可空 `source_url`，客户端渲染「在来源站查看」，用**系统浏览器打开**，只导航不抓取、不自行拼 URL。
- ⚠️ **踩过的坑**：Otaku 的**人读原页**是 `/contents/{id}`（首页卡片链接即此；`GET /contents/476` 返回 200 + HTML，`<title>街角魔族 2丁目 · Otaku</title>`）；而 `/api/contents/{id}` 返回 **JSON**，拿它当打开原页的入口等于给用户一个无效链接。两者必须区分。
- **无法可靠确定原页地址时返回 `null`，绝不猜测生成**；`null` 时客户端**不显示入口**（不是置灰，避免无效点击）。
- 多站时入口必须对应作品的 `source`——A 站作品回 A 站原页，**不串站**。

### 2.2.7 账号与身份：现状是平台自建，目标是复用来源站身份（⚠️ 契约级，待确认）

> ⚠️ **本节含未决事项。** 涉及「不代持来源站凭据」「不向来源站回写业务数据」「来源站原生账号不进平台」三条铁律的重新界定，**未获负责人与三人确认前不得实施**。

**现状（已实现，阶段 2 已通过验收）**
- 账号由平台自建，服务于平台客户端；与来源站账号是两套，**互不读取、互不关联**。
- 登录返回**不透明令牌**（43 字符），服务端会话有效期 30 天，**多设备会话并存**（同一账号可同时登录手机与电脑，互不影响）。
- 收藏 `status` 三态 `[want, watching, watched]`，并发冲突按 **LWW（最后写入胜出）**。

**为什么现状没有复用来源站账号（是事实约束，不是立场）**
2026-10-24 只读探测 `GET {base}/openapi.json`（共 131 个路径）确认：来源站**有完整账号体系**——
`/login`、`/register`（邀请码制）、`/logout`、`/me`、`/contents/{id}/favorite`、`/contents/{id}/status`、`/me/favorites/*`、`/me/history/*`、`/me/persona/*`。

但这些全部是**网页表单 + 会话 cookie 的页面端点（无 `/api/` 前缀），不是 JSON API**，也**不存在任何 OAuth / token 签发端点**。

因此要用来源站账号登录，只有三条路，两条不可接受：

| 路线 | 是否可行 | 原因 |
| --- | --- | --- |
| 平台代收用户密码转发验证 | ❌ **不可接受** | 直接违反「不代持来源站凭据」铁律，且一旦泄露是灾难级 |
| WebView 内嵌网站登录页 | ❌ 不可用 | 平台确实不碰凭据，但**拿不到用户身份**，收藏无法跨端同步，体验不可靠 |
| **站主开放授权端点（OAuth2 / 一次性票据）** | ✅ **唯一可行** | 用户在来源站完成登录与授权，平台只拿**可撤销的用户令牌**，**不接触密码** |

**目标状态与开放问题（需站主 + 三人确认，尚未启动）**
1. 站主提供授权端点 → 客户端用来源站账号登录，用户**不用重新注册**；
2. 站主可选开放「读 / 写我的收藏与状态」接口 → 客户端与网站**双向一致**。这属于**用户本人在授权范围内的数据使用**，与"向来源站回写业务数据"性质不同，**但必须先修订铁律措辞将两者区分开才可做**；
3. 在此之前维持平台账号过渡，并**保留后续切换到来源站身份的余地**（账号映射与数据迁移方案需单独设计，不能等切换时才想）。

**需要重新界定的铁律措辞（讲清后才动）**
- 现行表述把"服务凭据 / 爬取用途"与"用户本人授权"混为一谈。建议区分：**禁止**的是平台持有来源站的服务凭据、代用户爬取；**允许**的是用户在来源站主动授权后，平台持有可撤销的用户令牌。
- 这一改动影响：阶段 2 已实现的账号体系（可能需支持双身份源）、客户端登录流程、openapi 阶段 2 契约、以及"不回写"边界的定义。
- **属契约级变更**：先向负责人讲清改什么 / 为什么 / 后果 / 影响谁，再走三人确认，不擅自实施。

### 2.2.8 限流、重试与三条降级规则

- **限流**：并发 ≤2、1–2 req/s、每日 ≤5 万（配额由站主给定，写进适配器配置，超出即降速，**不试探上限**）；封面下载单独 ≤2 并发。
- **重试策略**：网络错误 / 超时 / 5xx / 429 → 退避重试；4xx（含 401、400）→ **不重试**，记为未送达并落盘报告；缺内部令牌 → 提交前直接失败，不发请求。
- **三条降级**：
  1. 来源站临时不可用 → **保留上次成功快照，不清空**，本次记失败下次重试；
  2. 某条记录某字段缺失 → 该字段不覆盖，其余照常更新；
  3. 来源站改字段名 / 改路径 / 改分页语义 → 适配器**报错并停在该步**，不静默跳过、不把空结果当成"作品全没了"。

## 2.4 已知限制（内部口径，对外不承诺）

1. **身份未与来源站打通（最大的体验缺口）**：当前客户端账号是平台自建，来源站已有用户仍需在客户端注册一次。目标是用来源站账号直接登录，依赖站主开放授权端点（见 2.2.7）。
2. **收藏与状态不回写来源站**：客户端里的收藏只在平台内，来源站侧看不到。需站主开放用户数据接口 + 用户授权，且要先修订「不回写」铁律措辞。
3. **当前单站点**：`source` 固定 `otaku_site`，客户端构建期确定站点、运行期不切换。多站是架构留口，**未实现**。
4. **数据覆盖率**：封面约 2.7%、评分约 36.2%、简介 84%+（档案体检）。客户端**必须有完整的占位路径**，且占位不得显示 `0` 或"暂无"这类伪值。
5. **`release_year` 历史数据存在 `null`**：字段是后加的，历史导入数据需要重跑管线才能补上，**不是缺陷**。
6. **富字段缺失**：别名、原名、话数、媒介、Staff、角色声优等**来源站 JSON 未出口**（DB 里有、HTML 里渲染，但接口不给），暂不纳入。
7. **搜索能力有限**：仅标题子串匹配、忽略大小写，**不支持别名与拼音**。
8. **不做删除语义**：作品在来源侧消失，平台不删除，客户端仍可查到。
9. **不做跨站合并**，也不做多来源评分合并。
10. **不承诺**：离线、推送、原生 App 商店发布——需要时单独立项。

## 2.5 接入一个新网站的工作量清单

1. **一份适配器配置**：`source` / `base_url` / 类型列表 / 分页参数 / 限流参数 / 字段映射。
2. **一个适配器实现**：列表解析、字段映射（含 `null` 归一化）、`source_url` 规则（务必区分人读页与 API 地址）。
3. **站点能力核验**：可枚举、ID 稳定且不回收、必填三项非空、缺失字段如实表达。
4. **客户端品牌配置**：构建期确定（`base_url` + 站点标识 + 品牌资源）。
5. **验收两遍**：接口层（同阶段 1/2/3 口径）+ UI 层（真机 / 桌面各一遍）。

## 2.6 术语表（客户沟通与团队内部通用）

| 术语 | 说明 |
| --- | --- |
| **来源站 / 网站** | 独立运营的内容网站，如 Otaku。平台的服务对象，不是数据供应商。 |
| **适配器** | 针对某个来源站写的接入模块，按配置驱动；改配置不改代码。 |
| **快照** | 平台库里的数据副本，非实时代理。来源站不可用时保留上次成功结果。 |
| **`source` / `source_id`** | 来源标识 + 来源站内作品 ID，两者共同唯一定位一条作品。 |
| **`work_id`** | 平台内部标识，首次生成后永不变；客户端只当不透明字符串。 |
| **`source_url`** | 来源站的人读原页地址，供客户端打开原页；无法确定时为 `null`。 |
| **延伸（回原页）** | 用户在客户端里一键打开来源站原页，继续评论、投稿、参与社区。**同一段体验的延伸，不是"从一个产品跳到另一个产品"**——不使用"回流"这种把网站当外部的说法。 |
| **LWW** | Last-Write-Wins，最后写入胜出，收藏状态的并发冲突处理策略。 |
| **幂等** | 同一批数据重复提交，结果一致、不重复入库。 |
| **占位** | 字段缺失时的展示处理（占位图 / 不显示评分 / 显示"暂无简介"），禁止用 `0` 或"暂无"这类伪值。 |
