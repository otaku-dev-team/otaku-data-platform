## 1. 结论先说

三块数据**都在首站源库里**，走已落地的 `sync-dataset`（同机派生库只读）就能拿到，
不需要爬 1.8 万次 HTML，也不需要换 426 MB 的 Bangumi 完整档。

但「Staff 有 40.8 万条」这个数字会误导决策：**其中 91% 是原画、作画监督、演出这类工序流水**，
观众在详情页真正会看的是导演、脚本、音乐、人物设定这些职位，它们全在 `tier='main'` 里。

所以本档的取舍是：

| 三块 | 收不收 | 条数 | 覆盖作品 |
| --- | --- | --- | --- |
| `staff` | 收 `main` + 中层工序白名单 | **183,356** | **8,945 部（47.5%）** |
| `characters` | 全收 | **75,742** | **8,015 部（42.6%）** |
| `studios` | 全收 | **4,270** | **3,644 部（19.4%）** |
| ~~`staff` 原画层~~ | **不收** | ~~166,176~~ | 工序流水，不是「谁做的这部片子」 |

合计 **263,368 行**关系数据 —— 是原始 48 万行的 55%。

单部作品的实际规模（导出后实测）：staff 平均 20.5 条、**最多 288 条**；
characters 平均 9.5 条、最多 60；studios 平均 1.2 条、最多 3。

### 2.2 `tier` 是什么

源站自己给 credits 分了三档，**这不是我们的分级**：

- `main`（26,813）：从 `infobox` 文本解析出来的核心职位 —— 脚本 10,110、美术监督 4,437、
  音响监督 2,473、制片人 1,221、音乐 978、企画 935、**导演 851**、副导演 834、
  人物设定 660、原作 584、系列构成 185…平均 **4.3 条/部**，最多 78 条。
- `long`（337,618）：从 Bangumi 关联数据灌进来的工序流水 —— **原画 166,176**、
  作画监督 66,613、演出 31,768、分镜 30,575、总作画监督 8,863、补间动画 2,994…
- `candidate`（43,518）：待确认的候选记录，形态与 `long` 相同（原画 26,290 占大头）。

### 2.3 `role` 有多脏

`role` 共 **1,334 种**取值，且混进了**漫画字段**：

| 脏值 | 条数 | 说明 |
| --- | --- | --- |
| `发售日` | 1,422 | 漫画的出版信息，被当成职位 |
| `作者` | 1,281 | 同上 |
| `版本:东立版` | 726 | 台版漫画版本名 |
| `连载杂志` / `ISBN-10` / `册数` / `链接` | 565 / 552 / 437 / 559 | 全是出版元数据 |

这些值都出现在 `tier='main'` 里，所以**光按 tier 过滤不够**，必须配 role 黑名单。

## 3. 收哪一层：白名单

### 3.1 规则

```
tier='main'                                     # 26,813 条，全部核心职位
  ∪ role IN (作画监督, 总作画监督, 演出, 分镜, 机械作画监督, 动作作画监督)
                                                # 156,794 条，跨 main/long/candidate
  − role IN (发售日, 作者, 版本:*, 连载杂志, ISBN-*, 册数, 链接, …)
                                                # 出版元数据黑名单
```

结果 **183,356 条 / 8,945 部**，其中 150,427 条（82%）有 `person_id`。

### 3.2 为什么按 role 而不是只按 tier

`tier` 只有三档，粒度不够：`long` 里同时躺着 16.6 万条原画（纯工序，几百人名单）
和 13.9 万条中层工序（作画监督 / 演出 / 分镜 —— 这些是**观众认得出、也想看**的职位）。
要「只去原画」就只能按 role 挑，按 tier 一锅端会连作画监督一起丢。

### 3.3 为什么排除原画

原画 166,176 条覆盖 6,194 部，平均 27 条/部，最多的一部几百人。它有三个问题：

1. **展示上无法收敛** —— 详情页不可能列 300 个原画名字，折叠 `/ 展开` 又没人展开；
2. **噪声大于信息** —— 观众找的是「谁导演的 / 谁写的剧本 / 谁配的音」；
3. **成本真实** —— 多 16.6 万行导入，换来的是界面上没人看的一坨。

将来若做「完整制作名单」页（不在本期），把这条加上即可，数据集与契约都不用改。

## 5. 六个必须避开的坑

### 5.1 三态语义决定「会不会静默清空」

`staff` 用 **`null` = 未提供（不动存量）/ `[]` = 明确没有（清空）/ 非空 = 替换** 三态。

原因很具体：**REST 通道拿不到 staff**。同一个作品可能先经 `sync-dataset` 写入 Staff，
之后一次普通 `--articles` / 站点同步走接口②把它覆盖成 `null`。若后端把「null」当「清空」，
数据集通道辛苦导进来的 18 万条会被一次例行同步抹掉，而且**不会有任何报错**。

这和封面相对路径覆盖是同一类故障（见 `db-intake-dataset.md` §六.3），所以规则必须写进契约。

### 5.2 整体替换，不是追加

数组语义是「这批值 = 该作品的全部记录」。追加语义在来源侧删人时**永远删不掉**——
detail 页会一直显示早已离开制作组的人。

### 5.3 后端必须批量插入

26 万行关系数据若逐条 `insert`，按实测的全量导入速度（约 8 条/秒）要 **9 小时**，
而这不是一次性成本——每次全量重导都要付。必须走 JDBC batch，并且按 `work_id` 先删后插。

### 5.4 `person_id` 两侧严重不对称

| 侧 | 有值率 |
| --- | --- |
| `staff`（main 层） | **0%** |
| `characters`（声优） | **100%** |

不是导出问题：`main` 层的 Staff 是从 `infobox` 的**文本**解析的，源头就没有人名 id；
声优侧来自 `content_cast.person_id`，是结构化的。

影响：**人物页只对声优成立**。Staff 只能显示「职位：人名」，做不成「点进去看作品」。
契约里 `WorkStaff.person_id` 先占位、注释写清楚「人物页落地前一律 null」，避免客户端误判。

### 5.5 `character_type` 84% 为空

`content_cast.relation` 分布：`null` 63,439 / 配角 8,418 / 主角 2,632 / 客串 670 /
闲角 510 / 旁白 65 / 声库 8。

客户端**不要**显示「未知类型」，也不要按类型分组排序——多数记录没有类型，分组出来就是
一个巨大的「未知」桶。

### 5.6 role 白名单要能改

1,334 种 role 意味着白名单一定会漏或错。放**数据集映射文件**里（`mappings/otaku.json`
的 `mode: query` SQL 条件），不写进代码——改词表不改代码，也不需要重新发版。

## 7. 换了一批数字之后（2026-10-28 服务器实测）

导出与载荷这两段已经真跑过一次，不再是纸面估算：

| 项 | 实测 |
| --- | --- |
| 导出耗时 | **6.8 秒**（`nice`/`ionice` 降优先级，未打断正在跑的全量导入） |
| 数据集体积 | **64.4 MB**（v1 是 79.8 MB，因为砍掉 20.6 万条原画流水） |
| 总行数 | **412,239**（v1 618,853） |
| `work_credits` | **183,356** —— 与按 role 白名单预估的数字**一分不差** |
| `people` | **17,916**（= 源 `entities` 全量） |
| 单部上限 | staff 最多 **288** 条 / characters 最多 60 / studios 最多 3 |
| 载荷 | 500 条一批里 56 条有 staff、54 条有 cast、20 条有 studios；单条 16 字段 |

单部 288 条意味着客户端必须做折叠（默认露 5–8 条 + 「展开全部」），不能整列渲染。

### 仍然没验的

- **后端导入耗时与 MySQL 磁盘增量**：后端四张表还没建，26 万行批量插入的真实耗时没有数字。
  方案 §5.3 的「必须批量插入」是按 8 条/秒逐条估算的，实际要看 pyxz0 的实现。
- **`content_credits.detail` 列**：存在（VARCHAR 200），内容形态没看，映射暂不导。

### 已经不再是问题

- ~~数据集 v1→v2 兼容~~：**定了直接拒收**。加表是增量变更，但同一份映射里 credits 的口径
  也从 40.8 万条变成 18.3 万条，读方不能假设「v1 的 credits 与 v2 是同一批数据」。
  重新导出只要 6.8 秒，没有保留双向兼容的价值。
- ~~缺 `entities` 表怎么办~~：跳过 `people` 并记 `degraded`，不整批失败（有测试钉住）。
  第三方客户的库未必有这张表。
