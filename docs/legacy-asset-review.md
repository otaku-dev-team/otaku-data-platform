## 0. 一句话补充

盘点的归类结论基本成立、可直接采信。但它**漏掉了本轮最有价值的一条**：

**`contents` 表有 25 列，JSON API 只出口 9 个。另有 10 个库中已存在的字段没有任何出口——其中 `title_original`、`aliases`、`series_id`、`episodes`、`media` 恰好是新平台最需要、而我们原本准备自己重建的能力。**

争取这些字段的收益，远大于我们自己实现系列识别与别名搜索的成本。

### 1.2 需要更正的三处

前两处是**我方此前记录有误**，第三处是盘点未覆盖。

| # | 原记录 | 实际 | 依据 |
|---|---|---|---|
| 1 | `/api/tags` 默认 `limit=30` | **默认 `limit=500`**，上限 2000 | `app/api.py:143` `Query(default=500, ge=1, le=2000)`；线上不传 limit 实测返回 total=500 |
| 2 | `tags` 约 80% 有值 | 抽样 400 条，**约 90% 有值**（39 条为 `[]`） | 线上抽样 anime 第 1–2 页 |
| 3 | 标签数中位 5 / max 5（原因不明） | **分布只有 0 与 5**（39 条 0、361 条 5，**无 1–4**）。根因定位到 `app/crud.py:3250` 的 `split_tags(...)[0][:5]` | 源码 + 线上抽样 |

第 3 条值得单独说明：分布呈二值、完全没有 1–4 的中间值，说明**截断是硬截断，且绝大多数作品的标签都被削到 5 个**。这会让「按标签筛选/推荐」的召回能力显著低于标签实际应有的水平。

## 2. 盘点未覆盖、但对新项目最关键的：10 个没有出口的字段

`Content.as_dict()`（`app/models.py:85-93`）只输出 5 个字段；`_content_payload`（`app/api.py:82-89`）追加 `cover_url` / `tags` / `year` / `bangumi_id`。**其余列全部无出口。**

| 字段 | 含义 | 对新平台的价值 | 优先级 |
|---|---|---|---|
| `title_original` | Bangumi 日文原名 | 搜原名能搜到；**重名条目的辨识依据** | **高** |
| `aliases` | infobox 拆出的别名（英文名 / 台版译名等），JSON 数组 | 同上，搜索召回 | **高** |
| `series_id` | 所属系列（同系列多季 / 剧场版指向同一行） | 直接落地我们契约**待确认第 3 项**（341 组跨类型同名、多季关联），省掉自建系列识别 | **高** |
| `episodes` | 话数 | 详情展示；追番进度的基础 | 中 |
| `media` | 媒介（TV / 剧场版 / OVA / Web） | 详情展示 | 中 |
| `source_material` | 原作载体（漫画改 / 小说改 / 原创） | 详情展示 | 中 |
| `source_url` | Bangumi 溯源链接 | 溯源与外部去重 | 中 |
| `book_kind` | 书籍细分（light_novel / literature） | 书籍角标 | 低 |
| `image_url` / `remote_image_url` | 本地原始封面 / 远端封面地址 | 封面本地化策略 | 低 |
| `meta_fetched_at` / `meta_failed_at` | 元数据补全时间 / 失败时间 | 判断某条是否已补全过 | 低 |

**与盘点有一处冲突，需站主确认：** 盘点 2.9 写「`media / source_material / episodes` 列已建但导入链路**从未写入**」，但源码中存在明确的写入路径——`app/bangumi_meta.py:325-329`（后台补全时写入）与 `scripts/clean_content_tags.py:169-171`。

两者不能同时成立，实际填充率以站主口径为准。**若已补全，这三个字段就是现成的详情展示数据。**

## 3. 三处会直接影响我们实现的事实

**1. 限流不在应用层。** `app/*.py` 中没有任何限流中间件。站主所述「超出会做 IP 级限流」应属运维/防火墙层策略。含义：超限时的表现**不一定是标准 429**，也可能是连接超时或丢包。同步作业要有超时与退避，不能只依赖 429 判定。

**2. 标签硬截断 5 个。** 见 1.2 第 3 条。客户端若以标签为主要筛选维度，召回会明显不足。

**3. `cover_url` 可能是空串。** 代码注释明确写着「空串 = 无封面」（`app/api.py:47`）。我方 `clean_cover_url` 已把空串与 `None` 一并转为 `None`，**此条已覆盖，无需改代码**；线上 anime 抽样暂未遇到空串，但不代表其他类型没有。

## 4. 追加给站主的提问（第二轮）

按价值排序。前三个是真正卡人的。

1. **能否把 `title_original` / `aliases` / `series_id` / `episodes` / `media` / `source_material` 一并加进 `/api/contents` 返回体？**
   这 6 个字段全部已在库中，加出口的成本很低。对我们而言，`series_id` 直接省掉系列识别、`title_original` + `aliases` 直接省掉别名搜索与重名辨识——**一个字段换一整块功能**。

2. **标签 5 个上限是设计还是遗留？能否放开，或提供完整标签的获取方式？**
   实测分布只有 0 与 5，硬截断证据明确。若不能放开，我们需要据此调整「按标签筛选」的产品预期。

3. **`media` / `source_material` / `episodes` 的实际填充率是多少？**
   盘点说从未写入，源码里有写入路径，请确认线上真实情况。

4. **限流是应用层还是防火墙层？超限时返回标准 429 还是直接断连？**
   决定同步作业的重试与退避写法。

5. **能否补 `/api/articles` 与 `/api/articles/{id}`？**（盘点 2.4 已提出）
   资讯管线本身可用，只差一层 API。

6. **能否把 `search_query` 的语义解析接进 `/api/contents/search`？**（盘点 2.3）
   现状是纯子串模糊匹配，搜「2024 年科幻 TV」这类查询不会生效。

7. **系列表 `series` 能否开 API？**
   若 `series_id` 能出口，配套需要能取到系列名与系列内成员列表。
