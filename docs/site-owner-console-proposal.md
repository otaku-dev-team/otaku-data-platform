## 1. 为什么现在立

- **客户必问**：「我能不能管理我的 App 的用户和数据？」——目前答案是「能，但还没建」。定位文档已把站主后台标为**实现缺口**（§6.6）。
- **它是身份打通的价值闭环**：阶段 2 之后，站主能看到「你的用户拿你的账号就能登录客户端」，但**看不到、也管不了**——没有后台，"身份打通"只做了一半。
- **它是商业模式的落地体现**：持续服务（默认）意味着我们部署运营；站主后台是站主自助管理的入口，不是附加功能。

## 2. 目标与非目标

### 2.1 首版目标（三件事，同 Issue #144）

1. **数据概览**：本网站的作品数、字段覆盖率、同步状态摘要。
2. **管理本网站的用户**：查看列表、禁用/解禁（范围以本站为界）。
3. **查看同步状态**：最近一次同步时间、成败、失败补齐入口。

### 2.2 非目标（红线，与定位一致，不可让步）

| 不做 | 为什么 |
|---|---|
| **站点配置** | 接入与配置新网站是**底座核心能力**。开放给站主，网站即可自行接入任意站点，服务价值归零（定位 §站主运营后台已定） |
| **跨站管理** | 站主只能看/管自己这一个网站 |
| **底座管理** | 平台自身、其他网站的接入与配置，不向站主暴露 |
| **改网站侧账号** | 见 §4.2 的关键边界 |

## 3. 角色与权限模型

| 角色 | 谁能当 | 可见范围 | 可做什么 |
|---|---|---|---|
| **站主**（本站管理员） | 该网站的运营方 | **仅本站**的数据与用户 | 概览、查看/禁用本站客户端用户、看同步状态 |
| **平台管理员**（我们） | 平台侧 | 全部网站与底座 | 接入网站、站点配置、跨站 —— **不在站主后台暴露** |
| 终端用户 | App 使用者 | 自己的数据 | 不使用本后台 |

**数据隔离是硬要求**（不是"尽量"）：

- 后台每个查询都按**站点维度强制过滤**，站点身份由登录态推导，**不信任前端传入的站点参数**；
- 越权访问返回 **403**；
- 必须有测试覆盖：站主 A 取站 B 的数据 → 403。

> 具体怎么实现过滤（拦截器、DAO 层、视图）属模块自主，这里只定边界与验收。

---

### 3.1 账号全渠道统一（2026-10-25 已拍板）

**所有渠道共用同一套账号 —— 网站的账号。** 渠道包括：网站本体、客户端（App）、站主运营后台，以及未来新增的形态（小程序 / iOS 等）。

- **唯一身份源 = 网站账号**：用户在任一渠道登录，都是同一个网站身份（`external_user_id` 一致），不需要、也不应该有第二个账号；
- **平台账号仅作过渡**：只在站点授权端点尚未就绪时兜底，**不是产品终态**；必须预留切换到网站账号的路径（账号映射），与定位 §4 一致；
- **不引入第二套账号体系**：后续新增渠道沿用同一套，不为某个渠道单独建号。

**注册入口可以在 App，但账号必须创建在网站侧。**（2026-10-25 拍板：App 内要能注册，保证体验）

- 用户在 App 内完成注册 → 走的是**网站自己的注册流程**（App 内承载 `/register`）→ 建出来的是**网站账号**，不是平台账号；
- 注册完即用这个网站账号登录，与网站、站主后台是同一个身份 —— **统一原则不破**；
- ✅ **不依赖网站开发**：网站已有完整注册能力（`/register` 两步：邮箱验证码 + 提交），**无需站点新增任何接口**。技术方案见 [`app-registration-approach.md`](app-registration-approach.md)；
- ⚠️ **红线**：不得用「App 原生表单 + 转发密码」实现 —— 那属于**代收用户密码转发**。密码只在网站页面内输入并提交，App 与平台后端均不接触；
- ⚠️ **剩余依赖**：邀请码（业务机制，非开发能力），见 §8.1。

这条直接决定站主后台的登录方式（§4.1）：站主用**网站账号**登录后台，不由我们另发一套管理员账号。

> 影响面跨渠道、跨模块 —— 后端身份模型、客户端登录流程、后台鉴权都以此为准。

## 4. 关键设计问题（Issue 未覆盖，本草案补充）

### 4.1 站主用什么身份登录后台？

| 选项 | 做法 | 评价 |
|---|---|---|
| A 平台自建管理员账号 | 我们给站主开号、管密码 | 简单，但与定位 §4「网站已有用户就用网站的账号」相悖；多一套凭据要维护 |
| **B 用网站账号**（✅ 已拍板） | 复用阶段 2 的站点 OAuth；站主本来就是网站的用户 | 符合定位；全渠道统一；不新增凭据；与 #147 复用同一套授权 |
| C 过渡后切换 | 先平台账号跑起来，OAuth 就绪后切网站账号 | 与「平台账号仅过渡」一致，但需预留切换路径 |

✅ **已拍板（2026-10-25）：选 B —— 用网站账号**。同一天拍板的「账号全渠道统一」（§3.1）把这条升级为硬原则：后台不能例外。

拍板理由：

1. **定位 §4**：网站已有用户，客户端就该用网站的账号 —— 后台同理，站主本来就是这个网站的人；
2. **账号全渠道统一**（§3.1）：所有渠道同一套网站账号；
3. 与 #147 账号绑定联调**复用同一套 OAuth**，不重复建设；
4. 少一套凭据 = 少一份泄露面（铁律：不代持用户凭据）。

**要解决的坑**：站点 OAuth 的 scope 是 `identity`（只给身份），**不带"管理员"标识**。

→ **解法（已定）**：平台侧维护一份**站主名单**（哪些 `external_user_id` 是本网站站主）。用网站账号登录成功后，校验该用户是否在名单内，决定能否进后台。

好处：不要求网站额外提供管理员 scope —— 符合"网站侧零改造"（定位：不排斥站主为身份授权做一次性开发，但能少改就少改）。

**过渡安排**：若 #147 联调未完成，可先按 C（平台账号）跑起来，但**必须预留切换到网站账号的路径**（账号映射）——过渡态不是终态。

### 4.2 「管理用户」的真实边界（最容易误解，必须写实）

首版的**「禁用用户」= 禁用该用户在本站客户端的登录**（平台侧会话失效），

**不等于**禁用他的**网站账号**。

- 网站账号的存废是**网站自己的事**（网站本来就有自己的用户管理后台）；
- 我们不回写网站侧的账号状态（铁律：不回写网站业务数据；且"站主禁用"不等于"用户本人授权"）。

因此后台 UI 必须**如实告知站主**：禁用后该用户**仍可登录网站**，只是不能用客户端。

> 若站主真的要"封掉网站账号"，那是网站后台的能力 —— 我们不做，也不该做。写清楚这一条，是为了避免站主误以为拿到了网站账号的生杀大权，上线后才发现不是。

✅ **已拍板（2026-10-25）：接受这个边界**，且 UI 必须如实说明「禁用 ≠ 封网站账号」。

### 4.3 数据隔离的验收形态

- 越权返回 403（不是 404）——Issue #144 已定 403；
- 测试覆盖跨站越权；
- 站主名单变更（新增/移除站主）要有据可查。

## 6. 与商业模式、交付边界的关系

- **持续服务（默认）**：后台由我们部署运营，站主自助使用 —— 无障碍。
- **私有化部署**：站主后台属于「该网站自己使用的那一个端」的一部分 → **可以交付**，但必须是**受限版**：
  - 有：本网站的数据概览、本站用户管理、同步状态；
  - **没有**：站点配置、跨站管理、底座能力、任何"接入新网站"的入口。

  依据：私有化硬边界 —— 只交付该网站自己使用的那一个端，**不给可取代本平台市场地位的能力**。

## 7. 验收口径（首版）

- [ ] 站主登录后只能看到**自己网站**的数据；跨站越权返回 403，有测试覆盖；
- [ ] 三件事均可用：概览 / 用户查看与禁用 / 同步状态（含失败补齐入口）；
- [ ] 「禁用」只影响客户端登录、不影响网站账号，后台有明确文案说明，并有测试；
- [ ] 站主后台**不存在**任何站点配置、跨站、接入新站的入口；
- [ ] `docs/` 下随首版补一份运营后台使用说明。

## 8. 拍板结论（2026-10-25，负责人已定）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 登录方式 | **B（网站账号 + 站主名单）** —— 已升级为全渠道统一原则（§3.1）；#147 未就绪可先按 C 跑，但必须预留切换路径（账号映射） |
| 2 | 「禁用用户」边界 | **只封客户端登录、不封网站账号**；UI 必须如实说明 |
| 3 | 站主名单维护 | 网站接入时由我们配置；后续可由已授权站主邀请（二期） |
| 4 | 首版用户管理范围 | **只做列表 + 禁用**；用户详情与收藏放二期 |
| 5 | 私有化是否交付后台 | **交付受限版**（剔除站点配置 / 跨站 / 底座能力） |
| 6 | App 内注册 | **要能注册**（保证体验），但账号必须创建在**网站侧**，不得产生第二套账号 |

### 8.1 对外依赖：已全部消解

> 本条原为「需向站点申请注册接口」，后收窄为「邀请码」，**现确认两者都不成立**。

- **注册接口**：2026-10-25 只读实测确认网站已有完整注册能力（`GET /register`、`POST /register/code`、`POST /register`），无需站点新增任何接口。见 [`app-registration-approach.md`](app-registration-approach.md)。
- **邀请码**：2026-10-26 复核注册页原文 ——「邀请码（可选）…… 可以留空直接注册」，且「注册账号为**普通用户**……若需**管理员权限**，请向站长索取管理员邀请码」。即**普通用户注册无需邀请码**，邀请码只与管理员权限有关。Issue #173 据此关闭。

**剩余的一项运营事项**（不是阻塞）：站主后台的**站主名单**（§4.1）需要确定由谁维护、如何增减——属平台侧运营动作，不涉及网站开发。

> 唯一无法靠技术消解的是**网站本身的可用性**：网站挂了则新用户注册不了。处置见 `app-registration-approach.md` §7（降级设计 + 责任归属写进合同 / SLA），不因此引入第二套账号。
