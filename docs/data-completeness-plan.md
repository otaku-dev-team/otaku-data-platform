## 1. 目标

把「封面 / 评分 / 简介」三项的可用覆盖率推到上线可接受的水平，或直接给出「做不到 + 客户端兜底」的明确结论。
**结论对 W1（客户端）和 W2（发现）都有用**：客户端占位策略、排序无效区间的处理，都依赖这里的真实口径。

## 2. 现状（来自数据体检，2026-10-22）

| 字段 | bangumi（556,342，97.3%） | otaku_site（15,318，2.7%） | 全库合计 |
|---|---|---|---|
| `cover_source_url` | **0.0%** | 99.6% | 约 2.7% |
| `rating_value` | **34.4%** | 100% | 36.2% |
| `summary` | 84.3% | 100% | — |
| `title` / `tags` / `release_year` | 91–100% | 79–100% | 可用 |

**最大缺口是封面**：97% 的条目（几乎全是 bangumi 侧）在列表里是占位图，上线观感第一道坎。

## 3. 根因（已查清，决定性）

- **bangumi 这 556,342 条来自本地档案快照**：`dump.zip` 里的 `subject.jsonlines`（Bangumi 官方数据集档案，约 1.86 GB），**该档案不含 `images` 字段**。sync-python 的 `bangumi` 源是纯本地档案读取，没有任何 live Bangumi API 客户端（见 `sync-python/README.md` 与 `sync/bangumi.py`）。
- **otaku_site 这 15,318 条来自在线站点 API**（`/api/contents` 返回 `cover_url`），所以 99.6% 有封面。
- **评分缺口同理**：bangumi 档案里评分覆盖本就只有 34.4%；otaku_site 100%。

**结论**：封面 / 评分的缺口是「上游档案 / 来源就没给」，不是我们入库时弄丢了。要补，必须从 Bangumi 上游重新取，不能靠现有来源站。

## 4. 选项与权衡

### 4.1 封面（核心）

| 选项 | 做法 | 可达覆盖率 | 代价 | 约束 |
|---|---|---|---|---|
| **A. Bangumi API 补封面** | 用存储的 `bangumi_id` 调 Bangumi 官方 API 取 `images`，回写 `cover_source_url` | 接近 Bangumi 自身覆盖（绝大多数条目有图） | 需 Bangumi API 令牌；新增一个只读上游客户端；约百万次调用要限流 | **走 PR 通知**（开新功能=通知，确认=确认收到、非征求同意）；令牌源=Bangumi 官网开发者工具或其镜像站；**密钥不入库**硬约束：令牌存环境变量、绝不进仓库 |
| **B. 换含 images 的档案** | 查 Bangumi 是否另有含 `images` 的 dump / 能否批量取（体检报告原话「补法待调研」） | 取决于新档案 | 调研 + 重新灌入 | 需确认档案来源合规、可对外用 |
| **C. 接受 + 客户端兜底** | 不补 bangumi 封面，靠 W1.5 占位策略；otaku_site 2.7% 有封面 | 维持 ~2.7% | 零成本 | 观感妥协，但合规、可上线 |

### 4.2 评分（建议降优先级）

- bangumi 评分覆盖 34.4%，体检报告明确「成本高，不建议补」。
- **决定：本轮不主动补评分**。W1.5 排序（按评分）对 65% 条目无效的问题，由客户端在排序说明 / 占位上解释（「暂无评分」而非沉底误导），不靠数据补全解决。
- 若未来做 A，可顺带补评分（同一 API 调用已返回 `rating`），属可选增益。

### 4.3 简介（无需动作）

- bangumi 84.3% / otaku_site 100%，已可用，不列为工作项。
