> 本文档为项目介绍，描述当前规划方向；相关能力为预期目标，不代表已经实现。
>
> **项目总目标、工作流范围与授权规则见 [`docs/project-charter.md`](docs/project-charter.md)**（2026-10-22 起生效）。
>
> **产品定位（技术判断的上位依据）见 [`docs/product-positioning.md`](docs/product-positioning.md)**（2026-10-24 起生效）——契约、接口与数据模型的取舍若与定位冲突，以定位为准。

## 1. 项目定位

本项目不是建设一个通用的 ACGN 数据服务平台，而是建设一套**面向多个独立网站的跨平台适配与客户端解决方案**。

核心目标：

1. 帮助多个独立网站适配不同客户端平台，包括 Web、Android、iOS 和桌面端等，具体支持范围按阶段确定。
2. 考虑不同运行和部署环境，使客户端与后端服务能够在约定环境中运行。
3. 让接入网站能够利用已有技术体系获得相应的客户端能力，减少每个网站从零开发客户端的重复工作。
4. 各网站保持独立运营，保留各自的品牌、业务逻辑和用户数据边界。

本项目面向多个独立运营的网站提供通用客户端解决方案，通过可复用的技术底座，帮助各网站降低独立开发和维护客户端的成本。每个网站都是独立的服务对象，拥有自己的内容与业务边界；平台共享通用能力，但不将各网站合并为一个统一的内容服务。

Otaku 是第一个接入对象，但继续独立运营：不合并网站、不以迁移 Otaku 全部业务为目标，也不默认共享不同网站的账号、收藏、浏览历史等用户数据。

**账号与个人数据：** 平台提供账号，以及个人收藏、观看状态等能力，**纳入本项目范围**（按验收清单的阶段 2 实施）。
**身份归属：** 客户端是**接入网站的客户端**，用户是网站的用户——**网站已有用户时，客户端应优先使用网站账号登录**（登录与授权在网站侧完成，密码不经平台，平台只持可撤销令牌）；网站尚未开放授权端点时，用平台账号过渡，**过渡不是产品终态**，且须预留切换路径。
详见 [`docs/product-positioning.md`](docs/product-positioning.md) §4 与契约 §4.8。各接入网站保留各自的运营与用户数据，平台不默认读取或共享各网站原生的浏览历史与评论。

**阶段范围说明：** 第一阶段只服务 Otaku 一个站点，用于验证端到端闭环；多站点/租户适配（品牌、配置、接入规范）不在第一阶段设计范围内，留待后续阶段由团队明确。

**产品原则（客户端与来源网站协作）：** 优先通过客户端提供统一、便捷的使用体验，在需要使用来源网站原有页面或功能时，保留与对应原页的关联；不以封闭用户或替代来源网站为目标。

## 2. 技术栈与模块分工

技术栈已经确定：

| 模块 | 技术 | 主要职责 |
| --- | --- | --- |
| 客户端 | Flutter | 跨平台客户端，页面展示与用户交互，通过 API 获取数据 |
| 后端 | Java / Spring Boot | 后端接口、业务处理与数据持久化 |
| 数据服务 | Python | 数据获取、清洗及相关处理 |
| 数据库 | MySQL | 数据持久化 |

团队按三人协作，分别负责 Flutter、Java 后端和 Python 数据服务。
各模块负责人可以自主决定模块内部的实现方式。涉及模块之间的接口、数据结构或依赖关系时，需要与相关成员协商一致。

## 3. 第一阶段共同目标（最小闭环）

第一阶段以打通一个**可验收的最小闭环**为目标，而不是一次性建成完整平台。围绕真实产品目标，最小闭环至少包含：

1. 至少一个网站能够通过约定的方式接入或提供业务数据。
2. Java 后端完成必要的接口处理。
3. Flutter 客户端在第一阶段选定的平台上调用真实接口并展示该网站的内容。
4. 能够说明基本运行环境、必要配置和验证方式。

各模块可以并行开发。后端和数据服务尚未完成时，客户端可以使用模拟数据推进工作；后端也可以使用测试数据独立开发和验证。模拟数据用于前期开发，不能代替第一阶段真实数据链路的验收。

**关于 Python 数据获取与处理是否纳入最小闭环：** 这是待团队确认的事项，不应为了保留技术栈而强行让所有数据都经过 Python。若接入网站本身已提供可用的数据接口（例如 Otaku 现有站点已暴露内容查询与搜索接口），最小闭环可以由「网站接口 → Java 后端适配 → Flutter 展示」直接构成；Python 数据获取与处理作为数据接入的补充路径，其是否进入第一阶段闭环、承担哪些字段的补充（如封面、标签），由团队结合实际数据来源与现有方案共同决定。

## 4. 协作原则

### 4.1 自主实现
各模块负责人自主安排模块内部的设计、编码、目录结构、开发工具和实现步骤。本 README 只规定项目共同目标、技术边界和协作要求，不限制成员在自己负责的模块内作出合理的技术决策。

### 4.2 接口协商
不同模块需要协作时，相关负责人应共同明确必要的接口约定，包括数据字段、请求与响应格式，以及必要的错误处理规则。接口一旦被其他模块依赖，涉及变更时应及时通知相关成员，避免各自按照不同约定开发。

### 4.3 及时同步
开发过程中遇到跨模块依赖、接口冲突或影响整体进度的问题，应及时与相关成员沟通。完成可供其他模块调用的功能后，应提供必要的使用方式、验证结果或联调信息。

### 4.4 尊重独立网站边界
对接 Otaku 或其他网站时，应明确需要复用的能力和数据范围。不得默认需要合并网站、迁移全部业务或共享用户数据。

### 4.5 数据合规
使用外部数据源时，应遵守相关使用条款、访问限制及适用法律法规。不要将密钥、密码等敏感凭据提交到公开仓库。

### 4.6 协作文件边界
不擅自删改其他协作者提交或负责的文件。如确需变更涉及他人模块的接口、数据结构或相关文件，应事先与相关协作者协商一致。

### 4.7 以仓库为协作依据
团队的现状以仓库中的文档、Issues 与 Projects 状态为准，不依赖线下口头同步。任何结论、接口约定与任务进度都应及时写回仓库，便于成员直接通过仓库判断现状。

## 6. 完成标准（第一阶段）

第一阶段以实际运行结果为准。最小闭环应能够打通：至少一个网站的内容可通过约定方式进入系统，经 Java 后端处理后，由 Flutter 客户端在选定平台上真实展示。

完成相关工作时，应确保必要的接口信息、运行方式和验证结果能够交接给其他成员。具体功能的实现细节和模块内部验收方式，由对应负责人结合项目目标自行确定；涉及整体集成的事项，由相关成员共同确认。

账号与个人收藏、观看状态等能力按验收清单的阶段 2 验收，可在第一阶段闭环之后开展。
